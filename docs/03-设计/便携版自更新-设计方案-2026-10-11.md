# 便携版自更新（zip 覆盖）—— 设计方案

- 定位：**便携版自更新**的设计正本（决策面）——施工面 = `02-执行/便携版自更新-执行方案-2026-10-14.md`（批序 / 靶点 / 门），状态住活账。接续现行「只提示不自动装」的更新检查（`src/update/check.ts`），把「去下载页」升级为「应用内下载 + 退出后自查替换」。**不做 electron-updater**（其 win 侧实现为 NSIS 安装包更新，与已拍板的便携 zip 发行形态冲突）。不属于本档：实施落点与门禁明细（住执行方案）。
- 实现锚（现状）：`src/update/check.ts`（检查客户端）、`src/update/semver.ts`（比较器）、`src/studio/server/api/app-info.ts`（端点）、`UpdateBanner.vue`（横幅）、`src/desktop/ipc.ts` 的 `desktop:open-external`、`electron-builder.yml` 的 win zip target。

---

## 一、目标与不做面

**目标**：用户在应用内一键完成「下载 → 校验 → 退出 → 替换 → 重启」，全程不需要知道 zip 放在哪、不需要手动解压。

**不做**：
- 不引入 `electron-updater`（需 NSIS 安装包或正式签名，两条都与现状冲突）。
- 不改发行形态（win 维持便携 zip；mac 维持 dmg + ad-hoc 签名）。
- 不做增量/差分更新（zip 全量替换；主程序约 200MB 级，全量下载可接受）。
- 不做静默后台自动更新（用户不点就不动——与「AI 与网络动作都让作者知情」的既有取向一致）。

---

## 二、为什么必须由外部进程完成替换

Windows 会锁住正在运行的 `CLWriting.exe` 与已加载的 `.dll`（`chrome_elf.dll`、`ffmpeg.dll`、`v8_context_snapshot.bin` 等）。**这是 OS 层行为，与选哪个库无关**。因此「应用自己解开自己的目录」在自身存活期间不可能成功。

三种可行形态：

| 形态 | 机制 | 判定 |
|---|---|---|
| A. 外部助手 | 应用起一个 detached 助手进程，自身退出，助手等锁释放后替换 | **选定** |
| B. 原地覆盖（重启后） | 应用先把新 zip 解到临时目录，标记「待替换」，下次启动最早期由新版本自己搬 | 备选（见 §三） |
| C. 依赖脚本 | 用 `.cmd` / PowerShell 做替换 | 否决：执行策略与杀软启发式风险更高，且难做原子回滚 |

**形态 A 的替换策略：目录交换，不做原地覆盖。** 原地覆盖一旦中途被打断（断电、用户杀助手、杀软拦截），会留下「半新半旧」的目录，且**无法回滚**——这是最坏结局。目录改名在同一卷上是近乎瞬时的元数据操作，因此流程恒为：

```
解压到同级新目录 → 旧目录改名 .old-<版本> → 新目录改名成正式名 → 重启 → 启动成功后删旧目录
```

任一步失败，把旧目录名改回来即可回滚。代价是替换期间需要约一份应用体积的空闲磁盘（便携软件可接受）。

---

## 三、形态 A 与 B 的取舍

**形态 B（自搬）**：应用退出前把新版本解压到 `<应用目录>/../CLWriting-<新版本>-staged/`，并写一个 `pending-update.json`；下次启动时由一个**极早期**的引导步骤检测到标记，改为「启动助手完成替换，然后重启」。
- 优点：不需要在替换时让助手等进程（助手只在下次启动的早期跑，此时自己就是新版本，文件锁问题转化为「自己换自己」——仍需助手，因为运行中的自己同样被锁）。
- 缺点：实际仍需助手（自己换自己同样被锁），只是把「等进程退出」换成了「启动早期介入」；而用户在下次启动时会经历一次「闪一下又重启」，观感更差。

**结论：选 A。** 一次退出、一次重启，语义最直白；且「用户点了更新按钮」本身就是明确的动作意图，退出是预期的。

## 四、组件设计

### 4.1 下载器（主进程）

- 落点：`<userData 共享根>/更新缓存/<版本>/CLWriting-<版本>-x64.zip`（多实例共用一份；放用户数据目录而非应用目录，避免替换时被一起搬走）。
- 源：GitHub release 资产（与检查器同源，`src/update/check.ts` 已能从 releases API 拿到 tag；需扩展为取 `assets[]` 里 `CLWriting-*-x64.zip` 的 `browser_download_url` + `size`）。
- 校验：**必须有** sha512 或 sha256 校验（发布链随包产出校验值，或从 release body/资产清单取）。校验失败即删文件并报错，绝不解压不可信字节。
- 进度与取消：流式下载 + 进度回传（端点走 SSE 或轮询，看 §4.5）；支持取消，取消即删半成品。
- 出站网络：内置 `fetch` **不读** `HTTPS_PROXY`（`src/rag/embed.ts` 已实测登记 G102），代理环境需走 Electron `net` 模块或显式代理配置。**这是必须验证的第一项风险**（见 §七）。
- 断点续传：不做（全量重下更简单）；但网络中断要能重试且不残留坏文件。

### 4.2 替换助手

- 形态：同一可执行体的特殊模式（`CLWriting.exe --apply-update --payload <zip> --target <dir> --pid <pid>`），不额外分发第二个二进制。
  - **理由**：便携 zip 里只有一个 exe，额外塞一个助手 exe 会引入「助手自身也要更新」的鸡蛋问题；复用主 exe 则助手天然有版本，且不增加分发面。
  - 约束：该模式下必须**极早判定、极早返回**——在任何窗口、日志、单实例锁、server fork 之前完成分支，避免助手进程变成第二个「应用实例」（尤其不要触发单实例锁逻辑，否则会与真实实例互踢）。
- 等待逻辑：轮询目标 exe 是否可独占打开（或等指定 pid 消失），**带超时**（建议 120s）；超时则放弃并回滚，把失败写进日志供下次启动展示。
- 替换序列（每一步失败即可回滚）：
  1. 校验 zip 完整性与目标目录可写性（**预检**，避免中途才发现只读盘）
  2. 解压到目标同级的新目录 `<target>-new-<版本>`（同卷，保证改名是元数据操作）
  3. `<target>` → `<target>.old-<旧版本>`（若已存在同名旧目录，先删或改用带时间戳后缀）
  4. `<target>-new-<版本>` → `<target>`
  5. 重启新 exe
  6. 新版本启动后（主进程就绪）删 `<target>.old-*`；删不掉就留着，下次启动再试
- **不搬 userData、不搬书库**（书库在用户自选目录，userData 在系统目录，都不在应用目录内）——这一点已在根 README 承诺「书稿都在书库文件夹里，怎么升级都动不到它们」，助手必须不违反该承诺。

### 4.3 多实例与多库多窗（本产品特有风险）

本产品明确支持同机多库并窗（每库一个实例、各自 userData），可同时开多个实例，**共享同一应用目录**。因此：

- 只要有任一实例存活，`CLWriting.exe` 就被锁 → 步骤 3 的目录改名会失败。
- 设计对策（三选一，拍板 = §九 D1 取方案一）：
  - **方案一（推荐）**：助手替换前先检测同目录下是否有其他存活实例（复用 `src/desktop/app-instance-guard.ts` 的文件锁/pid 存活探测设施）；有则**放弃并回滚**，UI 提示「请先关闭其他窗口后重试」。
  - 方案二：助手等待**全部**实例退出（长超时，例如 10 分钟），期间给用户一个可见的等待提示。实现复杂（助手无 UI，得靠落地文件让下次启动显示）。
  - 方案三：只允许「最后一个退出的实例」触发替换（各实例退出时置标记，助手等到标记齐）。最平滑但最复杂。
- **不建议**主动 kill 其他实例（用户可能有未保存的稿子；本仓有 journal 崩溃恢复，但主动杀进程不在本设计授权范围内）。

### 4.4 写不进去的位置

用户在 `C:\Program Files\`、只读网络盘、或受管目录里解压便携包——替换必然失败。要求：预检阶段（步骤 1）就发现并以**人话**说明（「应用所在目录不可写，请手动下载新版本覆盖」），不要静默失败、不要留下半成品。

### 4.5 前端交互

- 入口：`UpdateBanner.vue` 在「去下载」旁新增「下载并更新」（本轮仅 win + 打包态显示，判据 = 桌面桥方法存在性；浏览器版保持「复制链接」降级）。
- 状态机：`idle → downloading(进度%) → ready(待重启) / failed(原因 + 重试) → applying(退出中)`。
- 进度回传（拍板 = §九 D3）：**主进程下载 + 桌面桥 IPC 事件**，不走 SSE——下载与替换都落在主进程 / 助手侧，走 SSE 需新增主进程→server 子进程转发链与事件名三处同步，复杂度高于收益；浏览器版无桥，保持「复制链接」降级。
- 「待重启」态必须显式要求用户确认（有未保存内容时先走既有保存链），再触发退出。
- 失败提示要区分：网络失败 / 校验失败 / 目录不可写 / 有其他实例在跑（分别对应可操作的建议）。

### 4.6 与既有检查链的关系

- `src/update/check.ts` 的检查结果增加 `asset`（下载 URL + 大小 + 校验值）；无资产（例如只有源码包）时不显示「下载并更新」，退回「去下载」。
- 保留「不落盘、进程内一次」的检查语义不变；下载与替换是**用户显式动作**，与静默检查解耦。

## 五、发布链改动

- `electron-builder.yml` 的 win zip target 不变（助手复用主 exe）。
- Release 资产附**校验值**——发布链已产出 `SHA256SUMS.txt`（`.github/workflows/desktop.yml` 的 release job 合并重生成），自更新直接复用（拍板 = §九 D2），无需改发布链。
- 版本号比较沿用 `src/update/semver.ts`（已处理 rc 语义：`1.0.0-rc.4 < 1.0.0`）。
- **不发增量补丁**，不做 staged rollout。

## 六、风险与缓解

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R1 | 内置 fetch 不读代理 → 代理用户下载必失败 | 高（该用户群在境内占比不低） | 优先验证；改用 Electron `net` 或读既有代理配置；失败要有可操作提示 |
| R2 | 杀软对「等进程退出就替换二进制」的启发式拦截 | 中高（本应用**未签名**，态势更差） | 助手模式不隐藏自己；失败回滚并留报告；README 说明；长期靠购证签名 |
| R3 | 多实例导致改名失败 | 中 | 方案一：检测到其他实例即回滚 + 人话提示 |
| R4 | 替换中途断电 → 目录处于「旧已改名、新未就位」 | 中 | 助手启动时先做**恢复检查**：若发现 `<target>` 缺失但存在 `<target>.old-*`，自动改回；这也是「交换而非覆盖」的核心价值 |
| R5 | 只读/受管目录 | 中 | 步骤 1 预检 + 明确文案 |
| R6 | 磁盘空间不足（需一份额外体积） | 低中 | 预检 `statfs` 可用空间，不足即拒 |
| R7 | 助手模式误入正常初始化（开窗/起 server/抢单实例锁） | 高（若发生，行为诡异且难查） | 在 `main.ts` 最顶部按 argv 分支并 `return`，且加测试钉住「助手进程不建窗口、不起 server、不请求单实例锁」 |
| R8 | 新版本启动即崩（坏包） | 中 | 校验 + 启动成功才删旧目录；保留新旧两版各一次的机会（旧目录留到下一次启动再清） |
| R9 | mac 侧 | — | 本设计**只做 win**。mac 的自动更新需正式签名（现为 ad-hoc），购证后另开方案 |

## 七、实施前置验证（四项，全过才动工；执行序与分工见执行方案 §一）

1. **代理可达性**：在代理环境实测「内置 fetch vs Electron `net`」能否下载 GitHub 资产。这是本方案的存亡问题——若两条路都不通，方案对代理用户无意义。
2. **杀软行为**：在装有主流国产杀软的机器上，用最小原型（一个 exe 等待另一个 exe 退出后改名替换）实测是否被拦。
3. **多实例改名**：实测「任一实例存活时，同目录改名是否必然失败」——确认 R3 的存在与该走哪个方案。
4. **助手自改目录**：助手从被改名目录内运行（`<target>/CLWriting.exe --apply-update`）时，win 是否允许把该目录改名——锁的是 exe 文件、未必锁父目录名；这是交换序成立的前提，不过则助手改为从暂存副本运行。

机制项（3、4）可在 CI win 腿脚本化实跑；环境项（1、2）与 §八 真机验收在 Windows 真机并作一次会话（分工见执行方案 §一「验证面三分」）。

## 八、验收口径（实施时）

- 正常路径：点更新 → 下载有进度 → 校验通过 → 退出 → 目录已替换 → 新版本启动 → 旧目录被清。
- 回滚路径：在替换各步人为中断（杀助手、拔盘、置只读），下次启动必须是**可用状态**（新的或旧的，不能是坏的），且有可诊断留痕。
- 多实例：第二实例在跑时点更新 → 得到明确提示而非静默失败或目录损坏。
- 代理/离线：下载失败有可操作提示，且不留坏 zip、不改动应用目录。
- 助手模式隔离：`--apply-update` 进程不建窗口、不起 server、不抢单实例锁（用例钉住）。
- 不变量：**任何更新路径都不得触碰书库与 userData**。

## 九、决策点（已拍板）

| # | 决策 | 拍板结果 |
|---|---|---|
| D1 | 多实例策略 | 方案一；且落双闸——点击时预检（执行方案 §五 C1）+ 助手预检（§四 B1） |
| D2 | 校验值来源 | 复用现有 `SHA256SUMS.txt` 资产（发布链已产出，零改动）；可优先实测 GitHub 资产 `digest` 字段 |
| D3 | 进度通道 | 主进程下载 + 桌面桥 IPC 事件（弃 SSE；理由见 §4.5） |
| D4 | 助手形态 | 复用主 exe 的特殊 argv 模式；前置 = §七 第 4 项（助手自改目录可行） |
| D5 | mac 侧 | 本轮不做；购证签名后另案（维持） |
| D6 | 是否提供「仅下载不替换」 | 不单列渐进档，全链一次做；作失败兜底（下载成功但替换不可用时提供「打开缓存文件夹」），日后若求早交付可于批 A 后单列 |

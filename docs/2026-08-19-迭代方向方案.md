## 二、方向 A：架构成色——兑现「两百万字不崩」

### A1. 树红点增量化（性价比最高的一刀）

**现状**：每次打开书/刷新树，前端 fire-and-forget 拉一次 `GET tree-issues`（`src/studio/web-next/src/stores/tree.ts:111`），服务端 `collectTreeIssues` 对全书逐章同步整读（`src/check/run.ts:224-244`，每章 `checkWithDb` 内 `readDraft` 还把文件读两遍级别，`src/format/draft.ts:22`），跑在单一事件循环里。已有 `BatchCheckContext`（CC-P1-3）消掉了 O(N²)，但 O(N) 逐章同步读仍在。

**方案**：机检是零 token 纯函数，结果是章内容的确定函数——直接套用 `src/cache/rebuild.ts:96` 已验证的 (mtime, count, size) 三元组基准模式：

- 每章机检结果按 stat 指纹（path + mtime + size）缓存进 `.cache/index.db` 新表；
- 端点只重查指纹变过的章 + verdict 变过的章（verdict 驳回会升红点，`check/run.ts:241`）；
- 首查仍重，改为后台跑完经 SSE 推红点，不阻塞树渲染。

**效果**：打开书的冻结从 O(全书) 降到 O(变更章)。不改内核、不加线程。

**验收**：700 章规模下，二次请求 tree-issues 仅重查指纹变更章（单测断言文件读次数）；红点与逐章重算结果逐字节一致。

### A2. worker 包一层，不动内核

**现状**：`detectState`（`src/state/state.ts:94-193`，100 行）做 journal 扫描 + 整书目录树递归 walk（`scanCloudCopies`，`src/git/exec.ts:89`）+ rebuild + manifest 逐条探测，全同步；工作台进页即拉（`api/state.ts:49`，无缓存），overview 有 5 秒 TTL 缓存（`api/overview.ts:29`）但缓存过期后照样冻结。git 的 `spawnSync`（15 秒超时，`src/git/exec.ts:33`）在 AI 落稿保存路径上（`api/rewrite.ts:135`、`api/draft.ts:51`、`self-heal.ts:381`，仅 git 后端书）。全项目 worker_threads 零使用。

**方案**：保持「脚本面为主」的确定性内核原样，在 studio server 层加一个 job-queue worker，承接 rebuild / collectTreeIssues / detectState 的文件密集部分。两个有利条件使方案干净：

- node:sqlite `DatabaseSync` 在 worker 内照常可用，worker 有独立事件循环，同步 IO 不阻塞主线程；
- 全部 DB 连接都是短生命周期，唯一长驻单例是事件库（`src/events/store.ts:114` 引用计数），留在主线程即可，隔离边界天然清晰。

接口形态：worker 收 `{bookRoot, config, job}`, 回 JSON；server 层包成 Promise，请求处理器全部真正 async。**库 API 保持同步签名不变**，现有 267 个测试文件直调内核的用例零改动，只有服务层调用点变 async。

**验收**：大书请求期间 SSE 心跳不断、Electron 窗口可交互；worker 内核单测沿用现有测试。

### A3. RAG：先不上 ANN，做惰性指纹校验 + 预存范数

**现状**：`recall()` 流程是「全量读回全部向量 BLOB → 全书逐章 SHA-256 指纹校验 → 线性余弦排序」（`src/rag/index.ts:393-448`）。200 万字 ≈ 3.5 万块 / rag.db ~277MB，余弦实测 320-350ms 可接受；指纹校验每次召回读 700 个正文文件才是请求路径上的全量 IO。scale 测试界值 2 秒且注释自带跳闸语义（`test/rag/scale.test.ts:43`：「若此断言开始失败，那时再议向量索引——而不是放宽界值」）。

**方案**：

- **倒序校验**：先排序取 top-K'（如 20），只对命中章做指纹校验，过期则剔除降补，收敛到 top-5。召回质量不变（校验本来就是过滤闸），文件 IO 从 700 章 → ≤20 章。
- **预存范数**：写入时算好向量 L2 范数存列，余弦退化为点积，数学量减半。
- ANN 明确**不做**。真到线性扫描跳闸那天，node:sqlite 支持 loadable extension，sqlite-vec 一条路即可，届时再议。

**验收**：scale 测试保持全绿；新增断言「单次召回指纹校验的文件读 ≤ K'」。

### A4. 结构化日志通道——打包前近乎必做

**现状**：src 下 `console.error` 37 处 + `console.warn` 13 处，格式均为手写 `[tag] 中文` 字符串，无级别、无结构化、无落盘。全库无 logger 模块。关键论据：**Electron 打包态下 console 输出到无人看见的地方**——真实用户环境里这 50 处留痕全部蒸发。事件库迁移失败仅 `console.error`（`src/events/store.ts:399`）且旧库数据可找回，但用户无从知晓。

**方案**：

- 一个小 logger 模块：JSONL 按天落 `userData/logs/app-YYYYMMDD.log`，字段 `{ts, level, tag, msg, err?}`，保留 7 天自动清理；
- grep 驱动机械替换 50 处调用点，一天量级；
- 事件库迁移失败升级为**启动横幅**：「迁移失败，旧库保留于 <路径>，可找回」——走既有 healthCheck/态 1 通道即可。

**边界**：进程诊断归日志，业务观测归事件库（append-only SQLite），两条通道不合并——事件库是产品数据，日志是运维数据，保留策略不同。

**验收**：打包态运行产生日志文件；迁移失败场景用户可见提示。

## 三、方向 B：真实语料回归库——机检的「越用越准」

评审报告指出机检「手调正则 + 个案补丁、测试全是构造样例」。探查确认数据流真正缺的只有一环：**机检条目没有「误报」按钮**。作者裁决信号现存三处（review verdict、author/signal 删稿 diff、rule-hits），但机检面板上作者「看了但不改」的忽略完全蒸发——而这恰是误报治理的燃料入口。

### B1. 采集：误报按钮 + 事件落库

- `CheckPanel.vue` 每条红黄项加「误报」动作；
- 落一个 `check/false-positive` 事件（事件库 schema 现成，`src/events/types.ts` 加一个类型）；
- 载荷关键字段：`checkId`、章号、**命中区间前后 ±50 字摘录**——摘录就是语料本身。

### B2. 冷启动自举：从存量书零 UI 派生标注语料（最值得做的一步）

不改一行 UI，用「幸存者判定」从已写完的书直接派生语料：

- 机检报告已在事件库里（`check/report` 事件带 reds/yellows，`types.ts:236`）；
- 拿定稿正文对照：**命中区间在定稿中幸存 ⇒ 大概率误报；被改掉 ⇒ 大概率命中**；
- 同款 diff 技术已有先例：`src/ai/author-signal.ts:26` 就是保存时 diff 上一版 AI 稿跑规则命中。

收获列表走 learn 模块的候选制（`src/learn/index.ts` 作者勾选 → 入库），符合「程序建议、作者拍板」的一贯哲学。所有存量书立刻变成零成本标注语料，无冷启动。

### B3. 回归门：golden-master 测试

一个 vitest 集成测试重放全部语料摘录过当前检查器，断言「标了误报的不再命中」。此后任何词表/阈值/规则改动，复活一个误报就红 CI。测试从构造样例升级为真实文本，直接回应评审 5.2-4。

### B4. 词表进化与信息差词表派生

- 同一份语料按种子短语统计误报率（`imagery-seed.ts` 21 条现成分母），超阈值的注释/剔除；作者新标惯用短语进候选列表——沿用 learn 候选制入库 `src/check/` 词表。
- **信息差关键词从布线账本自动派生**：秘密本来就声明在 `布线/` 的账本 md 里，解析账本 front matter/标题派生默认关键词，比逐书手填 book.yaml 顺手，也符合「账本即真相」的既有口径。
- Beta 校准项（短篇字数阈值 `count.ts:508`、RAG 分块粒度 `rag/index.ts:41`）吃同一份语料定值。

**全链路零 token、确定性**，与 learn/机检现有风格一致。

**验收**：自举脚本对一本存量书产出候选语料清单；golden-master 测试在 CI 生效；误报按钮事件可查。

## 四、方向 C：超长篇上下文管理——补全金字塔中间层

### 探查核心发现

三层摘要体系（前章原文结尾 → 章摘要 → 卷摘要）中，**章摘要和卷摘要没有任何生成器**：

- `summaries` 表存在（`src/cache/rebuild.ts:246` 扫入 `定稿/摘要/`）、消费方存在（`src/process/prepare.ts:169` 章摘要 rank 1、`:331` 卷摘要 rank 3）、预算配置存在（`summary_chapter_max`，`src/format/yaml.ts:33`）——**唯独没有写这些文件的代码**，纯靠作者手写约定。
- 批量连写章间无共享内存上下文（`self-heal.ts` 的 `orchestrateBatch` 逐章独立闭环），只靠落盘文件重读传递；超过「近 1-2 章摘要 + 前章结尾 1500 字」的视野就断了。
- 备料预算闸已很完善（`prepare.ts:379` 两轮裁剪、flexibleRank 降档、RAG rank 5 最先砍），缺的不是调度而是**中间层内容本身**。

### C1. 章摘要生成器（单点杠杆最大）

- 挂「定稿」钩子：定稿时一次廉价 AI 调用（独立 task、低档位）生成 `定稿/摘要/章摘要/N.md`，受 `summary_chapter_max` 预算约束；
- 零新 UI；文件即真相，作者可手改，天然可覆盖；
- 自愈：prepare 发现第 N-2 章摘要缺失时从定稿正文补生成。

### C2. 卷摘要按需生成

prepare 需要 rank 3 段而 `定稿/摘要/卷摘要/N.md` 缺失时，从该卷已有章摘要链现场生成（输入 = N × summary_chapter_max 字，成本可控）。

### C3. 闭环到细纲：摘要金字塔服务规划

细纲 prompt 现在只有 总纲 1500 字 + 近 3 章标题 + 设定 + 进行中账本（`api/outline.ts:46-90`）——写到几百章时中间视野全靠总纲恒量。把**当前卷摘要**喂进细纲生成，一份数据两处收益（写作上下文 + 规划输入）。

### C4. 顺手校准 token 系数

`estimateTokens = chars × 0.6`（`prepare.ts:99`）是拍的。事件库 `llm/call` 同时记 `promptMeta.chars` 和 `usage.input`（`types.ts:207-220`）——拿现有遥测做实测回归，按模型分别拟合系数，备料预算闸立刻更准。

**明确不做**：批量连写章间内存直传（上一章结尾还在内存里省一次重读）。收益太小且违背「文件即真相」，落盘重读是对的。

**验收**：定稿一本含摘要钩子的书后 `定稿/摘要/` 自动生成；prepare 降档测试覆盖「有/无摘要」两态；细纲 prompt 包含当前卷摘要。

## 五、方向 D：用量/成本可视化——「不闷头烧钱」要看得见

### 探查核心发现：数据层几乎全就绪，前端连 API 都引了没渲染

- `aggregateTrace`（`src/ai/trace-stats.ts:107`）已按 task 聚合出 调用次数/成功率/平均重试/时长 P50·P95/总输入输出 token/**按日趋势**，端点 `GET /api/books/:name/trace-stats` 已上线；
- `WorkbenchView.vue:25` 已 import `getTraceStats`，但只渲染了其中的 ruleHits——byTask 聚合**一行 UI 都没有**；
- 记账「四路同口径」（成功/重试/中断/失败，`src/ai/runner.ts:399`）保证预算不可绕过；`usage` 里 cacheRead/cacheWrite 分开记录；
- 唯一有 cost 字段的 SSE usage 事件是 mock 的（`stream.ts:80` cost=0.0001 硬编码），真实链路 cost 恒 0（`stream.ts:106`）——**全库没有金额口径**。

### D1. 先把已有的渲染出来（后端零工作）

工作台加「AI 用量」卡片：按 task 出 调用次数 / tokens / 时长 P50·P95 / 成功率 + 按日趋势 sparkline。纯前端。

### D2. 加金额口径

- 设置 → AI 的供应商配置加**可选价格表**：每百万 token 四档单价（输入/输出/缓存读/缓存写——usage 本来就分档记，Anthropic 缓存读 0.1 倍这类模型能算准）；
- 聚合从 `llm/call` 事件算钱：每章成本、每日成本、本书累计；
- 展示粒度对齐作者心智：「这次自动写章烧了多少钱」。

### D3. 预算口径升级

- 现在预算闸是纯次数（`calls_per_chapter` 默认 8，`src/ai/calls.ts:154`）——有的章一次长上下文调用顶普通章十次，次数口径防不住；
- 四路记账已保证不可绕过，把 `checkAiCallBudget` 从次数扩展到 token/金额双口径（`budget.tokens_per_chapter` / `budget.cost_per_chapter`）是小改。

### 数据源分工（原则）

- `.cache/ai-calls.json`：继续只服务预算闸（chapter 块换章重置，是当前态）；
- `llm/call` 事件（append-only）：一切历史聚合与可视化的唯一真源。

**验收**：用量卡片展示 byTask 聚合；配了价格表的书显示金额；token 预算超限能拦住长上下文调用。

# 便携版自更新 —— 检查链代理（上游对照调研）

- 定位：便携版自更新余项「检查链不直读系统代理」（实录 = `02-执行/便携版自更新-执行方案-2026-10-14.md`「收口（Windows 面·批 D）」发现三）的**上游对照与本仓落法**——DSH（DeepSeek Harness，装机产物 `resources/app.asar` 内 `@deepseek-ai/dsh-http-proxy` 0.2.0-rc.2 全文）与 ZCode（开源仓 `github.com/zai-org/ZCode`，`main` 检出）两家 Electron 产品的代理实现盘点、对本仓的可行性判断与落地判据。不属于本档：决策本身（拍板 = 设计档 §九 D9，**取乙「检查迁主进程」**；落地与门 = 执行方案「收口（余项：检查链代理）」）；检查链与下载腿的既有设计与批序分别住设计档与执行方案。

## 一、问题面（本仓现状，2026-10-14 复读）

- 检查链跑在 studio server 子进程（`src/studio/server/index.ts:798` 起服后延迟一次调 `runUpdateCheckOnce`），出站走 Node 全局 fetch——不读任何代理（`src/update/check.ts`）；下载腿在主进程，走 Electron `net.fetch`，受系统代理（批 0 实测 154 MB 经代理 12.9 s 完成）。
- 批 D 实测：本机（系统代理 `127.0.0.1:5858`）子进程直连 `api.github.com` 超时；给子进程 `NODE_USE_ENV_PROXY=1` + `HTTPS_PROXY` 后 200——**环境变量注入是最短的修复腿**，且本仓运行时不设限：Electron 44.4.5 内置 Node 24.21.0（本机实测），该旗门槛 = Node 22.21+/24+。
- 波及面比「检查链」一词大：服务端子进程还承载 AI 链路（`@anthropic-ai/sdk` / `openai` 两个 SDK 未传自定义 fetch，出站同走全局 fetch）与 rag 向量端点（`src/rag/embed.ts`，现口径 = 「代理不支持、留痕缓办」）。今天配了系统/环境代理的用户，**整棵服务端子进程的出站都是直连**——检查链不提示只是其中一例。
- 因此「让子进程读系统代理」与「只让检查链读代理」是两件不同量级的事，选项据此分岔（§四）。

## 二、DSH：一套进程级策略 + 子进程环境注入

- 形态：一个进程级库（自研包 `@deepseek-ai/dsh-http-proxy`，非插件），启动时解析一次、装 undici 全局 dispatcher——「出站策略每进程只有一个答案，没有第二个实现可换、也没有比进程更窄的作用域可给」；普通 `fetch()` 与一切走到 `globalThis.fetch` 的 SDK 零改动受益。
- 解析口径：`http_proxy` / `https_proxy` / `all_proxy` / `no_proxy`，**小写优先、大写兜底**、空白视为未设（防空串遮蔽已设的大写名）；`ALL_PROXY` 兜两个 scheme，HTTPS 末位回落 HTTP 代理（Node 与 undici 自己都不做这层推导）；**不读 OS 系统代理**（明示的已知边界：只认环境变量，只切了代理应用开关的用户仍须自行导出变量）。
- 失败姿态：SOCKS / PAC / 不可解析 / 不支持的 scheme——报告（点名变量、不回显值）并**跳过该 scheme 直连**；「变量可能是为别的工具导出的，不能因代理不可用阻止启动」。
- 回环恒绕行：`localhost`、整个 `127.0.0.0/8`、`::1`、`0.0.0.0` 与 IPv4-mapped 拼写全直连——否则 Web UI、本地测试服、自带连接传输全部进代理成环；下发子进程的 `NO_PROXY` 四条字面量与匹配器自身（认整个 /8 段）**两份都在**，因为「一条列表项表达不了范围」。
- 子进程面（与本仓最相关的半页）：`proxyEnvironmentForChild()` 生成每键覆盖——**用户显式写过的键原样保留**（curl 用的 SOCKS 值不被本包的 HTTP 回落替换），用户未写过的 scheme 用解析值补齐（否则 Node 子进程不读 `ALL_PROXY`，父子路由分叉），旁路表恒为解析后的（只增不减）；恒带 `NODE_USE_ENV_PROXY=1`，**除非**将下发的值里有 Node 会拒的（SOCKS 等）——那时**扣下该旗**：Node 在该旗下于程序启动前解析 `HTTP(S)_PROXY`，非 http(s) 值会直接退出，子进程根本起不来。
- 一致性原则（一句可抄）：「一个分辨率、一个匹配器」——装进 dispatcher 的与对外的 `proxyForUrl` 必须同源，否则出现「一处按解析地址 pin、一处走隧道」的分叉。附带否决了 undici 自带的 `EnvHttpProxyAgent`（无 `HTTPS_PROXY` 时它会拿 HTTP 代理去隧 https，与「拒绝值后该 scheme 保持直连」的诊断相悖）。
- 验证法：每个出站调用点带一枚 `egress.spec.ts`（真代理 + 真传输，断言实际路由），仓库门拒绝裸 `new Agent()` 绕过全局 dispatcher；测试用回环假代理断言真请求确实过了代理。

## 三、ZCode：按出口分别定策 + 显式配置优先

- 桌面主进程：`session.setProxy` 管 Chromium 网络栈，**按出口分策**——`defaultSession`（自身对后端与模型 API 的流量）**刻意 `direct`**：「收敛到设置页的显式配置，不被本机系统代理左右」；内置浏览器 partition 用 `system` 跟随（注释：留空时不跟系统代理，需代理的站点只剩 `ERR_CONNECTION_TIMED_OUT`，用户无从下手）。
- 独立 Node 进程不吃会话代理：`packages/services/src/providers/api/nodeApiNetwork.ts` 注释明说「Host 是独立 Node 进程，Electron `Session.setProxy` 不会影响它的 `globalThis.fetch`」——于是在 Host 出站口**按请求注入 undici dispatcher**（`ProxyAgent`），刻意不把 telemetry 等其它裸 fetch 全局改道；dispatcher 按路由键缓存、重建与释放时收口。
- CLI/子进程面：`applyNetworkEgressEnv`（`apps/zcode-cli/packages/adapters/src/network/subprocess-env.ts`）给子进程按平台写代理键（win 大小写不敏感地先删再写，防旧值穿透）；值先规范化（无 scheme 补 `http://`）；解析优先级 = 显式配置 > 专用环境键 > 透传捕获的用户代理键。
- CLI 出站另有一套自造 fetch（`proxy-fetch.ts`）：按请求解析代理、用 `proxy-agent` 的 `ProxyAgent` 走 node http/https 隧道——「不用全局 dispatcher」的第三条路也走得通，代价是自持一套 fetch 适配（含取消/回压/响应体转换）。
- 与 DSH 的取向差：DSH = 一套策略覆盖全进程 + 全局 dispatcher；ZCode = 每个出口单独定策、显式配置优先、OS 系统代理只给浏览器面用。两家共同点：**都不让 OS 系统代理自动作用于自家 Node 出站**——因为两家都有「设置页显式代理」这个用户面；本仓没有，系统代理是「只有系统代理」的用户唯一入口，这条差异决定本仓不能照抄「刻意直连」的取向。

## 四、本仓落法选项（已拍板取乙）

- **甲：全子进程跟随系统代理（env 注入，DSH 子进程面同构）**。主进程用 `session.resolveProxy`（批 0 实测返回 `PROXY 127.0.0.1:5858`）解析目标主机代理，经 `buildChildEnv`（`src/desktop/server-manager.ts`，受控键纪律的现成单点）注入 `HTTP(S)_PROXY` + `NODE_USE_ENV_PROXY=1`；必带三件——**回环 `NO_PROXY`**（子进程内 rag 与 AI 端点常有本机/内网形态，不旁路即改道成环）、**scheme 校验**（`resolveProxy` 可给 `SOCKS5`/`DIRECT` 行；给旗喂非 http(s) 值子进程会起不来——照抄 DSH 的扣旗判据）、**与下载腿同源**（同一解析结果，防两腿再分叉）。收益远超「更新提示」本身：代理用户今天整棵服务端子进程直连，云模型与 rag 远端端点都不可达——甲一招同时解。代价：全子进程出站改道，是一次显式行为拍板（AI 链路 + rag + 检查链三面同时翻）。**本轮不取**：属更大行为面（连带改道 AI 链路），需另开批单独拍板。
- **乙：检查迁主进程（`net.fetch` 取数，结果下发端点）——已采纳**。波及面最小、与下载腿同源；代价 = 扩主↔子协议（现仅 ready/boot-error/shutdown-done 三种消息，`src/desktop/server-proc.ts`）与检查结果下发落态。ZCode 的 Host 模式是近亲（按出口注入 dispatcher）。落地 = `createUpdateCheckHost`（`src/desktop/update-controller.ts`）：`net.fetch` 跑检查 → parentPort 消息 → 子进程 `applyUpdateCheckResult`；端点读口与前端口径零改动。
- **丙：维持现状（口径化）**。把「仅系统代理的用户收不到更新提示、且服务端出站全直连」写成现行口径，与「预览通道检查开关」后置项并批再议。**不取**（乙的成本已被证实很小：一处宿主 + 一条消息，AI / rag 面零触碰）。

## 五、落地判据（照抄即可）

- 真代理验证：回环假代理（记录请求）+ 真子进程跑一次检查——断言请求确实过代理（DSH 的 install.spec 思路）；下载腿同法对照。
- 负向对照三枚：撤 `NODE_USE_ENV_PROXY` → 直连（批 D 已证）；撤回环 `NO_PROXY` → 本地端点请求进代理（回环旁路的必要性证明）；SOCKS 值注入负例 → 确认扣旗后子进程可正常启动（不进「起不来」形态）。
- 若走甲：AI 链路（两大 SDK）与 rag 的既有用例跑一遍确认无回归；rag 的「代理留痕缓办」口径同批改写（`src/rag/embed.ts` 的 `warnProxyEnvOnce` 语义反转）。

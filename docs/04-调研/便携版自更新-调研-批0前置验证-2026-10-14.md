# 便携版自更新 —— 批 0 前置验证（调研）

- 定位：便携版自更新**批 0 四项前置验证**的 Windows 真机实测记录与可行性结论（2026-10-14；win32 10.0.26300 / x64，Electron 44.4.5，系统代理 `127.0.0.1:5858` 在跑，火绒 6.x HipsDaemon 在跑）。不属于本档：决策本身（助手形态改「暂存副本」的落点住 `03-设计/便携版自更新-设计方案-2026-10-11.md` §七.4 / §九 D4）；批次落点与门 = `02-执行/便携版自更新-执行方案-2026-10-14.md` §八。
- 方法：探针跑**生产模块**——把 `check.ts` / `asset.ts` / `download.ts` / `extract.ts` / `cross-process-lock.ts` / `update-helper.ts` 用 esbuild 打成 CJS，经注入在 Electron 主进程 / `ELECTRON_RUN_AS_NODE` / 纯 Node 三种宿主下真跑；夹具 = 打包产物整棵复制（`clw-probe/swap/appN`、`elN`）+ 本地假锁/假 pid；第 1 项用真公开 release 资产（154 MB 便携 zip）。探针与原始产物在仓库外 `G:\...\clw-probe\`（不作实施依据，关键证据均内联于本档）。

## 一、结论（四项）

| # | 验证 | 判定 | 一句话结论 |
|---|---|---|---|
| 1 | 代理可达性 | **过** | Electron `net.fetch` 全程受系统代理：154 MB 包 12.9 s 下载完成，sha256 与资产 `digest` 逐字节一致；302 实际落 `release-assets.githubusercontent.com`（设计档所写 `objects.githubusercontent.com` 已过期）；全局 fetch 为直连通道（不吃系统代理），链路按 `net.fetch` 落码无误 |
| 2 | 杀软行为 | **过（未拦）** | 火绒在跑条件下，「等 pid 退出 → 目录改名交换 → 重启新版」最小原型与**真助手全链**多次真跑通过（applied/ok），无拦截、无弹窗、无需回滚 |
| 3 | 多实例与改名 | **过** | 实例存活时同目录改名必败（EPERM，退避重试 3 次不让）；进程杀后**立即**可改；`queryLockHeld` 三态判定（在飞空锁=持 / 过龄空锁=不持 / 死 pid 残留=不持）与实测逐条一致 |
| 4 | 助手自改目录 | **原形态不过 → 回退形态过** | Electron 进程**自镜像在目标目录内**时，目标目录改名必败 EPERM（真 `node.exe` 同形态不挡、Electron 镜像移出目标即通——三连对照）；已按设计档/执行档预写回退改「**助手从暂存副本运行**」落码 + 真机端到端 applied |

## 二、第 1 项：代理可达性（证据）

| 步骤 | 结果 |
|---|---|
| `session.resolveProxy('https://api.github.com')` | `PROXY 127.0.0.1:5858`（系统代理被 Chromium 网络栈读到） |
| `net.fetch` 拉 releases 列表（生产解析函数） | 200，`v1.0.0-rc.4`，资产 `CLWriting-1.0.0-rc.4-x64.zip`（154258432 B，API `digest` = `51fd8c84…0794`） |
| `net.fetch` 拉 `SHA256SUMS.txt`（302 跳） | 200；302 跳转落点 `release-assets.githubusercontent.com`；解析值与 API `digest` 一致 |
| `net.fetch` 全量下载（生产 `downloadUpdateZip`） | 12.9 s / 154258432 B / 进度回调 63 tick；下载后 sha256 = `51fd8c84…0794`，与期望一致 |
| 全局 fetch（内置）拉 releases 列表 | 可达（332 ms）——但该通道为**直连**（不读系统代理）；直连在本机时通时挂，故出站通道按 `net.fetch` 落（切换点 = `update-controller.ts` 单处 `netFetch` 适配） |

## 三、第 2 项：杀软行为（火绒）

- 环境：火绒（`HipsDaemon` 进程在跑，实时防护开）与系统代理同时在场；全链均在火绒在跑下执行，未做任何放行/加白。
- 最小原型（纯 Node：等 pid 退出 → `rename` 目录交换 → `rename` 回、再拉起新 exe）：通过，无拦截。
- 真助手端到端（Electron 全链：等待退出 → sha256 复核 → 解压 154 MB 真包（含 `resources/app.asar`）→ 目录交换 → 拉起新版）：**applied/ok**，无拦截；结果条与日志齐全。
- 观察面：暂存副本形态下，每次更新会在 `<home>/更新缓存/<版本>/helper` 新写一棵完整应用目录（含 246 MB exe），属杀软实时扫描的高频对象——本机未见拦截（复制耗时正常量级），未单独计量扫描时延。
- 局限：单机单杀软（火绒）结论；其余国产杀软与「拦截后能否放行」的交互未覆盖，失败兜底仍按「失败回滚 + 结果条留痕」设计。

## 四、第 3 项：多实例存活与目录改名

- 实例存活（进程与目标目录同一位置）时对目标目录 `rename` → `EPERM`；退避重试 3 次（50/100/200 ms）仍不让；**杀掉实例后立即成功**——「换目录必须等旧实例死透」的设计前提成立。
- 运行中的 exe **文件**本身可改名（镜像锁 ≠ 文件名锁）；目录改名被挡的是目录层面的占用（见下节第 4 项的新发现）。
- `queryLockHeld` 判定三态实测与实现逐条一致（直调生产函数）：500 ms 内新空锁 = 持（防启动窗误清）；过龄空锁 = 不持；死 pid 残留 = 不持。锁扫描 × `<home>/instances/*/app-instance.lock` 的多实例预检判定可靠。

## 五、第 4 项：助手自改目录（核心发现）

**四连对照（外部进程对目标目录 `rename`，目标目录同一、运行形态不同）**：

| 运行时 | 镜像位置 | 目标目录改名 |
|---|---|---|
| 无进程运行 | — | OK |
| **Electron exe（本产品 exe）** | **目标目录内** | **FAIL EPERM**（进程杀掉后立即 OK） |
| 真 `node.exe`（复制进目标） | 目标目录内 | OK |
| Electron exe（复制到目标外） | 目标外 | OK |

- 附加观察一：EPERM 期间对目标目录**逐条目**改名（含运行中的 `CLWriting.exe` 与 `resources/` 全树）**全部成功**——被占住的不是某个文件，而是**目录本身**；具体句柄未定位（Electron 启动链自身行为或安全软件对该 exe 进程的处置，二者未分离——真 `node.exe` 同形态不挡，且无与火绒直接关联的证据）。
- 附加观察二：真助手原形态端到端（`app3\CLWriting.exe --apply-update`，目标 = `app3`）→ 解压成功、等待成功、**`rename app3 → app3.old-1.0.0-rc.4` 必败 EPERM**，结局 `aborted（target-locked）`，安全收口（旧目录未动、半成品清理、旧应用照常拉起）。
- 附加观察三：回退形态端到端（助手 exe 与资源整棵复制到目标外 `el4` 再跑，其余 argv/流程一字不改）→ **applied（ok）**：结果条落 `{"outcome":"applied","reason":"ok"}`；`app3.old-1.0.0-rc.4` 在位；换入内容 = 包体（`app.asar` 4705763 B = 包内件，异于源构建 5292301 B）；新版从换入目录被拉起（5 进程树）。cwd 在目标内（真双击形态）叠加验证同样 applied（助手起手 chdir 兜底，见「途中缺陷」C）。
- 结论：**原设计形态（助手 = 目标目录内的主 exe）在本平台不可行**；按设计档 §七.4 / 执行档 §二.4 预写回退落地——**助手一律从 `<home>/更新缓存/<版本>/helper` 的整棵暂存副本运行**（交换序与 argv 契约不变；`--target` 仍指真应用目录）。「应用运行中整棵复制」已实测（源目录有活进程时复制成功、字节数一致；本机 ~0.2 s / NVMe，杀软扫描时延未计入）。

## 六、途中修出的产品缺陷（随本批修，各带红锚）

- **A. 助手解压写 `resources/app.asar` 必败**：Electron 的 asar 层把「写向 `*.asar`」当包体解析，`open` 即抛 `Invalid package`（打包态更新链必败）→ 助手分支置 `process.noAsar = true`（锚 = `update-helper-entry.test.ts` 的 `noAsarAtRun`）。
- **B. 启动清扫删含 asar 叶的目录必 EPERM**：`rmSync` 递归遇 `app.asar` 拒删（lstat 呈目录）→ `rmDirQuietly` 增「摘叶重试」（`resources/*.asar` 先改名为 `*.rm-<pid>` 再删；锚 = `update-controller.test.ts` 「asar 叶容忍」）。
- **C. 助手继承旧应用 cwd 在目标内时目录改名 EBUSY**：双击/快捷方式启动的旧应用 cwd = 应用目录，助手经 spawn 继承之 → 助手起手 `process.chdir(dirname(targetDir))`（上级 = 换名产物落点；锚 = 同 A 档的 `cwdAtRun`）。
- **D. 助手结局行与错误行随 `process.exit` 丢**：日志泵为异步写，退出前不等则「更新助手结局：aborted（…）」与解压错误行全部丢失（无控制台的助手只剩残缺证据，本批诊断一度因此失明）→ 新增生产 API `flushLogs()`，助手退出前等待（上限 2 s 防挂盘钉住退出；锚 = `log-backpressure.test.ts` 挂盘闸用例 + 入口档 flush 计数）。
- **E. 两处 win 平台默认测试失败**（存量，非本批引入）：`update-controller` / `update-ipc` 各一条「非 win/打包态」用例隐含「宿主平台 ≠ win」假设，在本机 beforeEach 下必红 → 用例显式置平台（`setPlatform('darwin')` / 描述符改写）。
- 观察留档：Windows 中文控制台下 JSONL 日志经 GBK 渲染显示乱码属终端呈现问题（文件为 UTF-8，内容完好）。

## 七、遗留

- 第 2 项单杀软、第 4 项机制未定位到具体句柄——两者都可能在更多机器上复现边缘差异（如杀软拦「新建一棵完整应用目录」）；批 D 真机验收按设计档 §八 口径继续观察。
- 暂存副本的退出链复制时延与磁盘占用（约 600 MB，随版本缓存清扫）为本形态固有代价；如需优化（后台预拷、仅拷 exe + run-as-node 独立脚本），另立批。

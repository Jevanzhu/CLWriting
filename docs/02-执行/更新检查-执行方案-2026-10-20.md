# 更新检查改造 · 执行方案（2026-10-20）

- 定位：**交接用施工方案**——更新链的自动检查节奏与手动「检查更新」入口，逐条给靶点、改法、参数与验收判据，接手者无需回溯讨论即可动工。
- 起因：发 1.0.1 时发现应用侧没有任何手动检查入口，且自动检查在进程内只跑一次——开着应用不重启的用户永远不知道有新版本。取证见本档 §一。
- 拍板状态：作者已拍板方向（周期 6 小时、不加用户可关的自动检查开关、不引入 `powerMonitor`、按钮落在「设置·关于」的更新区）。
- 状态（2026-10-20）：批一（主进程调度 + 契约 + 可观察面）与批二（前端按钮 + 状态行）均待开工。

## 一、现状取证

- 自动检查只在启动后 5 秒跑一次：`src/desktop/update-controller.ts:517` 的 `scheduleCheck` 以 `scheduled` 闸保证「本 app 生命周期只排一次」，缺省延时 `UPDATE_CHECK_DELAY_MS = 5000`（`src/update/check.ts:46`）。之后进程内没有任何再次出站的路径。
- 前端三次轮询不触发检查：`src/studio/web-next/src/stores/update.ts:29` 的 `POLL_DELAYS_MS = [6000, 12000, 24000]` 只是读 `/api/app-info` 端点，用于覆盖起服竞态。
- 无手动入口：`src/desktop/preload.ts` 暴露的更新面只有 `updateCapability` / `updateDownload` / `updateCancel` / `updateApply` / `updateReveal` 与两个订阅；`UpdateCheckHost` 只暴露 `scheduleCheck` 与 `pushLastResult`。
- 状态不可观察：`getUpdateCheckState()` 只有 `'idle' | 'done'`，无时间戳、无失败信息；`/api/app-info` 响应只带 `version` / `update` / `updateAttempt`。
- 检查必须走主进程：`src/update/check.ts:17` 注明子进程不自行出站——child 的全局 `fetch` 走 Node 网络栈、不读系统代理，只配系统代理的用户会恒失败且静默。链路是主进程跑检查 → `parentPort` 下发 `UPDATE_RESULT_MESSAGE_TYPE` → `src/desktop/server-utility.ts:159` 落 child 模块态 → 端点读取。手动检查必须复用这条链路。

## 二、自动检查设计

核心手法是 60 秒轻 tick 加时间比较，不用长定时器：`setInterval(tick, 60_000).unref()`，tick 内只在 `now - lastCheckAt >= 间隔` 且无在飞检查时出站。三处收益：系统休眠时 Node 定时器不走，醒来后首个 tick 即判定超时并补跑（长定时器要再等一个周期）；省掉 `powerMonitor` 这一新 Electron API 面（仓内零先例）；启动、周期、唤醒三类触发天然合并到同一判定，不重复出站。

参数与理由：

| 参数 | 取值 | 理由 |
| --- | --- | --- |
| 启动延迟 | 5000ms（沿用） | 不拖慢启动，覆盖冷启动 |
| 检查周期 | 6 小时 | GitHub 未认证 API 限流 60 请求/小时/IP，6 小时一天至多 4 次；独立软件发版频率远低于此 |
| 自动最小间隔 | 5 分钟 | 防多触发源叠加与频繁重启抖动 |
| 手动最小间隔 | 30 秒 | 防连点打爆 API；窗口内点击给回执而非静默 |
| 单次超时 | 沿用 `UPDATE_CHECK_TIMEOUT_MS` | — |
| 失败退避 | 30m → 1h → 2h → 4h → 8h → 16h → 24h 封顶，成功即重置 | 断网或被墙时不按 6 小时死磕，恢复后回归正常周期 |

## 三、可观察面

`getUpdateCheckState()` 由 `'idle' | 'done'` 扩为 `'idle' | 'checking' | 'done'`；新增 `getUpdateCheckMeta(): { checkedAt: number | null; lastError: string | null; failures: number }`。`/api/app-info` 响应**只加不改**地补一个 `updateCheck` 字段（老前端不受影响）：`{ state, checkedAt, lastError }`。

## 四、手动入口

位置在 `src/studio/web-next/src/components/ui/UpdateActions.vue`——该件由「设置·关于」页（`SettingsAbout.vue:24`）与顶栏角标弹层（`UpdateCorner.vue:186`）共用，改一处两处同得，符合该文件开头的防漂移口径。按钮置于按钮组首位且不依赖 `primaryAction`，保证无更新时「关于」页也有可点的检查入口。

链路（不可抄近路）：点按钮 → `stores/update.checkNow()` → `window.clwritingDesktop.updateCheck()` → `ipcRenderer.invoke('desktop:update-check')` → 主进程 `updateCheckHost.checkNow()` → `runUpdateCheckOnce({ fetchImpl: netFetch })`（系统代理在此生效）→ `pushLastResult()` → child 落态 → 前端 `fetchInfo()` 重读端点。

反馈四态：空闲时按钮「检查更新」、状态行显示上次检查时间；点击后按钮「检查中…」并禁用；结束后按结果分「已是最新」「发现新版本（主按钮转下载）」「检查失败（附退避后的重试时间）」；30 秒窗口内连点回「刚刚检查过，请稍后再试」。

## 六、判据

批一（落 `test/desktop/update-controller.test.ts` 与 `test/update/` 同域档）：

- 启动检查已排程后，`checkNow()` 仍能出站并下发结果——锚住 `scheduled` 闸不得被手动路径复用，是本批最关键一条。
- 假时钟推进 6 小时触发第二次检查；推进 5 分钟触发 0 次。
- 连续失败三次后间隔按退避增长；一次成功即重置。
- 30 秒内重复 `checkNow()` 回「刚刚检查过」且不出站。

批二（按域并入 web-next 既有档）：

- `/api/app-info` 响应含 `updateCheck.checkedAt`。
- `checkNow()` 后状态行由「检查更新」转「检查中…」并最终出结果。

## 七、明确不做

- 不加「自动检查更新」用户开关：现只有 env `CLW_DISABLE_UPDATE_CHECK`；加开关牵动设置项、持久化与默认值之争，另案。
- 不落盘 `lastCheckAt`：启动即检查是期望行为，频繁重启的抖动由进程内 5 分钟最小间隔兜住，不值得为此引入 userData 文件与清理。
- 不做后台静默下载与自动安装：下载仍由用户点击触发。
- 不引入 `powerMonitor`：60 秒 tick 已覆盖唤醒场景。
- 不做多通道（beta / stable）。

## 八、风险

- 60 秒常驻 tick：`unref()` 且每 tick 只做一次数字比较，开销可忽略。
- 多实例重复出站：主进程有单实例锁，另有在飞闸兜底。
- API 限流：6 小时周期加退避，最坏情形每天 4 次。
- 手动与自动并发：在飞闸统一拦截，检查中再点回「检查中」。
- 节奏分两批：批一只动主进程与契约，能独立跑通并回退；批二动前端，回退不影响调度逻辑。

## 九、版本策略

功能进 1.0.2。装 1.0.1 的用户拿不到按钮，唯一发现路径仍是重启应用（重启时自动检查会看到 1.0.2）——链路不断，只是慢一版。

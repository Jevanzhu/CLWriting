## 一、背景与目标

项目目前按 2026-06-30「仅 mac」决策打包（electron-builder.yml win/linux 块注释暂缓），但代码层已做了大量无意识的跨平台铺垫。目标 = 把「仅 mac」扩为「mac + win（x64 先行）」：Win 10/11 用户可装可跑可用中文书库，核心链路（建书/写章/机检/定稿/导出/索引/对话助手）行为与 mac 一致；不追求 UI 像素级一致。

不做（本轮边界）：Linux 适配；Windows ARM64 架构；自动化 UI 行为差异对齐。

## 六、风险与已知坑

- **rename EPERM/EBUSY**：Windows 独占打开/杀软扫描——批 5 加重试，勿视为环境玄学（保存链路可复现）。
- **\\?\ 长路径前缀**：Node 自动产生，但传给 Explorer/部分 Electron API 可能失败——showItemInFolder 冒烟必须覆盖。
- **用户文件名历史存量**：不做存量清洗（数据孤儿风险），仅新写入消毒——文档明示，避免误以为全量合规。
- **vitest chmod 用例**：不 skip 而是修语义会失去 mac/Linux 上真实 EACCES 覆盖——正确姿势是 skipIf(win) 而非改断言。
- **PowerShell 首次冷启动**：字体枚举首调秒级——缓存后一次。
- **同步盘三重干扰（2026-08-23 补，Windows 用户高发）**：书库放 OneDrive/坚果云等同步目录时，**三套锁文件**（`<journal>.lock` / `ai-calls.json.lock` / `.clwriting/task-gate/*.lock`）+ node:sqlite WAL 文件都会被云端同步进程独占打开/延迟上传——恰好构成批 5 防的 rename EPERM 同款冲突源，且同步乱序可致锁文件/WAL 副本不一致。对策：README 前置写明「书库勿放同步盘目录」（批 5 已有该句，本条补齐原因表述与风险面清单）；长期可考虑启动时探测 userData/书库是否在 OneDrive 路径下并弹提示（列批 5 可选）。
- **回滚口径（2026-08-23 补）**：J0-J4 全部为配置/脚本/测试门改动，回滚 = revert 对应提交（utilityProcess 方案回滚验证同款纪律）；J2 消毒收敛如有意外行为回退单个调用点即可（各点保留原函数形态只换内部实现）；无数据迁移、无不可逆操作（「不做存量清洗」原则的另一面）。

### 3.1 P1（×1）

**R44-2 | P1 | [跨平台] flushSyncOnUnload 同步 XHR 被 Chromium page-dismissal 策略整体拦截——关窗/刷新时最近一段编辑静默丢失（双实验实证）**

- 证据：`src/studio/web-next/src/stores/doc.ts:499-542`（flushSyncOnUnload：beforeunload 内对每个 dirty 文档同步 XHR `xhr.open(PUT,…,false)+send()`）；`doc.ts:61-71`（bootTokenSync 同步 GET 同阻断面）；`src/studio/web-next/src/pages/Book.vue:258-263`（beforeunload 注册点）；`test/studio/webnext/f3-unload-sync-reboot.test.ts:47`（`vi.stubGlobal('XMLHttpRequest', FakeXHR)`——测试面 stub 掉 XHR，对真实引擎行为结构性失明）。
- 实证：①E 域子代理实验（仓库自带 `node_modules/electron/dist/electron.exe` + same-origin HTTP + `win.close()`）：dismissal 外同步 GET 返回 200 正常；beforeunload 内同步 PUT `send()` 同步抛 `NetworkError`，**服务端从未收到 PUT**；②主审独立复证（自建最小 electron 实验，同二进制同源形态）：请求日志仅 `GET /page` + `GET /api/sanity`，**零 PUT**。Chromium 自 M80 起在页面卸载路径禁同步 XHR，无版本开关。
- 场景与影响：最后一次成功保存（手动 ⌘S 或 autosave，默认间隔 30s、可设 5–120s，`Book.vue:281-291`）之后的键入，在点窗口 X 关闭或 Ctrl+R 刷新时**静默丢失**——无请求、无 toast、无确认。普通 dirty 关窗路径本就无任何 UI 提示，全靠这条同步兜底；兜底失效后「编辑永不静默丢失」底线在关窗/刷新场景整体破防，最坏窗口 = 一个完整 autosave 间隔的连续输入。`.版本` 快照只覆盖已保存状态，救不了未落盘键入。代码注释自认的「token 缺失时编辑由 .版本 快照兜底」对未保存键入同样不成立。
- 关联记档：R42 收口「维持 5」中的挂账项「**同步 XHR 实机**」本轮实机收口，结论为**负面**（兜底在生产引擎下一个字节都发不出）——挂账项转正立项。
- 建议：方案一（推荐，自有壳可控度最高）：桌面主进程 `mainWindow.on('close')` 中 `preventDefault()` + IPC 通知渲染层**异步** flush、完成（或短超时）后再真正 `destroy()`；方案二：渲染层改 `fetch(…, { keepalive: true })`（Chromium 明确允许在 dismissal 存活，注意 64KB body 上限——超大章需截断或降级路径）。修复后补一个**不 stub XHR** 的 Electron 实机回归测试堵住 f3 的结构性盲区。

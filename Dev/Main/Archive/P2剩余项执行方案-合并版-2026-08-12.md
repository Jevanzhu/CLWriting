## 2. SSE event as 断言提取（1h）

**文件**：
- `src/studio/web-next/src/stores/workbench.ts`（9 处 `as`）
- `src/studio/web-next/src/stores/chat.ts`（1 处 `as`）

**问题**：SSE event 经 `JSON.parse` 后用 `as Record<string, unknown>` 断言取字段，无运行时校验。后端事件结构变化时前端静默失败。

**方案**：提取 type guard 函数到 `stores/sse-guards.ts`：

```typescript
// stores/sse-guards.ts

/** SSE event 基础守卫：是对象且含 type 字符串 */
function isSseEvent(ev: unknown): ev is { type: string; [k: string]: unknown } {
  if (typeof ev !== 'object' || ev === null) return false
  const e = ev as Record<string, unknown>
  return typeof e.type === 'string'
}

/** self_heal_phase 事件守卫 */
export function isHealPhaseEvent(ev: unknown): ev is {
  type: 'self_heal_phase'; phase: string; attempt?: number
} {
  if (!isSseEvent(ev)) return false
  return ev.type === 'self_heal_phase' && typeof ev.phase === 'string'
}

// ... 其余事件类型按需添加
```

**改动范围**：新增 1 文件 + workbench.ts dispatch 内替换 + chat.ts 替换。

**验证**：`workbench-selfheal.test.ts` + `composables-low.test.ts` 回归。

## 3. batch_size 自动连写编排（4h+）

**文件**：
- `src/studio/server/api/stream.ts` — auto-write 端点
- `src/ai/orchestrate/self-heal.ts` — 自愈闭环
- `src/studio/web-next/src/views/WorkbenchView.vue` — 进度展示

**现状**：
- `batch_size` 配置可存（SettingsAi UI + book.yaml）
- auto-write 端点接受单章 `{ chapter }`，处理一章即返回
- SettingsAi 已标注「即将支持」（P1-PROD-1 修复中加的 `.tag-soon`）
- 无多章循环编排

**方案（后端编排）**：

```
POST /auto-write { chapter, batchSize? }
  batchSize 默认 1（单章，向后兼容）
  batchSize > 1 → self-heal 循环：
    第一章 pass → 自动推进 chapter+1 → ... → 全部完成或中途 escalate
    SSE 回流每章进度（self_heal_phase 附 chapter 字段）
    中途 escalate 则停止，保留已完成章节
```

**改动清单**：

| 文件 | 改动 |
|------|------|
| `self-heal.ts` | `runSelfHeal` 支持 `{ chapters: number[] }`，循环调 `orchestrate`；每章完成 emit `self_heal_phase { phase: 'chapter_done', chapter }` |
| `stream.ts` | auto-write 端点解析 `batchSize`，展开为 `chapters` 数组传入 `runSelfHeal` |
| SSE 事件 | `self_heal_phase` 加 `chapter` 字段；新增 `self_heal_batch_progress { done, total }` |
| `WorkbenchView.vue` | 展示连写进度（「正在写第 3/5 章」） |
| `SettingsAi.vue` | 移除 batch_size 的「即将支持」标签 |
| `api/stream.ts`(前端) | `autoWrite` 参数加 `batchSize?` |

**验证**：
- 单测：`self-heal.test.ts` 加多章场景（2 章连写 + 中途 escalate）
- e2e：`auto-write.spec.ts` 加 batchSize=2 场景
- 手测：真 provider 跑 3 章连写

## 4. RelationsView / StyleView 拆分（4h+）

> ⚠️ 高风险——纯代码组织优化，不改变用户可见行为。
> 建议：随功能迭代自然拆，不专门开 batch。

**当前行数**：RelationsView 1322 行 / StyleView 1284 行

### RelationsView 方案

```
RelationsView.vue（~300 行 编排）
  ├── RelationGraph.vue（~400 行 SVG 力导向图渲染）
  ├── RelationForm.vue（~300 行 编辑表单）
  ├── RelationList.vue（~200 行 侧边列表）
  └── useRelationGraph.ts（~200 行 composable：节点/边状态 + 力学计算）
```

**拆分边界**：
- `useRelationGraph.ts`：节点/边数据结构 + 径向布局算法 + 拖拽状态
- `RelationGraph.vue`：SVG 渲染（`<g>` 节点 + `<path>` 边 + 缩放/平移）
- `RelationForm.vue`：角色/世界观/伏笔的关系编辑表单
- `RelationList.vue`：侧边列表（搜索 + 筛选 + 点击定位）
- `RelationsView.vue`：编排（props 传递 + 事件路由 + AI 梳理触发）

**风险点**：SVG 力导向图的拖拽状态（`dragNode.x/y`）从组件内 ref 迁移到 composable 后，需确保响应式不丢帧。

### StyleView 方案

```
StyleView.vue（~300 行 编排）
  ├── StyleEntryPanel.vue（~350 行 条目库 CRUD）
  ├── StyleCandidateBox.vue（~300 行 候选确认/忽略）
  ├── StyleSamplePanel.vue（~200 行 样章库管理）
  └── StyleBaselineCard.vue（~150 行 基线查看/冻结）
```

**拆分边界**：四段式各独立，通过 `style.load()` 共享数据。
**风险点**：候选确认 → 条目库刷新的联动需通过 emit 或 store 正确传递。

**验证**：vue-tsc 无错 + 全部 e2e 绿 + 手测各面板交互。

## 5. Shelf / ShelfModal 去重（2h）

**当前行数**：Shelf.vue 1037 行 / ShelfModal.vue 957 行

**问题**：两者模板 80% 相同（书卡网格 + 右键菜单 + 新建流程 + 搜索/排序），仅宿主容器不同。

**方案**：提取 `<ShelfGrid />` 共享组件：

```
ShelfGrid.vue（~700 行：书卡网格 + 右键 + 新建 + 搜索/排序）
  props: { mode: 'page' | 'modal' }
Shelf.vue（~200 行：页面壳 + 路由）
ShelfModal.vue（~200 行：弹窗壳 + Teleport）
```

**风险点**：`useShelf` composable 已提取逻辑共享；剩余模板重复在书卡渲染 + 右键菜单 + 搜索/排序 UI。提取时注意 `onCreated` 回调在 page vs modal 模式下的行为差异（路由跳转 vs 关弹窗）。

**验证**：`shelf.spec.ts` + `shelf-search.spec.ts` e2e 全绿 + 手测书架/弹窗两入口。

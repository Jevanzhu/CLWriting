## 一、对既有排期的一个调整建议

### 建议 1：B1「机检误报按钮」考虑提前插队

方向 B（语料回归库）在执行方案里排位靠后，但它依赖真实使用产生的误报数据——**越早上线，数据积累越早开始**。B1 本身工作量不大，建议在批 0/批 1（A4 日志 / A1 树红点）之后评估插队，让 B2（存量书自举）开工时已有线上数据可汇合。

## 二、发布面

### 建议 2：先做一次「可发布性确认」

迭代方向方案明确排除了 RC 收尾项，但发版前它们是硬门槛。建议动 A1 之前花半天确认账实相符：README 计数同步、e2e 冒烟全绿、7 提交已推送（kk 轮已推送见 CI 绿，核对即可）。不是修，是确认。

### 建议 3：boot token 发放面需要真修复而非文档披露

`GET /api/boot` 本机任何进程可取 token（ee-P2-12 遗留，README 已明示）。若产品将分发给其他用户，应排正式修复，不能止步于「网页拿不到」一层防线的文档说明。

## 三、工程健康

### 建议 4：性能回归门（本次讨论最想推的一条）

方向 A 揭示的真正风险是**请求路径上的同步文件 IO**（RAG 每次召回全书 SHA-256 指纹校验 `src/rag/index.ts:129-145`、detectState 全同步 walk）。这类问题单测测不出、只有长篇+慢盘才暴露。建议在 CI 加一个性能回归门——哪怕只是 500 章合成书的 tree-issues 耗时断言——守住「两百万字不崩」的承诺。与 A1/A2 完成的时机正交，但越晚加越难还原基线。

### 建议 5：债务编号体系落索引

kk-P2-14、ee-P2-12 这类编号信息量大但只活在 git log 里，换会话/换 agent 即断传承。建议在总览决策状态表落一份「编号 → 报告条目」索引，随评审轮次维护。

## 四、流程面（docs/ 事件的根因）

### 建议 6：文档操作加一道确认闸

2026-08-20 02:16 的提交 `7c88e2e` 绕过文档链把三份文档复制进项目根 `docs/`（正本已在 `Dev/Main/` 收编；kk 轮 S7 台账已记「建议删」）。根因是长会话尾部 agent「顺手整理」。建议在 `CLAUDE.md` 文档操作链加一行硬规则：**新增/移动任何 `.md` 必须先报路径给作者确认**。一行字，防重演。

## 五、数据与产品面

### 建议 7：「一键导出完整书稿」一等公民入口

恢复机制（journal / git 后端 / manifest / cloud copy）做得细，但用户感知的安全感来自显式导出入口。哪怕只是把现有机制包一个导出按钮，对信任感的贡献可能超过方向 A 的全部优化。写作软件，稿子就是用户的命。

### 建议 8：知识层更新入口随 B 立项一起设计

`知识层/` 是给模型读的散文速查，目前只有 manifest 无演化机制。方向 B 语料回归会产生大量「机检误报规律」，其天然归宿是知识层——建议 B 立项时把更新入口一并设计，避免经验又只活在 git log 里。

### 建议 9：新书冷启动体验

四方向全为作者端服务，没有一个回答「用户第一天」：空书冷启动、无语料时机检与 RAG 的表现。B2 解决老书自举，新书第一印象可能更值得看一眼。

### 建议 10：仓库卫生小项

`test-results/`、`coverage/` 在仓库根目录，确认 `.gitignore` 覆盖；Electron 打包路径建议做一次「干净机器安装 → 打开 → 写一章 → 重启」全程演练（知识层/种子词表等非代码资产是 Electron 项目经典翻车点）。

## 一、背景与目标

### 1.1 要借鉴的 DSH 模式（先定性，非抄代码）

DSH 模型设置页（`ModelsSection` / `ProviderEditor`）的交互本质是：

1. **列表即卡片**：每个提供方一行折叠卡片（`rowCard`），行头 = 名称 + 标记（自定义标签）+ 凭据状态点（绿=已配置 / 红=缺失）+ 行尾操作（编辑 / 删除）。
2. **单张就地展开**：`editing` 只存**一个** target；`open = !adding && editing.provider === row.provider`；点「编辑」`setEditing(open ? undefined : target)` 切换；渲染 `open ? <ProviderEditor/> : null`。**不切视图、不弹全屏**，编辑器嵌在该行下方。
3. 编辑器分层：**主字段 = 单个 API 密钥输入**（`type=password`，placeholder 按凭据状态分级）；「自定义设置」收进折叠 `<details>`（baseURL / 显示名 / 协议 / 模型列表）；模型列表每行又有自己的展开区（contextWindow / maxTokens）。
4. **新增即卡**：新增卡内嵌「未配置的目录提供方」下拉选择 → 就地起新卡编辑器；另有 CustomProviderCard 手工声明路由。
5. 并发安全：每次写带 `expectedRevision`，外部改动 → `settings-conflict` 拒绝；成功后用响应返回的脱敏子树 + revision 回填，再做凭据写入。

> 注：DSH 是 React 编译产物，我们只移植交互/状态模型与分层思想，不照搬代码。

### 1.2 CLWriting 现状（核对后）

| 维度 | 现状 | 差距 |
|---|---|---|
| 编辑交互 | 「编辑/新增」→ `v-if="!editing"` **整页切走**到独立表单（`AiServicePanel.vue`） | 无行内就地展开 |
| 展开控制 | 布尔 `editing` + `editId`，切视图 | 无「单 target 互斥展开」 |
| 组件体积 | `AiServicePanel.vue` **1297 行**（评审 P2-16） | 需拆分 |
| 密钥存储 | **已走 Vault**（`src/ai/provider/store.ts`：`saveProviders` 每次重建 `vault.keys = sealKey(...)`，磁盘 `providers.json` 不含明文；删除自动清密文；残留明文按半迁移规则收拢） | 与 DSH「密钥只写不读回」**基本对齐**，无需从零迁移（见 §五 P3 核查） |

### 1.3 目标形态

把 `AiServicePanel.vue`（「服务提供方」tab）重构为：

- **组件拆分**（顺带清偿 P2-16）：AI 列表 / RAG 列表 / 编辑器 / 模型编辑器 / 档位 各自独立组件，AI 与 RAG 共用「行卡骨架」。

- **可选并发加固**：`revision` 冲突检测（P4）。

## 四、交互 / 状态设计（核心：单卡展开）

```ts
// ProviderList.vue 内（AI 与 RAG 各自持有，P2 拍板）
const editing = ref<{ id: string; kind: 'ai' | 'rag' } | null>(null)
const adding = ref<Target | null>(null)   // 新增卡与编辑互斥

// 每行
const open = adding === null && editing?.id === row.id
// 点「编辑」：setEditing(open ? null : { id: row.id, kind })
// 渲染：open ? <ProviderEditor :key="row.id" /> : null
```

- **互斥**：`editing` 为单值，任何一行展开即收起其它行（P1：`v-if` 卸载，草稿不跨展开保留）。
- **分层**：编辑器状态（draft / keyDraft / 校验）留在 `ProviderEditor` 组件内部 `ref`，`editing` 只控制「哪张展开」。
- **新增**：`adding` 单值互斥；新增卡 = 内嵌空白编辑器就地起新卡（对齐现状「添加」入口）。DSH 的「未配置目录提供方下拉」在本项目无数据源——CLWriting 无 installed catalog，不引入（见 §十）。

## 五、P3 核查：Vault 现状（照搬 dsh 的落点）

经源码核查，**CLWriting 的提供方密钥已经走 Vault 信封加密**，与 DSH「密钥只写不读回」模式基本对齐：

- `src/ai/provider/vault.ts`：HKDF-SHA256 → KEK → DEK → AES-256-GCM 信封；`Vault.keys[id]` 以 provider id 为键存密文。
- `src/ai/provider/store.ts`：
  - 磁盘结构 `providers 不含 apiKey，密文统一在 vault.keys`（`:83-92`）；
  - `saveProviders` 每次以 providers + ragProviders 重建 `vault.keys`，删除的 provider 自动清密文（`:251-282`）；
  - 残留明文 apiKey 字段按半迁移规则收拢，无 vault 时的存量明文全量首次迁移（`:195-209`）；
  - AI 与 RAG **同走 vault**。
- `src/ai/provider/redact.ts` / `maskProvider`：API 回传遮蔽，回收站安全。

**本方案对 P3 的处理**：不新增迁移工程；仅在卡片化实现时**收尾核验**——
1. `providers.json` 落盘后再确认无明文残留（半迁移标记是否已随现状收敛）；
2. UI 凭据状态点（绿/红）用 vault 存在性推导，不再依赖 `apiKeyMasked` 猜测；
3. 确认编辑时"留空 = 保留原 Key"走的是解密后内存值（现状已如此，保持）。

> 结论写进方案的目的是**不重复建设**：P3「照搬 dsh」的实际形态 = 确认 + 收尾，而非重写存储层。

## 六、数据流 / 并发 / 校验（P4、P6）

### 6.1 并发 revision（P4）

- **后端**：`GET /api/providers` 返回 `revision`——**递增计数落盘**（providers.json 顶层 `revision` 字段，store.ts 每次 saveProviders 写前 +1；存量文件无该键视为 0，外部手编文件同理不炸）。`POST/PUT /api/providers` 与 `PUT /api/tiers*` 接收 `expectedRevision`，不匹配 → 409 `{ error: '配置已在其他窗口被修改，请刷新' }`，更新后才刷新 revision。
- **前端**：`getProviders()` 缓存 revision 到统一 store，所有写请求携带；409 时提示刷新（复用 `ui.toast` / `friendlyError`）。
- 目的：封掉双窗口 / 多来源（评审 P2-17「providers 三源无统一状态」）的覆盖竞态。

### 6.2 API Key 校验（P6）

- 前置于 save：trim 后必须为可打印 ASCII（`[\x21-\x7E]`，同 HTTP 头值域）；拒绝与 `NAME=value` 环境变量整行粘贴匹配、或首尾成对引号包裹的值。
- 只读留空（编辑 = 保留原 Key）不算失败；纯空白输入判失败。
- 服务端既有 trim + 必填校验保留，作为第二道防线。

### 6.3 统一 store（承接 P2-17，列第二步）

- 目标：AI/RAG 列表 + 档位 + 对话档位收敛到一个 Pinia/模块级状态（`provider.ts`），消灭 `AiServicePanel` 本地 ref / `useChatTier` / WorkbenchView 三处独立拉取。
- 本方案将 store 统一列为**第二步（卡片化阶段）**的一部分；第一步纯拆分暂不动数据来源，保证回归面最小。

**删除**：保留现有 `ui.ask` 确认（已点名提供方），改为卡内 danger 按钮（对齐 DSH），服务端原有"删除自动清 vault 密文"行为不变。

### 7.1 模型行字段清单（P7 已拍板：对齐 DSH 四字段）

| 字段 | 必填 | 输入形态 | 空值语义 | 校验 |
|---|---|---|---|---|
| `id` | 是 | 文本 | —（必填） | trim 后非空 + 提供方内唯一；按行号点名报错（如「模型 2：id 必填 / 重复」） |
| `name` | 否 | 文本 | 不落键（选择器回落显示 id） | 空串视为未设 |
| `contextWindow` | 否 | K/M 后缀文本（`256K`→256000） | 不落键 = 回落（§7.2） | 正整数；不可解析文本保留在输入框、保存时按行号拒绝 |
| `maxTokens` | 否 | K/M 后缀文本 | 不落键 = 回落（§7.2） | 同上 |

- 行结构**保持开放**（DSH 教训）：编辑一行只 patch 已知字段，未知/未来字段原样存活，不整行重建。
- K/M 解析与回显一套纯函数（DSH `DeepSeekModelsEditor.tsx` 同款语义：`1M`=1000000、整千短写回显、不可解析文本不即时抹掉——保存时点名拒绝）。

### 7.2 显式 resolve 链（CLAUDE.md AI 链路守则）

每层显式 resolve、不允许隐式默认穿透；**解析结果落 trace / llm call 事件**，保证重放可精确重建：

```
maxTokens     = model.maxTokens ?? quirks(model).maxOutputTokens ?? 协议兜底（anthropic 线 MAX_TOKENS；openai 线不发）
contextWindow = model.contextWindow ?? undefined → chat checkpoint 预算 clampCheckpointOutputTokens(contextWindow)
```

- 现状基线：anthropic 适配器已是 `req.maxTokens ?? q.maxOutputTokens ?? MAX_TOKENS`（`anthropic-adapter.ts:85`）；**unknown 家族无 `maxOutputTokens`**（`model-quirks.ts:313` 起）→ 兜到 128000，注释自点名「P1-5：128000 对旧模型 400」——恰是本字段要治的风险（自定义 Anthropic 网关接小上限模型必炸，用户无路可走）。
- **contextWindow 随批接线**（P8 已拍板）：全仓唯一消费者 `orchestrate/chat.ts:473` 现状**无参调用** `clampCheckpointOutputTokens()` → 恒取上限 16384。接线后预算 = clamp(contextWindow×0.25, 4096, 16384)。死字段防线维持——若实施中接线被裁，字段一并砍。

### 7.3 明确不进模型编辑器的参数

| 参数 | 理由 |
|---|---|
| temperature / top_p / top_k | `types.ts` GenRequest 刻意排除（新模型发则 400），项目级决策不翻案 |
| effort **值** | 档位层所有（`tier.effort` + `quirks.effortMap` 收敛）；DSH 教训：per-model 能力不设在提供方级 |
| `effort` 支持声明（三态：随表 / 不发 / 发） | 真实缺口（unknown 家族恒不发 effort，自定义模型名不命中前缀即无路走），但会撕开 quirks 表的用户可写口子——**二期单独立项**，不混本批 |
| 协议 / 端点 / Key | 提供方级 |
| input 模态（DSH 的 text/image） | 本项目纯文本链路，无图片输入概念 |
| toolUse / structuredMode / maxTokensKey / echoReasoning 等能力位 | 表驱动定论（静态表取代探测已拍板）；structured 已有 400 降级记忆兜底 |

### 7.4 模型清单源接线（本批最大成本项）

档位/对话选择器的清单源从「纯 listModels 拉取缓存」改为「**已配置 models ∪ listModels 候选**」，否则手填模型进不了下拉：

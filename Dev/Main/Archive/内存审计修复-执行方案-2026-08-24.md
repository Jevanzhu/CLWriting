## 一、审计结论摘要（修复依据）

高（峰值主因）：H1 导出链全书内存中转 4~6×（`src/export/index.ts:145-227`）+ 导出 worker 无 `resourceLimits`/跨书无并发闸/测试态每线程挂 tsx（`src/export/run-async.ts:41-53`、`io.ts` task-gate 仅单书）；H2 RAG 建索引 `vectors: number[][]` 全量累积 ≈430MB/200 万字书（`src/rag/index.ts:338-346`）；H3 事件库 `listEvents` 全量投影族——append-only 表 × `stmt.all()` 双份物化 × 投影链再 3~6 份排序副本，调用点 trace-stats/cost-stats/restore/chat-history/audit/chat-branches 全不传 limit/type；H4 scale 测试峰值叠加窗（maxForks 只封并发数不封单 fork 峰值）+ 造书 join O(N²) + embed 桩 number[] 双份。

中（真驻留/高频峰）：M1 `src/process/settings-context.ts:40 cardCache` 无上限模块 Map（含角色卡全文，删卡/换书不失效——全库唯一确认「只 set 不 delete」型）；M2 `src/format/chapters.ts:183 chapterDirCache` 删书/改名不清理（`clearChapterDirCache` 零调用）；M3 前端 chat store `ToolCard.summary` 整章正文无截断常驻（2 万字/卡 × 200 条消息）；M4 SQLite 句柄异常路径泄漏 ×3（`src/check/run.ts:64-73` PRAGMA 抛错绕过 close / `src/cache/rebuild.ts:247-250` ROLLBACK 抛错跳 close / `src/events/store.ts:193-248` openSessionStore DDL/repair 抛错滞留）；M5 restore 后 history 失败出口不 trim（8 书 LRU 兜底内单书可驻留数 MB——**本方案登记维持**，理由：语义属「可恢复的运行态」非泄漏，trim 时机涉对话连续性取舍，留待产品层决策）；M6 桌面 `server-manager.ts:501-510` 子进程 stdout 行缓冲无单行上限 + `src/log/index.ts:160-168` 落盘串行链慢盘无界排队；M7 `health`/`analyze-style` 端点每请求全书扫描无 TTL 缓存。

低（挂账不修，记档理由见 §五末）：前端每击键 5~8 次整章全文复制链（UX 需逐项防抖设计，独立批）、`ngramRepeatRate` 全书误用护栏、spill/estimateTokens `Array.from` 全展开、settings keep-alive 无 max、doc LRU dirty 逃逸通道（依赖后端故障场景）、provider store 删除不同步、foreshadow 每次备料全书重读、若干 10s settle 定时器等。

## 三、批 A：治峰值

### A1 导出链降峰（H1）
- **问题**：`exportBook`（`src/export/index.ts`）全书正文四阶段驻留（units 数组 → purify 拷贝 → `join` 整书大串 → 写盘 Buffer），峰值 4~6× 全书体积；worker（`src/export/run-async.ts`）无 `resourceLimits`；task-gate 仅按书限并发，跨书可同时 N worker。
- **修法**：①导出正文改流式——净化逐章产出后即追加写入临时文件（保留 `atomicWriteFile` 收尾 rename 语义，头/尾元数据单独小串），峰值降为单章级；②worker 加 `resourceLimits: { maxOldGenerationSizeMb: 1024 }`（堆超限 worker 按既有 error 路径收口 422，不炸主进程）；③导出并发闸升级：模块级全局信号量（同时在跑 export worker ≤2），跨书排队——409 语义不变。
- **验收**：既有导出测试全绿 + 新增「跨书第二路导出排队/放行」单测；导出产物字节级不变（golden 对比）。
- **风险**：流式化改动 exportBook 主路径——分小步（先 resourceLimits/并发闸，后流式化），每步跑 test/export 全量；回滚粒度 = 单步。

### A2 RAG 建索引批内写库（H2）
- **问题**：`buildIndex`（`src/rag/index.ts:338-346`）分批 embed 只是分批请求，`vectors: number[][]` 全量驻留至 COMMIT（≈430MB/200 万字书，number[] 8B/维）。
- **修法**：embed 一批写一批——批结果在事务内直接 `storeChunk`（embedding 传 `Float32Array`，`float32ToBuffer` 零改动），不回收累积数组；事务提交语义/失败回滚不变。
- **验收**：`test/rag` 全绿（建库→召回语义不变）；scale 测试耗时无回归（界值仍过）。
- **风险**：低——写库时序从「commit 前统一」变「批内」，同事务内幂等键不变。

### A3 测试编排降峰（H4）
- **修法**：①两个 scale 测试造书循环的 `total = paragraphs.join('\n\n').length`（每追加一段全量 join，O(N²)）改增量 `total += seg.length + 2`；②rag scale embed 桩 `Array.from(pseudoVec(t))`（Float32Array→number[] 双份 2 倍体积）改直接共享 `Float32Array` 入参形态（`EmbedResult` 形态核对后取最小改动）。
- **验收**：两 scale 测试绿、耗时不升；`check:counts` 计数不变（无新增文件）。
- **风险**：桩形态改动需贴合 `embed` 契约——实施期核对 `src/rag/embed.ts` 签名。

## 四、批 B：治投影（H3）

### B1 listEvents 游标化 + 类型下推
- **修法**：①`src/events/store.ts listEvents` 的 `stmt.all()` + `rows.map(rowToEvent)` 改 `stmt.iterate()` 逐行 parse（消「原始 JSON 字符串数组 + 解析对象数组」双份共存，与 readAllChunks 同修法）；②新增 `type` 可选参数（SQL `WHERE type = ?` 下推），`trace-stats`/`cost-stats` 只取 `llm/call`。
- **验收**：`test/events` 全绿 + 新增 type 过波单测（非 llm/call 事件不进聚合）；restore/chat-history 语义不变（仍全量，投影语义需要）。
- **风险**：低；排序仍由 SQL `ORDER BY` 保证。

### B2 branch-tree 投影去重复拷贝
- **问题**：`src/events/branch-tree.ts` `selectBranch`/`selectBranchTo` 各自 `sortEvents` 3 次（每次 `[...events].sort` 复制）+ filter 再一份；`foldSurface` 同构。
- **修法**：`sortEvents` 加「已有序跳过」（投影链输入来自 SQL `ORDER BY seq` 时 O(n) 检测后零拷贝直返）；`selectBranch` 内部排序结果复用（3 次→1 次）。
- **验收**：`test/events`（branch-tree 既有用例）全绿 + 新增「已有序输入不拷贝」行为锁死例（可用副作用计数或直接锁语义）。

### B3 openSessionStore 异常 close（M4 之一，与批 C4 同族提前并档）
- **修法**：`src/events/store.ts:193-248` `new DatabaseSync` 后的 PRAGMA/DDL/repair 阶段抛错路径统一 `try { ... } catch (e) { db.close(); throw e }`。
- **验收**：新增「损坏库打开失败后句柄不滞留」单测（同路径二次打开可成功——repair 幂等语义既有）。

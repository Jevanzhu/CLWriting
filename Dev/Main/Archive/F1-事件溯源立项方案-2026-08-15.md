## 一、目标与非目标

**目标**
1. 五层写作链路（上下文→起草→审查→润色→提交）每层输出全事件化，带结构化终止原因；
2. 对话助手 agent 会话事件化（跨重启恢复、压缩走遮蔽不丢人类抄本）；
3. 血缘：任一章草案可回溯「哪个 prompt、注入了哪版设定/伏笔状态、哪次机检结果」；
4. 任意前缀重放（foldSurface）：重建任意时刻「模型当时看到了什么」；
5. 伏笔埋设→推进→回收全足迹事件化 + FTS 检索；
6. 「模型可见 ⟺ 已记录」可机械校验（prompt 注入内容必须能回溯到事件）。

**非目标（明确不做）**
- 不改正文文件存储（markdown 路径/目录结构原样）；
- 不改章节版本机制（Revision 指纹 + .版本/ 快照 + manifest 定稿基线原样）；
- 不劫持编辑器保存路径、不事件化作者手改；
- 不搬 dsh 的 JSONL/zstd、Cordis、SESSION_FORMAT_VERSION 门禁机制；
- 事件里不复制正文全文——只记 Revision 指纹 + 路径引用（超长中间产物走 spill）。

## 二、事件类型字典（v1）

三类事件族（映射自 dsh types.ts:236-333，按 CLWriting 域裁剪）：

**边界类**（不进 surface）
- `session/start` / `session/end{reason}`
- `turn/start{turn}` / `turn/end{turn, reason}`（reason ∈ completed/aborted/blocked/error/max-tokens/interrupted）
- `step/start{turn, step, layer}` / `step/end{turn, step, reason}`——layer ∈ context/draft/review/polish/submit（五层链路每层一个 step）
- `compaction/start` / `compaction/end{ok, error?}`

**消息类**（surface-eligible，必须带 surface_op）
- `user/message{message}`——作者指令/细纲确认/tool_result 回填（framing 归生产者）
- `assistant/message{turn, step, message, usage?}`——草案/审稿意见/润色稿/对话回复；空 content 只承载 usage 的壳投影为 null
- `tool/call{turn, step, callId, name, arguments}` / `tool/result{turn, step, callId, content, isError?}`

**内容/状态类**（血缘与记账）
- `revision/ref{chapter, revision, path}`——正文版本指纹引用（血缘锚点）
- `settings/snapshot{scope, version, digest}`——注入设定快照（角色卡/世界观/境界/伏笔状态指纹）
- `check/report{chapter, reds, yellows, reportRef}`——机检报告（自愈打回判据来源）
- `retry/attempt{attempt, maxAttempts, redIssues}`——自愈重写轮次（「连续相同红项换策略」的 canonical key 来源）
- `foreshadow/change{operation, entry}`——伏笔状态机，动词 create/edit/pause/resume/complete/block/clear（goal 词汇）
- `todo/write{todos}`——章节任务清单整表快照（无 id 三态，last-write-wins）
- `llm/call{model, usage, stopReason, errCode?}`——合并 trace.ts 的 TraceEntry
- `llm/retry{attempt, delayMs, provider, policyKey}`——重试记账（先落库后等待）
- `spill/ref{locator, bytes}`——spill 外置引用（事件只记 locator）

## 三、存储设计

**落址**：`<userData>/clwriting/session/<bookHash>.db`，每书一库；书库目录零改动。

**DDL（v1）**

```sql
PRAGMA journal_mode = WAL;
CREATE TABLE IF NOT EXISTS events (
  seq         INTEGER PRIMARY KEY,      -- 全局单调 rowid；session 内重放按 seq 排序
  session_id  TEXT NOT NULL,
  turn        INTEGER,
  step        INTEGER,
  type        TEXT NOT NULL,
  data        TEXT NOT NULL,            -- JSON 载荷
  surface_op  TEXT,                     -- NULL | 'append' | 'replace'
  shadow_start INTEGER,                 -- replace 遮蔽闭区间 [start, end]（seq）
  shadow_end   INTEGER,
  source_seqs TEXT,                     -- JSON 数组：sourceEventSeqs（血缘/被遮蔽节点）
  replace_generation INTEGER NOT NULL DEFAULT 0,
  created_at  INTEGER NOT NULL
);
CREATE INDEX idx_events_session ON events(session_id, seq);
CREATE TABLE IF NOT EXISTS sessions (
  session_id TEXT PRIMARY KEY,
  format_version INTEGER NOT NULL DEFAULT 1,
  book        TEXT NOT NULL,
  header      TEXT NOT NULL,            -- JSON：kind/起始元数据
  created_at  INTEGER NOT NULL,
  updated_at  INTEGER NOT NULL
);
```

**与 dsh 的三处刻意差异**（写进注释）：
1. seq 用全局 rowid 而非每 session 连续计数——多 session 同库，投影按 session_id 过滤 + seq 排序即可，「seq 即数组索引」的优化在 SQL 下无意义；
2. shadow 区间直接落列（shadow_start/shadow_end）而非塞 JSON——查询「哪些节点被遮蔽」走索引；
3. replace_generation 落列——派生消息缓存的失效判据可 SQL 查询。

**写入纪律**（照抄 dsh/盘点教训）：每批一个事务；先写事件再变更内存投影（观察者一致性）；「先落库后等待」（llm/retry）；失败回滚到上次提交点；torn 行（seq 空洞）由启动修复补 closers。

## 四、surface 投影与 deriveMessages

**投影语义**（照抄 dsh surface.ts:362-379 + 83-114）：

- 只有 user/message、assistant/message、tool/result 三类可上 surface；
- append：追加到可见序列尾；replace：新节点遮蔽闭区间 [start,end] 内全部旧节点（旧事件仍在表中）；
- 投影规则（唯一逐节点规则）：
  - user/message → data 原样（framing 归生产者）；
  - assistant/message 空 content → 跳过（usage 壳不进抄本）；
  - tool/result → tool_result 消息；
- foldSurface(prefix)：从空状态逐事件重放前缀 → 重建任意时刻的模型可见消息序列；
- 派生消息缓存以 replace_generation 判失效。

**校验链**（照抄 surface.ts:185-347）：非 surface 事件禁带 surface_op；replace 的 start/end 必须已可见且 start≤end；source_seqs 必须完整覆盖每个被遮蔽节点、全部早于当前 seq、无重复。

**UI 抄本**：读 append 起源事件（人类可见史不被压缩遮蔽抹掉）；审计视图用 foldSurface 展示「模型看到的 vs 人类看到的」差异。

## 五、血缘设计

- 每个 assistant/message 事件带 source_seqs：引用「本次请求依赖的输入事件」——settings/snapshot、revision/ref、check/report、user/message；
- 章节草案血链：草案事件 → revision/ref(前一版) + settings/snapshot(设定版本) + retry/attempt(重写轮次)；
- 「模型可见 ⟺ 已记录」校验器：prompt 组装函数在发送前把注入段落登记为事件；校验器断言「请求内容 ⊆ 事件可重建内容」——违反即告警（开发期 fail loud，运行期告警）；
- 伏笔足迹：foreshadow/change + 正文 grep 命中都事件化 → FTS 检索「哪章埋了哪章收了」。

## 八、跨平台说明（决策 1 依据）

- node:sqlite 为 Node 内置模块，win/mac 同 API、无原生编译（better-sqlite3 需按 Electron ABI 重编译，弃）；项目已在 self-heal.ts、cache 层使用，路径已验证；
- JSONL+zstd 方案需引入 zstd 原生绑定（dsh native/ 目录即为此），跨平台成本更高，弃；
- 注意点：Electron 升级时确认内置 Node ≥ 24（engines 已声明）；WAL 依赖本地磁盘语义——userData 在本地盘无碍，未来若做云同步需先评估 WAL 兼容。

### PM-1 [P1] 伏笔足迹缓存 MISS 同步单 tick 全书联合正则扫——写后打开伏笔面板/总览即数百毫秒级冻结

- 位置：`src/studio/server/api/foreshadows.ts:81-102`（`getForeshadowsCached` 同步 MISS 路径 + 指纹含 `写作/正文` 目录 mtime `:68-78`）；`src/document/foreshadow.ts:343-386`（`buildKeywordIndex` 联合正则逐章全文扫）、`:276-334`（`scanForeshadowTrails`）、`:428-453`（`collectChapterTexts`）。
- 证据（亲核）：
  ```ts
  // foreshadows.ts:82-93 —— MISS 即同步单段完成全书扫描，无任何让出
  const sig = foreshadowDirSignature(bookRoot)   // 指纹含 写作/正文 目录 mtime
  const entries = readForeshadows(bookRoot)
  const trails = scanForeshadowTrails(bookRoot, entries)  // walk + 联合正则扫全书
  // foreshadow.ts:365-369 —— 每章正文一次联合正则全文扫描
  for (const [章号, text] of chapters) { re.lastIndex = 0; while ((m = re.exec(text)) !== null) { ... } }
  ```
- 机理：缓存指纹包含正文目录 mtime——保存走原子 rename，**任意一次保存即刷新目录 mtime 使缓存失效**；MISS 后在同一个 tick 内同步完成：递归 walk 正文目录 + 逐章 statSync + 变更章读盘（R66-6 `chapterTextCache` 已把未变章 I/O 降为指纹复用，但**联合正则对全书每章全文的一次扫描与倒排索引构建仍是单段同步 CPU**，O(全书字数)，无 setImmediate 让出）。前端两个消费方（`ForeshadowPanel.vue:131` watch immediate / `OverviewView.vue:86` 总览页）走同一 GET。模块自身注释（`foreshadow.ts:395-398`）承认此路径 200 万字下曾「秒级阻塞」，R66-6 只解决了重复 I/O。
- 触发：写完一段（已保存）→ 打开/刷新伏笔面板或切到总览页 → 服务端单 tick 全书重扫。
- 影响：200 万字级书单次阻塞估算数百毫秒（冷缓存叠加逐章同步 I/O 更久）；期间 SSE 心跳、保存、其余请求全部排队。

- 置信度：高（机理双侧亲核；量级为估算未实测）。**R47 批在途改动仅涉此文件的过期逐出（R47-18，+4 行），与本体不同面，无冲突。**

### PM-2 [P1] countWords 码点展开把全文物化成单字符数组——全链最高频内存抖动源（实现本体层）

- 位置：`src/format/words.ts:12-14`（唯一实现，服务端与 web-next 共享——`chapters.ts` re-export、`web-next/src/shared/words.ts` re-export）。
- 证据（亲核）：
  ```ts
  export function countWords(body: string): number {
    return [...body.replace(/[#>*_`~\-\[\]()!\s]/g, '')].length
  }
  ```
- 机理：两步都是 O(n) 分配——`replace` 无条件产出剥标记副本（2M 字 ≈ 4MB）；`[...]` 展开再物化长度 = 字符数的数组：数组本体 ≈16MB + n 个单字符堆字符串（V8 单字符缓存只覆盖 Latin-1，中文每字符独立 SeqTwoByteString ≈24-32B）→ **每次调用瞬时垃圾 70-90MB（200 万字输入），数完即弃**；CPU 侧展开 + 年轻代清扫远慢于纯计数循环。
- 调用面（代理逐一核实）：服务端每次保存 ×2（`service.ts:497-498` 新旧文各一）、`readChapter` 每次现读（`chapters.ts:102`）、树 probe 冷路径、版本列表兜底（`version.ts:512`）、定稿（`finalize.ts:175`，与 readChapter 双算）；浏览器端 `EditorView.vue:101-115` **每击键（150ms 防抖后）对当前全文**、保存成功后再算一次（`doc.ts:229`）。常规 6KB 章无感；超大单章场景每击键 + 每 30s 保存双份反复制造 70-90MB 级瞬时分配，GC 频率陡增。
- 与 RC-1/R47-1 的正交性：R47-1 修「面板挂点防抖漏配」（WritingInfoPanel/HistoryPanel/FocusStatsBar 三处未防抖）；本条修「实现本体」——重写后即使不防抖，单次成本也从「全文正则 + 码点数组物化」降为单遍零分配计数，两个修复互补不互替。
- 修复建议：改单遍 charCode 计数、零分配，**口径逐位不变**（R31-11 备案约束）：剥除集全部为 BMP 字符，`/[#>*_`~\-\[\]()!\s]/` 的 `\s` 需展开为完整码点集（含 `\u00a0\u1680\u2000-\u200a\u2028\u2029\u202f\u205f\u3000\ufeff`），代理对按 1 码点计（现状 `[...]` 语义）。一处改动服务端 + 前端全链同时受益。回归测试钉住口径（对含 emoji/代理对/全角空格/nbsp 的样张断言与旧实现逐位一致）。
- 置信度：高（实现与全部调用点核实；内存量级为 V8 对象模型估算 ±30%，量级确定）。

### PM-3 [P1] journal pending 行携带全文 + 超 2MB compact 整读整解析——大章每笔保存 4× 全文 IO 放大

- 位置：`src/document/journal.ts:81-93`（pending 条目含 `content` 全文）、`:242`（`JOURNAL_COMPACT_BYTES = 2MB`）、`:267-292`（`maybeCompactJournal`：`findUnsettled` 整读 + 逐行 JSON.parse → 重写 + fsync）；调用点 `src/document/service.ts:479`。
- 证据（亲核 compact 路径）：
  ```ts
  // service.ts:479 —— content 为全文（2M 字 ≈ 6MB）
  opId = await appendPending(journalPath, docId, currentRev, byteRestore ? '' : content)
  // journal.ts:279-285 —— 超阈即整读找 unsettled 再重写
  const unsettled = findUnsettled(journalPath)   // 整读 + 逐行 JSON.parse（含全文行再物化 4MB）
  atomicWriteFile(journalPath, ..., { fsync: true })
  ```
- 机理：每笔保存把全文追加进 journal（stringify 转义副本 + utf-8 编码 + append + fsync）；文件超 2MB 即在 settle 后触发 compact：整读 + 逐行 parse（解析含全文的 pending 行再物化一份 4MB 字符串）+ 重写 + fsync。6MB 单章稳态每笔保存 ≈ **24-25MB 磁盘写 + 12MB 读 + 3-4 次 fsync，全部同步 IO 在事件循环上**（30s autosave 节拍持续运转）；journal 在阈值附近反复膨胀-压缩，SSD 写放大。
- 触发：单文档正文（含 fm）> 约 1.4MB UTF-8 时每笔保存必触 compact；极限单章 100% 触发。
- 修复建议：① pending 内嵌全文设尺寸闸：`content` 超如 256KB 时写 `content: ''` + 降级标记（降级形态已存在，R31-21 实证可行），崩溃检测语义不变，恢复材料改依赖 `.版本/` 快照（`maybeSnapshot` 覆写前留底已保证，大文档收紧为必留底即可）；② `findUnsettled` 对超长行先做后缀/标记判定再决定是否整行 JSON.parse，免为找 unsettled 解析 6MB 行。
- 置信度：高（机制、阈值、调用链亲核；「每笔必触」依赖单章 > 2MB 前提，属极限场景成立）。

### PM-4 [P1] executeSave 保存链全程多副本并存——超大单章单笔保存峰值 ≈ 文本的 15-25 倍

- 位置：`src/document/service.ts:443-570`（亲核全程）。
- 机理（2M 字单章一次保存内同时/先后存活的副本）：`input.content` 4MB（入参不可释放）→ `canonicalizeText` 副本 4MB（`:463`）→ journal stringify 副本 + 行拼接 ≈10MB（`:479`）→ `diskBytes` 6MB（`:443`）→ `oldBodyText` 4MB 活到快照留底后（`:494-516`）→ `bodyOf` split/join 瞬时 ≈8MB ×2 → **countWords 码点展开爆发 70-90MB ×2（PM-2）** → `atomicWriteFile` 内部 Buffer.from 6MB → **`:568-570` 再一次 `Buffer.from(content)` 6MB 纯冗余**（R40-20 注释自述「刚写入的字节即 content 直接派生」，却又重新编码了一遍）。稳态副本 ≈35-45MB，countWords 爆发窗口峰值 **≈100-130MB = 4MB JS 文本的 25 倍**；常规 6KB 章 ≈300KB 无感。
- 影响：Node 侧堆瞬时冲高 + 深度 GC 停顿；保存串行队列耗时拉长，同步 IO 串联阻塞事件循环。
- 修复建议：① `contentBytes` 单次转换复用——`atomicWriteFile` 与 `computeRevisionBytes` 共用同一 Buffer（atomic.ts 已支持 Buffer 直写零转换）；② 消除 `oldBodyText` 文本中间态——`maybeSnapshot` 普通保存分支直传 `diskBytes`（writeVersion 已支持 Buffer 留底），wordDelta 旧值改 docId 级「上次保存字数」缓存（保存成功记新字数，下次命中免重算，连带省掉 `bodyOf(oldBodyText)` 的 split/join）；③ 配合 PM-2 重写后峰值可压回 ≈8 倍以内。
- 置信度：高（各副本行号与生命周期亲核；MB 数字为 V8 模型估算 ±20%）。

### PM-5 [P2] 字数日记 jsonl 无界增长 + 每次保存触发双全文件同步读/split（无 compaction）

- 位置：`src/document/words-diary.ts:32`（readBaseline）、`:112`（readTodayDelta）——各自 `readFileSync(fp).split('\n')` 全文件读 + 全行数组分配；写侧只 append 无压缩（`:57/:99`）；触发链 `doc.ts:236`（每次保存成功 fire-and-forget `ensureBaseline` → GET，`words.ts:39-59` 无按日去重）+ `documents.ts:279`（一次 GET 双读）。
- **亲核降级记**：服务域代理报 P1 的机理「readTodayDelta 全部行 JSON.parse」**部分失实**——在途 R47-25（四十七轮）倒序短路已把 parse 循环收成 O(当日行数)；残余成立面为：① 每次保存触发的 GET 仍执行 **2×（readFileSync 全文件 + split('\n') 全行数组分配）**，随 jsonl 文件（append-only、无 compaction/轮转）书龄无界增长线性变贵；② 文件本体无压缩。重度自动保存一年 ≈ 数 MB-10MB 文件 → 每次保存后 30-130ms 同步停顿，O(n²) 累计行为不变、常数已大减。定级 P2（长书龄渐进退化）。
- 修复建议：写侧 compaction——跨日首写（appendBaseline 时发现日期变更）把历史每日多条 delta 合并为一行日汇总（baseline + 日累计 delta 语义全保），走跨进程锁 + 原子写；或按月分文件（读侧只开当月 + 昨月末条）。
- 置信度：高（亲核；影响为线性外推）。

### PM-6 [P2] 版本面板 words 兜底成必然路径——打开版本面板 = O(版本数 × 全文) 同步 IO

- 位置：`src/document/version.ts:504-512`（`read.meta.words ?? countWords(read.content)`）；根因 `src/document/service.ts:670/987/1224`（保存链三处 `writeSnapshot` 均不传 `words`；对照 `finalize.ts:175` 与 `:1344/:1597` 已传先例）。亲核：三处调用点 options 仅 origin/reason/baseRevision/policy/force。
- 机理：`?? countWords` 兜底本为兼容旧版本，但保存链从不写 `words` → 兜底成必然：每列一次版本对每个版本文件**整读正文**（readVersion 无界读，非头部 64KB 的 readVersionMeta）+ 全文计数。策略上限 30 版 × 6MB = 一次面板打开 ≈180MB 同步读 + 30 次全文 countWords，全在事件循环。
- 修复建议：保存链 `maybeSnapshot` 落版本时把字数写进 meta（wordDelta 已算出旧文字数，或对留底内容计一次——PM-2 重写后成本单遍零分配）；旧版本仍走兜底。
- 置信度：高（亲核三调用点 + 先例对照）。

### PM-7 [P2] ngramRepeatRate 滑窗 n-gram 全量入字符串键 Map——超大单章机检瞬时峰值 ≈150-250MB

- 位置：`src/format/sentences.ts:30-63`（亲核：BMP 快路径 `s.slice(i, i+n)` 每窗新串入 `Map<string, number>` + R31-18 astral 码点路径 `cps.slice().join('')`）。
- 机理：2M 字单章 ≈2M 次窗口 slice 物化 + 2M Map 条目（短串 32-48B + 条目开销 ≈50-60B）≈ **150-250MB 瞬时堆**，检完即弃；跑在主服务进程（非导出 worker 的 1GB 堆闸内）。机检 API 按需触发（非每键/每保存），常规 6KB 章数千条目无感。
- **修复建议修正记**：文档引擎代理建议「按句分块流式」经主审核验**不成立**——重复计数**跨句聚合**（counts 全文统一累计，两句各现一次的短语是重复），逐句独立 Map 会漏检；正确方向：gram 键改 64 位滚动哈希 `Map<number, number>`（BMP 路径按码元滚动、astral 路径按码点序列哈希，两键空间不相交——沿用 R31-18 同思路），碰撞概率 2^-64 级可忽略；回归测试钉住 rate/repeatInstances/repeatChars 三值与旧实现逐位一致。
- 置信度：高（亲核；字节数 V8 模型估算）。

### PM-8 [P2] foreshadow 章正文缓存按条数封顶、无字节预算——超规格书缓存上限即全书正文常驻

- 位置：`src/document/foreshadow.ts:401-425`（`CHAPTER_TEXT_CACHE_MAX = 4096` 条，无字节预算）。承诺规格（200 万字）下 ≈4-8MB 常驻可接受（注释登记的有意权衡）；书到两千万字级 ≈40MB+ 常驻且无压力感知。
- 修复建议：字节预算双闸（如 64MB），插入时累计 size 超预算按 FIFO 淘汰至预算内；条数闸保留。
- 置信度：高（亲核注释与实现；「构成问题」依赖超出承诺规模，故 P2）。

### PM-9 [P2] 左栏拖拽热区 mousemove 读 rect 后写 cursor——布局脏窗口内强制同步 reflow

- 位置：`src/studio/web-next/src/components/shell/WorkspaceShell.vue:72-76`（亲核）。

### PM-10 [P2] 对话冷启动恢复与历史/审计端点全量载入事件库——O(全书事件) 瞬态峰值随书龄单调增大

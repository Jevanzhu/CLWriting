## 四、发现清单（P2×2 + P3×10；全部主评审亲验）

> 编号 R1W-N（win 专项 R1 轮）。判级沿用项目口径：P1=崩溃/数据丢失，P2=功能性缺陷，P3=健壮性/体验。

### P2

**R1W-1　`src/fs/atomic.ts` 清理路径 `rmSync` 无防护（6 处）——瞬时占用可把成功写反转为失败**

- 位置：`atomicWriteFile` catch（:85）；`atomicWriteStream` 三个 catch（:120/:128/:140）与 publish 分支（:134）；`createFileExclusive` finally（:186）。
- 证据（createFileExclusive finally 为例）：
  ```ts
  } finally {
    rmSync(tmpPath, { force: true })
  }
  ```
- 影响：tmp 文件在 closeSync 后数微秒内恰是杀软/索引器锁定窗口（本文件 :31 `RETRYABLE_RENAME_CODES` 注释自认「win 主战场」）。`rmSync` 撞 EBUSY/EPERM 时：①createFileExclusive 场景——目标已成功建成，finally 抛错吞掉 `return 'created'`，调用方（doCreate/doCopy/style-entry）报 WRITE_ERROR「新建失败」，作者重试即撞 ALREADY_EXISTS；②catch 场景——清理抛错掩盖原始 rename 错误（错误归因失真）。
- 修复方案：新增导出原语 `rmQuietly(path)`（try/catch 吞错，残留交既有 `sweepAbandonedTmpFiles` 兜底——tmp 命名本就匹配 ABANDONED_TMP_RE 清扫模式），六处收编。

**R1W-2　`src/fs/cross-process-lock.ts:199` release 的 `rmSync` 无防护——finally 中的释放失败反噬受锁操作**

- 证据：
  ```ts
  try {
    if (readFileSync(lockPath, 'utf-8') !== payload) return
  } catch {
    return
  }
  rmSync(lockPath, { force: true })   // ← 唯一无防护点
  ```
- 影响：release 在全库调用方均于 finally 中执行（`document/service.ts:556`、`manifest.ts:289`、`finalize.ts:251`、`install/books.ts` 等）。锁文件创建+关闭后即被杀软瞬时锁定 → release 抛 EBUSY → finally 异常顶替已成功的保存/清单写返回（文件已写好却回 500）。锁文件读回比对守卫做得极细，删除本身漏防。
- 修复方案：新增导出原语 `rmWithRetryQuiet(path)`（EPERM/EBUSY 3×50ms 退避后吞错 + log.warn 留痕）；残留自愈路径已存在——锁文件带活 pid 判 held，超龄（MAX_HELD_MS 10min 无续期）走 stale 接管，进程死后由 sweep 的 .lock 分支清扫。

### P3

**R1W-3　`src/document/service.ts` doTrash 删源失败无回滚——半完成软删无恢复（对照范式已在库内）**

- 位置：软删链尾 `rmSync(oldSafe, { force: true })`（:1526 附近）。
- 影响：link 落位 `.trash/` 后删源撞 EBUSY/EPERM（编辑器占用正文文件是 win 常态）→ 外层 catch 报「删除失败」，但回收站副本已落地 + trash 条目已登记。重试走时间戳后缀链在 `.trash` 堆叠重复副本；对陈旧条目 restore 报 OCCUPIED。同文件 doMoveOrRename（R33-43）对同型窗口已有「删源失败→拆掉落位新链」的回滚范式，doTrash 漏配同款。
- 修复方案：删源 try/catch——失败时 best-effort `rmSync(finalTrashAbs)` 拆掉落位副本，返回带明确人话的 WRITE_ERROR（文件未动可重试；残留条目按既有 Z-6 守卫语义无害）。

**R1W-4　`src/document/service.ts:997` syncRenamePieceList 静默吞错——章纲与正文文件名无痕分叉**

- 证据：`renameSync(oldSafe, dst)` 外层 `catch { /* 清单同步失败不阻断正文 rename */ }` 零日志。
- 影响：不阻断语义正确（注释明示），但 win 上章纲文件被编辑器占用 → rename EBUSY 被静默吞 → 正文/章纲文件名永久分叉且无任何诊断痕迹（本文件其余失败路径均 log.warn）。
- 修复方案：catch 内补 `log.warn`（不动语义）。

**R1W-5　`src/install/books.ts:78-79` 保留设备名校验漏「CON.md」形态——与自家消毒单一真相源口径漂移**

- 证据：`bare` 只剥尾点/尾空格后全名匹配 `^(CON|PRN|...)$`，`CON.md` / `aux.txt` 放行；而 `src/format/filename.ts winCompatNamePart` 用 `split('.')[0]` 判——同仓两口径。
- 影响：建书名 `CON.md` 漏到 mkdir——Win10 报 ERROR_INVALID_NAME（作者看到 generic errno 文案而非预设人话拒绝），Win11 产生设备别名歧义目录。
- 修复方案：`bare` 计算改取首段（`.split('.')[0]`），对齐 filename.ts 口径；补用例（`CON.md`/`aux.txt` 拒，`conan.md`/`我的书` 过）。

**R1W-6　`src/desktop/server-manager.ts:235-237` env 删除不认 win 大小写不敏感环境变量名**

- 证据：`{ ...process.env }` 产出大小写敏感普通对象；`delete childEnv['CLW_STUDIO_TOKEN']` 对宿主残留的小写 `clw_studio_token` 无效（win 环境名不区分大小写、保序保留），子进程 env block 出现双重键，取值未指定——若命中旧值则全请求 403。
- 修复方案：逐键 `toUpperCase()` 比对删除后再注入受控值（N-1 意图的真实兑现）。

**R1W-7　`src/desktop/initial-book.ts:36` + `src/desktop/main.ts:278` 路径比较大小写敏感（win）**

- 证据：`resolve(workDir, b.path) === abs`（--book 直达匹配）与 `findWorkDir(dir) === resolve(dir)`（isLibraryDir）均为字符串全等；win 路径大小写不敏感、盘符/8.3 大小写可漂移 → 大小写不一致的 `--book G:\Lib\MyBook` 静默落 null 被丢弃。库内先例：`document/manifest.ts:250` / `knowledge/manifest.ts:20` 均有 win32 降口径比较。
- 修复方案：`src/fs/user-data-path.ts` 增 `samePath(a,b)` 原语（resolve + win32 双侧 toLowerCase 后比较），两处收编 + 单测。

**R1W-8　`src/git/exec.ts:63/:122` git spawn 未设 `windowsHide`——打包态 GUI 下 git 调用闪控制台黑窗**

- 证据：`spawnSync('git', args, { cwd, stdio, encoding, ... })` 与 `spawn('git', args, { cwd, stdio })` 均无 windowsHide。src 内全部 child_process 调用点（6 处）唯此二处起外部控制台程序；打包态主/子进程无控制台时，git.exe（控制台程序）会新建可见控制台窗。statusPorcelain 在启动迁移链、ai-track 在保存链，均高频。
- 修复方案：两处补 `windowsHide: true`（隐藏窗口不影响 stdio 管道；dev 有控制台形态行为不变）。

**R1W-9　`src/desktop/main.ts` 退出兜底缺口——无 session-end/信号/未捕获异常处理**

- 证据：grep 全文件零 `process.on('SIG…')`、零 `session-end`、零 `uncaughtException`。优雅停机链（3.5s，serverManager.shutdown）只挂在 before-quit/window-all-closed。win 上 OS 关机/注销（WM_ENDSESSION）、dev 控制台 Ctrl+C/Ctrl+Break 时整链被跳过，utility child 随进程硬死（journal 恢复 + 10min 孤儿会话宽限兜底，数据不丢但收尾全失）。打包态主进程未捕获异常的 stderr 无人可见。
- 修复方案：①`app.on('session-end')` → best-effort `void serverManager.shutdown().catch(...)`；②`process.on('SIGINT'/'SIGBREAK')` → `app.quit()`（走既有 before-quit 幂等链，quitViaShutdown 门防重入）；③`process.on('uncaughtException')` → log.error 留痕（JSONL 落盘）+ 延迟 `process.exit(1)`（保持等价崩溃语义，仅补诊断）。

**R1W-10　`src/desktop/main.ts:557-565` 主窗最小高度 760 硬下限 > 1366×768 工作区——小屏出生即压任务栏**

- 证据：1366×768（win 最常见小屏）工作区 ≈728px；`winH = min(1237, wa.height-80) = 648` 被 `minHeight: 760` 钳到 760，窗口底沿探入任务栏 ≈32px；`window-state.ts WIN_MIN_HEIGHT=760` 恢复下限同步使小屏存档永不生效。
- 修复方案：主窗创建下限改 `Math.min(760, wa.height - 8)`（下限不得超过可用空间——「三栏不挤」的产品意图在大屏原样保留）；`WIN_MIN_HEIGHT` 760→600（恢复损坏检测下限随行；宽度 1200 不动，1366 宽工作区可容纳）+ 契约测试同步。

**R1W-11　`src/rag/store.ts:151` deleteRagDbFiles 的 `unlinkSync` 无 EPERM/EBUSY 退避——删库自愈链对瞬时锁脆弱**

- 影响：损坏库自愈（rebuild 端点）中 db 已正确 close（阶段 21 修复），但 unlink 仍可撞杀软瞬时锁 → rebuild 500 需人工重试。同文件 renameSync 迁移已有同型意识（R65-4），删除侧漏配。
- 修复方案：新增导出原语 `unlinkWithRetry(fp, {unlink/sleep/retries 注入})`（EPERM/EBUSY 3×50ms 退避），deleteRagDbFiles 三后缀收编 + 原语单测。

**R1W-12　`src/studio/server/static.ts` 未拦 win 保留设备名请求——dev 态可挂死连接**

- 影响：GET `/CON`、`/NUL` 等落 stat（win 上设备名可解析成功）→ readFile 设备可挂起等待（dev 有控制台时）/异常回落。纯本地回环 + 打包态无控制台，利用面极窄；win 适配补全口径。打包态 dist/web 资产名恒带 hash，合法资产永不命中保留名。
- 修复方案：静态分支 stat 前按 basename 拦保留名（含 `.扩展名` 形态）→ 404；测试断言 `/con`→404（跨平台可跑）。

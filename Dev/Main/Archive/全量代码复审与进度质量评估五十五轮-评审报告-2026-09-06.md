### 6.1 P1×1

**R55-C-1〔P1〕chat 每轮发送全量历史，发送前无体量防线——重工具会话可超窗卡死**
- 位置：`src/ai/orchestrate/chat/turns.ts:466-523`（发送）、`src/ai/prompts/chat.ts:156-194`（trimHistory）、`src/ai/orchestrate/chat/finish.ts:143-160`（finalizeHistory 唯一调用点）、`src/ai/provider/failure.ts:91-99`（shrink-prompt 无消费者，注释自认「A7 接线前无消费者」R66-11）。
- 机制（主审亲验）：轮循环发送前只消毒不截断（`const sanitized = sanitizeHistory(history)` → `messages: sanitized`）；体量防线 trimHistory/compaction **只在成功收尾后的 finalizeHistory 执行**；trimHistory 正常分支按回合金切（窗口 10 回合），**20k 码点预算只存在于「边界不足」回落分支**（R53-C-1 修复面）。
- 定量：单项有界（用户消息 5 万字符上限、read_chapter 单次 20k 码点上限〔turns.ts:47-51〕、每回合工具循环 ≤5 轮〔MAX_AGENT_TURNS=5〕），但 **回合 × 窗口累计无界**：10 回合窗口 × 每回合多个 20k tool_result ≈ 20 万+ 码点，128k 级模型上可稳定超窗。
- 影响：超窗后每次发送必 400（CONTEXT_WINDOW_EXCEEDED），failureAction('shrink-prompt') 无消费者、降级链剥 structured/tools 不解决超窗，压缩又依赖「成功完成」才触发——**该会话卡死，只能清空历史自救**。无书稿数据丢失（chat 历史仅对话层）。
- 修复建议：轮循环发送前按码点预算预检预切（复用 fallbackBudgetCut 同口径保尾切，不依赖错误反馈环）；或接通 shrink-prompt 消费者（A7）作二道防线。建议前者为主、后者登记。

### 6.2 P2×6（全部主审亲验成立）

**R55-A-1〔P2〕session-end 观察窗 5s 与停机链最坏预算失配，复合场景自愈拒绝**
- 位置：`src/desktop/main.ts:264`（SESSION_END_RECOVERY_MS=5000）+ `src/desktop/server-manager.ts:602`（shuttingDown 态 restartPinned 返 null，注释称「观察窗时长已覆盖正常收尾」）。

**R55-C-2〔P2〕calibrate-tokens 无 task 过滤混入 chat 样本，TOKEN_COEFFICIENTS 拟合失真**
- 位置：`scripts/calibrate-tokens.ts:53-58`（全量采样 `WHERE type='llm/call'` 无 task 过滤）+ `src/ai/orchestrate/chat/turns.ts:490`（chat 的 promptMeta.chars 自 Q-11 起只记当轮末条消息）+ `src/ai/token-calibration.ts:7-9`（头注假设「chars = prompt 全字数」）。
- 影响：多轮 chat 真实输入含整段历史而 chars 只记末条 → 样本 chars 低估数个量级 → 该模型拟合 coeff 虚高 → TOKEN_COEFFICIENTS 建议值失真，波及 estimateTokens、预算闸与 R73-1 估计入账。离线维护脚本，但失真流入运行时。

**R55-E-1〔P2〕readJson「断开无 error 形态」下 promise 永不 settle，同步占住的闸随 handler 悬挂**
- 位置：`src/studio/server/http.ts:214`（`req.once('close', clearIdle)` 只清闲置计时器不 settle promise；error 路径 :204-213 只覆盖 ECONNRESET/EPIPE）。
- 机制（主审亲验）：客户端发部分 body 后干净半关闭（无 errno 形态，R51-G-2 注释自认存在）→ close 触发、计时器被清、resolve/reject 均不执行。按 CC-P2-9 在 readJson 前同步占闸的端点（stream.ts:463、io.ts:124 等）try 块永不退出 → 闸与跨进程锁文件（pid 活着不判 stale）永不释放，该书写端点/export 409 至进程重启。
- 触发面：本机信任域内客户端上传 body 中途被杀，概率低但后果为持久可用性损失。
- 建议：close 回调补 `if (!req.readableEnded) reject(clientAbort)`（一行防御，不依赖 Node 行为判定）；或先补「干净半关闭」实测用例钉 Node 24 行为后收口。

**R55-F-2〔P2〕SSE 半开连接盲窗：无客户端失活检测，自愈完全依赖服务端超时**
- 位置：`src/studio/web-next/src/composables/useSse.ts:159-166`（onopen 置 connected 后无任何活性 watchdog；主审 grep 复核零命中）+ `useHeartbeat.ts:9`（独立在线探测，失败信号未回灌 SSE）。
- 影响：服务端「接受连接、回 200 头、此后不发数据也不关」（进程挂起/隧道停滞）时 EventSource 无 onerror——UI 冻结在「已连接」最长至服务端 requestTimeout（~300s 档）。非数据丢失（重连后 sync 快照重建 + 残文水印保护），可靠性缺口真实存在。
- 建议：心跳连续 2 拍失败或「距最后一条 SSE 消息 > N 分钟且 running」时调 sse.resync()；或服务端加 keepalive 注释帧 + 客户端超龄 watchdog。

**R55-F-3〔P2·设计取舍待作者拍板〕渲染进程硬崩溃时 ≤自动保存间隔的键入无本地持久化兜底**

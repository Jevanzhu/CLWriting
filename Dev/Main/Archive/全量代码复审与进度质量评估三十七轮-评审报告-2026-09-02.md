### 4.1 P1（×1）

**R37-1〔E1 前端〕切书/关窗守卫看不到「在途保存」的脏文档 → 静默丢编辑竞态**
- 位置：`src/studio/web-next/src/stores/doc.ts:426-430`（flushDirty 扫描条件）、`doc.ts:445`（conflictedDirtyDocs 同款排除）、`doc.ts:479`（flushSyncOnUnload 同款盲区）；消费面 `src/studio/web-next/src/pages/Book.vue:149-160`。
- 证据：
  ```ts
  const dirty = [...docs.value.values()].filter(
    (e) => e.dirty && !e.saving && !e.conflict && !failed.has(e.docId),
  )
  if (dirty.length === 0) return [...failed]
  ```
- 机理（主评审亲验）：autosave/⌘S 在途（`saving=true`，API 超时档可达 30s）期间作者继续键入（快照后新键入使 `dirty` 保持 true）→ 切书：Z-8 冲突检查与 F1 失败检查双双跳过 saving 项 → `flushDirty` 立即返回空 → `setBook` 清空 `docs` 与 `inflightSaves`（R33-12）→ 在途 `doSave` 此后只写**已脱离缓存 Map 的旧 entry**：成功则快照后新键入永不上盘；失败/409 则连同快照内容一起静默丢失。`f1-flush-failure-guard.test.ts` 只覆盖「flushDirty 自己发起的保存失败」形态。
- 影响：作者在保存慢（网盘/大书/服务冷）场景下切书，最后数百毫秒~数秒键入不可恢复丢失且无任何提示——与本库「编辑永不静默丢失」底线（Q-3/F1/Z-8 三代守卫）正面冲突。
- 修法：`flushDirty` 对 `dirty && saving` 条目先 `await` 其在途 promise（catch 吞错）再进重扫循环，使在途保存的成败与快照后新键入全部进入既有失败上报/循环重扫闭环；`Book.vue` 在 flush 后补一次冲突态复检（在途保存落定后新转冲突的条目并入守卫弹窗）。

## 五、发现清单（R53-N）

严重度口径同链上历轮：P0 数据丢失/安全破口全场景；P1 红线级窄场景；P2 明确缺陷窄场景；P3 打磨项。

### 5.1 P1（×1）

**R53-A-1 win 关机/注销链跳过渲染层 flush——「编辑永不静默丢失」红线窄缺口（P1）**

- 位置：`src/desktop/main.ts:912-945`（close 拦截）、`src/desktop/main.ts:975-1000`（session-end 处理器）。
- 机制：win 收到 session-end（关机/注销/重启）→ 处理器置 `sessionEnding = true` → `saveWinState()` + `serverManager.shutdown()`（3.5s 预算）——**全程无渲染层 flush**；此后 close 拦截在 L919-920 `if (sessionEnding || appTearingDown) return` 直通放行，渲染层的关窗 flush 链（R44-2 重造的 `__clwFlushBeforeClose` 钩子）在该场景被短路。
- 后果：win 关机/注销是高频日常动作；距上一次 autosave 节拍 ≤ 自动保存间隔（默认 30s）内的键入静默丢失。正常关窗/退出路径（close/quit 拦截）均有 flush，唯 session-end 链缺位——不对称可证非设计取舍。
- 在案备案：R44-2 注释曾声明「不在有限窗口里白等渲染层 flush」（指拒绝无上限等待），但**未排除短预算尝试**（如 shutdown 3.5s 预算内并行发一次 flush 请求、尽力而为）；R50-A-1 已修「取消关机后 sessionEnding 不复位」（观察窗自愈），本项是同族剩余缺口，R50 修复面未覆盖。
- 降档讨论：主审维持 P1——触发动作高频（每次关机）+ 丢失面为用户最后键入 + win 专用链。修复方向（§八 批 1）：session-end 处理器内与 shutdown 并行下发一次带超时（≤2s）的渲染层 flush 尽力而为请求；失败不阻塞关机（保持现行为），但消掉「能 flush 而不 flush」的不对称。

### 5.2 P2（×5，全部主审亲验成立）

**R53-B-1 chat close 第二段 appendEvents 失败不可重试——与在案注释宣称不符**

- 位置：`src/events/chat-bridge.ts:200-321`。
- 机制：close 两段式——首段 flush 失败会回滚 `ended` 可重试（L233-244）；第二段 `appendEvents`（L305）失败**不回滚**且 `finally dispose()`，此后重试被 L227 `if (this.ended) return null` 吞掉。L279-285 R51-B-4 修复注释宣称「close 失败可重试」，实际仅覆盖首段。
- 后果：恰在第二段失败时，本轮对话事件副录永久缺尾（正文已落盘、事件链断尾），重试通道名存实亡。
- 修复方向：第二段失败同样回滚 `ended`（dispose 延后到成功或放弃路径），或明确登记取舍。

**R53-C-1 chat 历史收缩回合数盲区——收缩失效静默全量携带**

- 位置：`src/ai/prompts/compaction.ts:50-60`（planCompaction）+ `src/ai/chat.ts:154-180`（trimHistory）+ `src/process/finish.ts:160`（唯一调用点）。
- 机制：`planCompaction` 在 `turns.length <= keepTurns`（10）时返回 null（不收缩）；`trimHistory` 从尾向前找 10 个**纯文本 user** 边界，找不到则 `cutIdx = 0` → `slice(0)` **全量返回**。长对话里连续工具回合/无纯文本 user 的窗口超过阈值时，收缩计划为 null 或裁剪落空，历史整段随每次请求全量携带。
- 后果：token 成本静默膨胀（不崩、不错，但「200 万字不崩」的成本防线在该窗口失效）；无 warn 留痕。
- 修复方向：找不到边界时按 token/字符预算硬截断 + warn 留痕，或 planCompaction 对超长历史强制生成收缩计划。

**R53-D-1 manifest 缓存 mtimeMs 粗粒度陈旧命中（P1 候选降 P2）**

- 位置：`src/document/manifest.ts:50-155`（manifestStatSig L58-65 返回 `${st.size}:${st.mtimeMs}`）。
- 机制：FAT/exFAT 文件系统 mtime 2 秒粒度 + 同尺寸写入 + **他进程写**（外部编辑器改书库文件）→ 指纹不变 → 缓存陈旧命中 → 后续 RMW 回写把外部修改回滚。
- 降档理由：应用自身单实例锁内写路径有 journal/事件序保障；触发需外部进程在 2s 窗口内同尺寸写入，窄场景。同类先行（R44 族 darwin 折叠、R36 目录 stat）均已按 P2 处置。
- 修复方向：指纹并入目录 mtime 或 inode/ino+size 组合（chapters.ts 的 bigint mtimeNs 先例可循）。

**R53-D-2 journal 256KB 快照剥离丢字窗——崩窗内新内容零盘上副本**

- 位置：`src/document/journal.ts:75-109`（JOURNAL_PENDING_SNAPSHOT_MAX_BYTES = 256KB，超限落 `degradedFallback`：`content:''` + `degraded:true`）+ `src/document/state.ts:303`（恢复报文）。
- 机制：PM 轮引入的降级闸（防 journal 单行膨胀）把超限 pending 快照剥离为空串——降级后到下一次成功保存之间崩溃，恢复链拿不到该文档任何盘上副本；state.ts:303 恢复报文称「可从版本历史恢复」，但剥离窗内的新内容尚未进版本历史，**提示误导**。
- 附注：`pending.content` 全仓 grep 零程序性消费方（恢复链只消费 degraded 标记），剥离即真丢。
- 后果：单章 >256KB（超长章）+ 编辑后崩溃 = 新增内容丢失；红线「编辑永不静默丢失」在降级窗内失守——因触发需超长章+崩溃双条件，定 P2（与 PM 轮降级闸的既定取舍同源，但当时未披露「恢复提示误导」一面）。
- 修复方向：降级时保留 hash 截断头尾（或落旁文件），恢复报文如实改「最近内容未能保全」。

**R53-E-1 leads_book 缓存落盘无纪元终核——姊妹路径不对称（P1 候选降 P2；R52-E-1 同源先例）**

- 位置：`src/check/run.ts:470-590`（epochFp0 在 rebuild 前计算，L482-488——即 R52-E-1 修复产物）+ L567 computeLeadsBookFp（rebuild 后）→ L579 writeLeadsBookRed **无复核**；对照章级行 L728-735 有终核。

- 修复方向：照 L728-735 章级行口径补「写前纪元终核，不符则弃写」。

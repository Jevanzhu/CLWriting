### 5.1 P2×6（全部主评审亲验成立）

**R34D-1｜P2｜`src/ai/runner.ts:597-602`（对照 :566、:621）——重试分支硬记 usage=null，可重试截断流的真实消耗按 0 入账**
同函数 abort 分支（:566 `abortUsage`）与终态失败分支（:621 `failUsage`）均尊重 `GenError.usage` 载荷，唯重试分支 :599 `recordUsageSafe(null)`、:602 `usage: null`——:597 注释「失败响应无 usage，token 记 0」是 R31-1/R32-2 引入「截断随错带 usage」前的过期假设。三适配器对传输截断均随错上抛 usage（responses-adapter.ts:464 等），test/ai/provider/r32-error-usage.test.ts:66,159 已断言 `retryable:true` 且携带 usage——数据在适配器层可得、runner 层丢弃。影响：网关流中途截断且已见 usage → 可重试 NETWORK 错误 → 该 attempt 按 0 token 入 ai-calls.json 与 llm/call 事件 → 预算闸 token 口径与成本聚合系统性低估；同一次运行的记账口径取决于错误落在哪个分支。修法：重试分支复用 `e instanceof GenError && e.usage ? e.usage : null` 并更新注释（亲验：三分支逐行对照成立）。

**R34D-2｜P2｜`src/format/leads.ts:60,130-136`——履历畸形行被无条件折入上一条证据，账本静默损坏**
`HISTORY_ENTRY_RE`（:60）要求「非空证据（`(.+)$`）+ 章号后空格（`\s+`）」，不匹配的非空行经 R64-17 续行逻辑（:130 `else if (entries.length>0 && t!=='')`）折空格并入上一条证据（:135）。/tmp 实测：`- 第012章 埋下：`（空证据）解析后第 12 章声明整条蒸发、第 11 章证据被改写拼接；`第012章埋下：`（缺空格）、全角数字形态同触发。下次 writeLead 回写将改写后的证据物化。影响：防吃书闸对丢失声明失明（漏拦）、受损证据引文 grep 必不命中（假黄）；R76-19 空证据黄项只看已解析条目，看不见此路径；与 lead-updates.ts 对畸形行 warn 的口径不对称。触发面为人工编辑形态（系统自写侧恒产规范形）。修法：折入前判 `/^\s*-\s*第/` 前缀（形似条目但格式不符）不折入、上报或保真保留；正则 `(.+)$`→`(.*)$` 收编空证据（亲验：正则与分支逐行核对成立）。

**R34D-3｜P2｜`src/document/lead-finalize.ts:206,263-273`（配合 `finalize.ts:111`）——定稿闸锁内重读、履历回写却消费锁外预解析快照，同章编辑窗口丢作者账目**
`resolveLeadUpdateTargets` 在 prepareFinalize 于全部锁（布线锁/清单锁）**外**解析 `targets.updates`；`finalGateBlockers` 用锁内新读判定放行，`applyLeadUpdatesLocked` 却按陈旧 `targets.updates` 回写履历（:206 循环）并以 `residue` 清空主文件（:273）。R33D-4 在 :263 补的锁内复核**只查章标签（换章）不查内容（同章编辑）**——`账本推进.md` 在编辑器白名单内（files.ts:42 WORKDIR_EDITABLE）且 wiringFileLockKey 不覆盖它，作者在锁等待窗口（最长 ~10s）内删掉一条错误账目或改写证据措辞，闸按新内容放行、旧快照仍永久写入线索履历、作者新措辞被无痕清空。违反 ff-P1-1 自宣「闸看到的=回写要写的」。修法：`applyLeadUpdatesLocked` 持锁核心内对主文件/归档重新执行 `readChapterUpdatesForChapter`，以其结果生成履历条目与 residue，陈旧窗从 ~10s 缩到微秒级（亲验：锁内外数据流逐段核对成立）。

**R34D-4｜P2｜`src/document/manifest.ts:133-147,171-180` + `src/format/draft.ts:123-143`——清单「在册可读但零条可解析」被当合法空集，防覆盖闸三防线同时 fail-open**
`finalizedPathSet` / `finalizedChapterSetOfBook` 只区分「读失败（EACCES/EBUSY）→ null/undefined 全量兜底」与「零文档条目 → 空集」（M-2/M-13 口径，:170 注释自认「解析级损坏不重开」）——解析级全损（作者编辑器/云同步冲突把 `文档清单.jsonl` 存成 GBK 或截断，readManifest 静默跳过全部坏行）落入空集分支：assembleStatus `currentChapter=0` → AI 连写指向第 1 章 → `ensureChapterNotFinalized` 遍历零条目不拦 → saveDraft 覆盖已定稿第 1 章（有快照留底兜底，但作者已确认内容被静默替换）；下一次任何清单写把空表物理落盘，损坏变永久；healthCheck 无「清单在册零条目 vs 正文树有章」哨兵。正文区同类风险全仓有非 UTF-8 防线，唯独清单没有。修法：healthCheck 增哨兵（清单在册可读且 0 条目而正文树有章节文件 → 报红禁写）；清单原子写同步留 `.bak` 影子（亲验：三条调用链逐段核对成立）。

**R34D-5｜P2｜`src/studio/web-next/src/stores/chat.ts:465`——regenerate 的 parentSeq 取默认分支历史，与当前显示分支分叉，混合血统落库**
`regenerate` 调 `fetchChatHistory(bookName)`（不带 branchId，docstring 自述「拉默认分支权威历史」）；而 `switchBranch`（:429）带 `branchId ?? undefined`。多分支书：用户经变体组切到非默认分支 B → 点重新生成 → 本地截断 `messages` 与 `activeBranchId` 作用于 B 分支视图，POST 的 fork 基点 parentSeq 却是主线最后一条 user 的 seq → 服务端按主线上下文生成，前端显示「B 分支截断前缀 + 主线上文的回答」混合血统视图并以此落库（新 branchId），分支语义被破坏。调用口 handleRegenerate 对分支无门控；f6-regenbook-prereg.test.ts 的 mock 恰好只用单一 branchId，未覆盖此窗口。修法：`fetchChatHistory(bookName, activeBranchId.value ?? undefined)`，parentSeq 与截断/激活作用于同一分支 + 补非默认分支 regenerate 回归（亲验：与 switchBranch 对照成立）。

**R34D-6｜P2｜`scripts/corpus-commit.ts:79-82`——空列表分支 `process.exit(0)` 短路尾部退出码哨兵，语料门入库端假成功**
`if (all.length === 0) { console.log('无勾选条目…'); process.exit(0) }`（:79-82）先于文件尾部「拒绝/丢条不静默」哨兵（:118-123 `rejectedCheckIds>0 || failedExisting>0 || droppedExcerpts>0 → exitCode=1`）执行。当勾选行全部摘录解析失败（`droppedExcerpts>0`、`all=[]`）或全部落在被拒 checkId 节下时，退出码 0 且文案「无勾选条目」误导——与头注 R63-13/R63-11/R64-36「退出码标红让作者看见」宣称相悖。影响：作者勾选后手编候选 md 格式损坏 → 全部丢条 → 流水线视作成功，CI 回归门（corpus.test.ts）零新增，回归保护静默缺席。修法：空列表分支内先判 `droppedExcerpts>0 || rejectedCheckIds>0` 再定退出码，文案区分「真没勾」与「勾了但全解析失败」（亲验：短路序逐行核对成立）。

# harness 借鉴对照（对话面 + AI 底座）-调研-2026-09-29

- 版本：v1（对照结论，未拍板）。
- 状态：**研读底稿**——不作实施依据；任务状态与开放项以总览第三节为准。
- 定位：对 DeepSeek Harness（下称 harness）的**对话面**与 **AI 底座**做源码级对照，产出「可借 / 不借 / 我们更强」三面结论与优先序，供后续立设计档时取用；本文不替代设计文档，也不代表任何决策。
- 证据基础：本地源码级参考仓 `Dev/参考项目/deepseek-harness`（`.gitignore:29` 忽略，全本地零入库；版本 `0.2.0-rc.2`，commit `639ed01539`，与本机安装版同版本）。行数统计**含测试**。四条吃重论断经实读抽验（见 §二.3、§三.3 锚注）。

## 一、结论摘要

1. **对话面可借，但只借交互法则与投影纪律，不借框架**——他们对话呈现约 3.8 万行（React + Lexical + Cordis），我们整个前端才 43478 行；框架层不可移植（§二.3）。
2. **AI 底座比对话面更值得借**——同为 TypeScript 后端逻辑，无跨框架障碍；可借项集中在法则与小函数，而非 15 万行量级的包体系（§三）。
3. **我们有三处已强于他们**：凭据管理（KEK/DEK 信封 + OS 绑定 vs 其明文 YAML）、成本可见性（pricing/cost-stats/token-calibration 无对应物）、跨 provider 换网重发（他们明确无跨 provider 故障转移）。三处均不借（§三.4）。
4. **最高性价比是三条底座法则**：审批 fail-closed + 守卫单调、终态/取消原因闭集、事件日志 surface/log-only 二分（§三.2）。
5. **一个被低估的方向**：我们 review 链已声明 `parallel_subagents` 能力却因宿主不支持而降级为顺序三审（`src/review/contract.ts:325`）——这正是子代理模型的真实落点，不是"为架构而架构"（§三.2 C 档）。
6. 两处治理事项见 §五。

## 二、对话面

对照面：输入区（composer）+ 消息流，外加 dock 浮窗外壳。我方实现为 `src/studio/web-next/src/components/panels/chat/ChatComposer.vue`（裸 textarea）、`ChatMessages.vue`（纯文本消息流）、`src/studio/web-next/src/composables/useChatComposer.ts`。

### 2.1 差距实况

- **草稿模型**：他们 `SessionInputShell` 为每个 Session 持有一个 Lexical editor（`packages/client/ui-conversation/src/client/input/editor/runtime.ts`），草稿是结构化文档，故引用 chip 可做原子 decorator 节点、slash 命令可做行首高亮。我们是纯字符串 textarea。
- **输入框形态**：我们是固定 2 行 + `min-height` 56px（dock 档 70px）+ `resize: none`，无自动增高、无 max-height（`src/studio/web-next/src/components/panels/chat/ChatComposer.vue:200-212`）。
- **提交语义**：他们有 `input/submission-policy.ts`（86 行）解析 Queue/Steer 投递模式，Enter 与主发送按钮共享同一手势，Ctrl/Cmd+Enter 走互补模式；我们只有 Enter 发送 + Shift+Enter 换行（`src/studio/web-next/src/composables/useChatComposer.ts:155-163`）。
- **运行中状态**：我们 `v-if="chatRunning"` 让 Stop 顶掉 Send（`src/studio/web-next/src/components/panels/chat/ChatComposer.vue:116-122`），运行中要发消息只能靠 Enter；`busy`（写稿编排运行）时 textarea 直接 `disabled`，连草稿都打不了（同文件 `:70`）。
- **队列可见性**：他们 QueueDock 逐条列出 next-turn 并带 Edit/Remove/Steer；我们只有一行 notice 文本（`src/studio/web-next/src/composables/useChatComposer.ts:134`）。**后端能力已存在**：`pendingChats` 队列、容量 10、超容丢最旧有通知（`src/ai/orchestrate/chat.ts:101-105`、`:133-155`）——缺的是只读投影接口 + UI。
- **消息渲染**：我们 `{{ msg.content }}` + `white-space: pre-wrap`（`src/studio/web-next/src/components/panels/chat/ChatMessages.vue:317`），全仓无 markdown 渲染依赖；回复里的加粗/列表/代码块以原始标记呈现。
- **输入触发**：他们 `/` 与 `@` 光标处分组候选菜单（`ui-input-trigger` 包）；我们输入框内无，`CommandPalette.vue` 是独立全局面板。
- **其他**：附件/拖放/图片整套我们为零；上下文用量圆环我们为零；Esc Esc 停止（其 `stopSequenceMs` 默认 500ms）我们为零。
- **滚动**：我们 rAF 节流 + 64px 距底阈值跟随（`src/studio/web-next/src/components/panels/chat/ChatMessages.vue:47-70`）做得不比他们差，但缺"回到底部"按钮。

### 2.2 可借（分档）

- **A 档·1.0 前可做（纯前端低风险）**：textarea 自动增高 + max-height；IME 组合期隐藏 placeholder；运行中 Send 与 Stop 并存（需重排 footer）；回到底部按钮。
- **B 档·1.0 后立设计档**：队列可见可控（需后端只读投影 + 单条删除）；提交手势策略（借 86 行等价物）；控制栏自适应测量（借 `skeleton/control-row-layout.ts`，39 行）；上下文用量圆环；`@章节` 引用与 `/` 命令触发（**纯文本插入档**，不上 Lexical）。
- **注意**：Markdown 渲染需新增依赖（`markdown-it`），涉及 `check:packaging` 门，建议压到 1.0 后而非首发前动。

### 2.3 不借 / 我们更强

- **不借**：Cordis 插件宿主、slot 注册体系、68 个 client 包、Lexical、附件与图片整套、多 target 隔离。理由：我们是**一库一助手、单 target、无第三方插件生态**；`src/studio` 下严检 grep 无任何槽位/插件注册基础设施，引进即付架构税。
- **我们更强，别换掉**：失败路径健壮性。按书失败草稿 stash（含改名迁移与清理，`src/studio/web-next/src/composables/useChatComposer.ts:21-46`）、幽灵气泡按 id 定位回滚（防切书后误弹历史末条，同文件 `:118-149`）、双入口并发守卫、IME Enter 让渡——这些是我们自己踩坑填出来的，成色不低于他们同类逻辑。
- **形态级判断**：他们对话面的成熟来自"**一份 append-only 日志 + 多个视图投影**"（Chat / Trajectory / Deliverables）。这一半对我们划算且基座已在（见 §三.2 A 档与 §四）。

## 三、AI 底座

### 3.1 体量对照

| 侧 | 规模 |
|---|---|
| harness 非前端叶子包 | ≈253 个（`packages/` 顶层 55 组） |
| harness 底座关键包（含测试） | `core/agent-loop` 2490 · `core/session` 3421 · `core/tools` 5798 · `llm/llm` 4122 · `llm-deepseek` 2806 · `llm-retry` 531 · `token-meter` 1471 |
| harness 底座组（含测试） | `compaction` 9607 · `context` 12737 · `session` 47922 · `subagent` 34747 |
| 我方 | `src/ai` 86 文件 / 15967 行 · `src/studio/server` 65 文件 / 15615 行 |

结论：不是"搬"的问题（量级 5–10 倍差），是"选点"的问题。

### 3.2 可借（A/B/C 三档，按性价比）

**A 档·低成本高确定性**

- **① 两条安全法则直接抄**。harness 的**审批 fail-closed**：`tools/pre-execute` waterfall 返回 `ask` → 走审批 seam，**无应答者即拒绝**（`packages/core/tools/src/index.ts:146` 原话 "approval support turns `ask` into denial"；处置逻辑 `:1500-1515`）；另有单调守卫 `ToolGuard`（同文件 `:724`）**只能 deny，不可被重排为放行**。我方确认闸现有 `pending Map<callId,resolve>` + 2 分钟超时 + `confirmTimedOut` 记账，但危险工具（`delete_chapter` 等）的闸应具备"无应答即拒 + 守卫只加严"这两条性质。
- **② 终态原因与取消原因收成类型映射**。harness 的 turn 终止原因由 `TurnEndReasonMap` 声明（默认 `completed` / `aborted` / `blocked` / `error` / `max-tokens` / `interrupted` / `forked`，并可经声明合并扩展；`packages/core/session/src/types.ts:201-232`），取消原因为受控联合（`user` / `parent` / `disposed` / `hook`，`packages/core/agent-loop/src/agent.ts:84-90`）。我方收尾判定散在 `src/ai/orchestrate/chat/turns-phases.ts` 三段（mask 分流 / max_tokens / 无工具完成）。对齐为类型化原因后，"这轮为什么停"可枚举、可断言、可审计。
- **③ 护栏收成单一策略层**。harness 对应物是独立 seam：`guard/timeout-policy`、`permission-presets`、`sandbox-policy`。我方值散在五处以上：`MAX_AGENT_TURNS=20`（`src/ai/orchestrate/chat/turns-phases.ts:74`）、`AGENT_DEADLINE_MS=30min`（`src/ai/orchestrate/chat/state.ts:20`）、`CONFIRM_TIMEOUT_MS=2min`（`src/ai/orchestrate/chat.ts:44`）、`DEFAULT_TIMEOUT_MS=600s`（`src/ai/runner.ts:132`）、chunk 挂起 60s（`src/ai/gen.ts:69`）、重试 3 次（`src/ai/retry-policy.ts:32`）。纯重构，且与 `CLAUDE.md`「默认值显式 resolve」同向。

**B 档·需设计文档，但正对我们已记录的隐患**

- **④ 重试/降级从"调用点内联"改为"事件监听"**。harness 的重试挂在事件上（`ctx.on('agent/request-error', …)`，`packages/llm/llm-retry/src/index.ts:243`），是横向策略而非各调用点内联。我方 `src/ai/provider/failure.ts:95-112` 是自查坦白书：`switch-provider` 与 `shrink-prompt` "只有 chat 编排层各接线一次"，"self-heal/spawn/rewrite 等非 chat 路径仍无消费者，runner 内该动作照旧同归终态"。同一决策表跨链路行为不一致，根因即策略内联。
- **⑤ 单一提示词组装点 + 可见性硬不变量**。harness 用 `agent/pre-step` waterfall 组装 system prompt，且提示词只经 `system/message` 历史传递、空渲染即清除；更强的是不变量：每次循环请求的消息必须与日志派生结果**序列化逐位一致**（`JSON.stringify` 比对），违反即报 `log-reconstruction desync`（`packages/core/agent-loop/src/invariant.ts:41-42`）。我方是两处镜像组装（`src/ai/prompts/chat.ts:53` `chatSystem()` vs 同文件 `:87` `visibleInjections()`），源码注释自述"任一侧改拼接源即破坏「模型可见 ⟺ 已记录」""抽样校验对 knowledge 通道失明"，且校验为 opt-in（`CLW_VERIFY_VISIBLE=1`，`src/ai/orchestrate/chat/turns-visibility.ts:33`）。目标是把可见性对齐从**抽样诊断**升为**可断言硬不变量**。
- **⑥ 事件日志 surface / log-only 二分 + 替换语义**。harness 信封含 `type/seq/time/data/ignorable/surfaceOp/sourceEventSeqs`：**surface 事件产生模型历史，log-only 不产生**；压缩产物不是改写历史，而是紧随其后一条带 `surfaceOp: replace` + `sourceEventSeqs` 的 `user/message`（`packages/compaction/compaction/src/types.ts:24-55`），`compaction/start|summary|end` 本身为 log-only。回放靠 surface op 折叠精确重建。可借参数起点：`thresholdRatio 0.8` / `headroomTokens 65536` / `retainRatio 0.16` / `compactionRetries 1`（`packages/compaction/compaction-basic/src/config.ts:20-23`、`:75`、`:105`）。我方痛点在压缩只覆盖 chat（`src/ai/prompts/compaction.ts:105`，失败 fail-open 回落硬截断）且**恢复相位必须全量读事件**（`src/ai/orchestrate/chat/restore.ts:71`、`:81` 明示不走尾读），长书启动 O(N)。本条是唯一会触及事件库 schema 的，最需先划边界。

**C 档·需求已在库，作为方向评估**

- **⑦ 子代理（隔离只读审查这一档）**。我方 review 链已声明 `capabilities.parallel_subagents`（`src/review/contract.ts:108`），宿主声明 `false`（`src/studio/server/api/review.ts:198`），故降级为**顺序三审**（`src/review/contract.ts:325`："当前宿主不支持并行独立 subagent，降级为顺序三审"）。harness 对应物：`maxDepth` 默认 1 / `maxActiveSubagents` 默认 8、逐子 `toolFilter.allow/deny`、`delegationDepth` 单调不可降（`packages/subagent/subagent/src/index.ts:202-203`）。对我们有用的不是"多代理并行"口号，而是**独立上下文 + 只读工具集 + 结果回主链**：既提高三审独立性，也减轻主链上下文占用。大件，单独立项评估。

### 3.3 不借

- Cordis 插件宿主、9 万行级 `session`+`subagent` 组、24 个 `tool-*` 包、MCP、ACP、sandbox——我们无第三方工具生态，也不执行不可信代码（无 bash 工具）。
- **他们的"没有 max turns"**（`packages/core/agent-loop/src/agent.ts:390-395`：只要 inbox 还有排队项就开新轮；`packages/core/agent-loop/src/constants.ts` 全文件仅一项并行上限常量，无轮数帽）。我方 `MAX_AGENT_TURNS=20` + deadline + 确认 + 预算四闸更保守，方向正确，勿倒学。
- **并行工具上限 10**（`packages/core/agent-loop/src/constants.ts:6`）。我方工具串行派发是刻意的：写文件有顺序依赖，并行只引入竞态。

### 3.4 我们更强（勿顺手换掉）

| 面 | 我方 | harness |
|---|---|---|
| 凭据 | KEK/DEK 信封（HKDF-SHA256 + AES-256-GCM）+ Electron safeStorage/DPAPI 的 OS 绑定，`VaultOsKeyMissingError` 防降级（`src/ai/provider/vault.ts`） | `credentials-local` 为**明文 YAML**（`.credentials.yaml`，靠 0700/0600 权限），非加密、非 keychain |
| 成本可见性 | `pricing.ts` 四档计价 + `cost-stats.ts`（llm/call × 价格表）+ `token-calibration.ts`（chars→token 系数拟合，剔 chat、n≥30） | 无对应成本报表包 |
| 跨 provider 换网重发 | `switch-provider` 恰一次最小版接线（仅 chat 链，覆盖面待补） | **明确无跨 provider 故障转移**（`llm-retry` 仅指数退避 + 抖动，初值 500ms） |

## 四、总优先序与落点建议

1. **1.0 首发前不动 AI 底座**——A/B/C 三项均落在"生成正确性"路径（重放、可见性、确认闸），风险高于 UI 改动一个量级，且无一是首发阻塞项。
2. **1.0 后**：A 档三项（尤其 ①②）可并入任意批次顺带做，不值得单独立项；B 档三项各需设计文档（`03-设计` → 评审 → `02-执行`）；C 档先出评估再定。
3. **形态级可选方向**：把"一份 append-only 日志 + 多视图投影"补齐——对话 / 轨迹 / 产物三视图共用同一投影纪律。我方基座已在（`CLAUDE.md`「模型可见 ⟺ 已记录」、按书事件库、`GET /api/books/:name/audit`、`AuditView.vue`、`src/ai/trace.ts`），缺的是投影多样性；且能顺带解决对话区"工具过程行永久占屏"。B 档⑥ 是该方向的必要条件。

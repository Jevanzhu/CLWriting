# 多库多窗（同机多库并排）-设计方案-2026-09-29

- 版本：v2（D1-D7 已拍板定案 2026-10-02）。
- 状态：**已实施完成**（2026-10-02 L2 全绿：vitest 1292 档 / 8817 通过；e2e 34 spec / 55 用例；tsc + vue-tsc + eslint + 五 check 净）——任务状态以总览第三节阶段行为准。
- 定位：同机同时打开多个书库（并排多窗）的形态选择与施工设计。含现状核查（实核，锚 file:line）与四组实测记录（§二.7）。
- 命名说明：本文「多库多窗」指**同机同账户下多库并排**；「同事各机同库（NAS/SMB 共享）」现状已可用，见 §二.6 与 §六.2，不作本设计实施面。

## 一、背景与目标

### 1.1 目标

- 同机同时打开 N 个书库，各自独立窗口、独立工作区，互不干扰地编辑。
- 保持既有单库体验逐位不变：只开一个库时，用户感知与现状完全一致（含切库、书架窗、书库管理窗、退出语义）。
- 同一书库不得被两个实例同时打开（正文双写 = 语义层冲突，非文件撕裂，无锁可救）。

### 1.2 非目标（不做面）

- 跨机协作：不合并各机对话史/审计事件库（现行口径维持「对话史/审计不跨机」）。
- 单进程内的窗口间协作（跨窗拖拽、统一标签页）。
- 跨机同库的语义层冲突防护（各机各自的内存态，最后保存者覆盖）——现状即如此，本设计不改变。
- 移动端/多用户账户体系。

## 二、现状核查（实核）

### 2.1 单实例锁（两道）

| 机制 | 落点 | 作用域 |
|---|---|---|
| Electron 原生锁 | `src/desktop/main.ts:117` `app.requestSingleInstanceLock()` | **userData 目录**（实测确认，见 §二.7） |

### 2.2 窗口与生命周期（单主窗假设）

### 2.3 库定位与切库

- 启动定位：bootstrap 内定出唯一 `workDir`（`main.ts:293` 起）——持久化 `current` > `findWorkDir(cwd)` > welcome。**主进程不解析 `--dir`**（该参数目前只到 server 子进程，见 §二.4）。

### 2.6 同事各机共享书库（现状已可用，非本设计实施面）

- 库内锁（books.jsonl / book.yaml / manifest / 文档保存）天然跨机互斥；事件库各自落在本机 userData，**不跨机合并**（总览「现行口径」已明载）。
- 已知限制：providers/全局偏好每机一份（各自配置）；同库跨机同时编辑同一章为「最后保存者胜」，无防护（现状即如此）。
- 体系缺口（评审已登记）：多开/并发用户形态无系统性测试位——e2e 单 workDir 串行。

### 2.7 实测记录（本次，2026-09-29）

| # | 实验 | 结果 |
|---|---|---|
| 1 | 同 userData 起第二实例 | Electron 锁 `false` → 进程退出，不进 ready |
| 2 | 异 userData 起第二实例 | 正常起：各自 fork server，端口随机且互异（实测 6074 / 2606），各开各窗 |
| 3 | 共享 userData + 独立 `sessionData` 的双 Electron 实例 | **可同时运行**；运行后共享 userData 根**零写入**——Chromium 全部写面（Cache / Local State / Preferences / Session Storage / Network / DIPS / GPUCache 等）落在 sessionData |
| 4 | 共享 userData 起两个 node server（`server-main.js`，两个不同库） | 各自 ready（实测 5395 / 5398），共享 userData 仅写出 `logs/`；日志文件 4 行全可解析（小样本未见交错，长行撕裂风险仍在，登记见 §四.5） |

**结论**：Electron 锁的作用域 = userData 目录（实测 1/2）；`sessionData` 可把 Chromium 写面整体搬走（实测 3）；server 侧「一库一进程」形态现成可用、数据面无冲突（实测 4）。

| # | 缺口 | 现状 |
|---|---|---|

| G4 | `logs/app-YYYYMMDD.jsonl` 同 userData 下两进程 append 同文件 | 小样本未观察到撕裂（实测 4）；长行（>PIPE_BUF）理论撕裂风险 + 7 天清理正则只认 `app-*.jsonl`，分目录即两全 |

## 三、决策定案（D1-D7 已拍板）

### D1 形态：一库一实例（多进程）vs 单进程多主窗

**定案：一库一实例（多进程）**。理由：① server 侧现成参数化（§二.4），零改造；② 进程隔离天然（任务闸/SSE/worker/崩溃）；③ 服务端与库内的跨进程锁体系正是为此而建（§二.5）；④ 主进程改动收敛在「锁 + 状态分片 + 入口」，不动 `handleTrusted` 与 IPC 上下文解析。

- 落选（单进程多主窗）：需把 `wins.mainWindow` 单引用（25 处）改多实例、`serverManager` 改 Map、菜单动作按焦点窗路由、IPC 上下文按 sender 解析库（当前 handler 取模块级 `currentWorkDir()`）、退出语义改「全窗关完才退」。改动面与风险显著更大，收益仅省内存。
- 落选（维持现状/搁置）：保留「单实例单库 + 切库重启」。

### D2 实例 key 与 Electron 锁的复用

- **定案**：`instanceKey = hash(平台折叠后的库路径)`（win/mac 折叠、linux 全等），welcome 态用固定 key。
- 关键收益：**Electron 原生单实例锁自动实现「同库单实例、异库多实例」**（其作用域就是 userData 目录，实测 1/2），`second-instance` 聚焦体验现成保留，`sessionData` 隔离自动获得。
- 约束：key 必须在 `app.setPath('userData')` 之前算出 → 库路径解析要**同步、零磁盘 IO** 地提前。故**不得**用 `bookHash`（`events/store-migrate.ts:45`，win32 走 `trueCasePath` 逐段 `readdirSync`，失联网络卷会同步冻结主进程——正是慢盘面加固要防的形态）。平台折叠已足够覆盖盘符/大小写漂移。
- 库路径来源：新增主进程参数 `--dir`（先例：`--book` 已由主进程解析，`desktop/initial-book.ts:22`）> `workdir.json` 的 `current` > `findWorkDir(cwd)` > welcome。前三者均为字符串运算，不探测目录。

### D3 目录分工：应用级共享根 vs 实例目录

- **定案**：Electron 的 userData 改为 `<home>/instances/<instanceKey>/`（`<home>` = 现 `%APPDATA%/CLWriting`），同时把「应用级数据根」显式下发给 server 子进程（`--user-data <home>`，与 Electron 自身 userData 解耦）。

| 数据 | 落点 | 说明 |
|---|---|---|
| Chromium 会话/缓存 | 实例目录（自动） | 实测 3：根目录零写入 |
| `window-state.json` | 实例目录 | 每库各记自己的窗口几何 |
| `logs/` | 实例目录 | 消解 G4；7 天清理正则不变 |
| `app-instance.lock` | 实例目录 | 守卫随 key 走（提权双开防线保留） |
| `providers.json` + vault / `global.json` / `prompts/` | 共享根 | 应用级，跨库共享（与「双库并存」设计意图一致） |
| `clwriting/session/*.db` | 共享根 | 按 bookHash 分库，天然并存 |
| `workdir.json` / `studio-token.json` | 共享根 | 库注册表与应用级 token |
| **不可迁移项** | 根上旧 Chromium 缓存目录 | 改后成孤儿，留无害（清理可选，非必需） |

- 迁移面：**零数据迁移**——共享根即现存 `%APPDATA%/CLWriting` 原地不动；实例目录为新增。唯一例外：根上旧 `window-state.json` 可一次性读入首个实例（或丢弃重记）。
- `CLW_SMOKE_USER_DATA`（`main.ts:102`，e2e 隔离钩子）语义改为覆盖 `<home>`，实例目录嵌套其下。

### D4 同库重入与「切库到已开库」

**定案：聚焦那个实例并关闭本实例**（同库第二实例拿不到 Electron 锁 → 聚焦首实例，现状语义原样保留）。

- 该行为在 D2 落地后由原生锁自然涌现（零新增代码）：切库重启的新进程算出目标 key、拿不到锁即退出，Electron 把持锁实例的主窗拉到前台——与「切库 = 切过去」的直觉语义一致，且切库本就会关掉当前窗。
- 落选：(a) 提示「该库已在其他窗口打开」并放弃切库（需新增锁探测 + 对话框，多一次反悔机会）；(c) 允许同库双开（**不可取**：正文双写语义冲突）。
- 附带调整：切库链的 `app.releaseSingleInstanceLock()`（`workdir-controller.ts:489`）在新形态下不再必需（新实例落在不同 userData 目录），保留为无害或删去，实施时定。

### D5 打开新库的入口

**定案**：菜单「文件 → 在新窗口中打开书库…」+ 书库管理窗 recent 项逐条「在新窗口中打开」。实现为 spawn 新实例（打包态 `process.execPath`；dev 态需拼 electron + app 路径——先例 `scripts/electron-smoke.mjs:104-106`）。

- 入口语义定案：双击/快捷方式无参启动维持「上次的库（current）」；无参且该库已开 → 聚焦（现状语义，原生锁自然涌现）；欢迎页不加「打开另一个库（新窗口）」入口（菜单 + 书库管理窗已够）。
- 书架/书库管理子窗：随实例走，语义不变（各库各有自己的书架）。

### D6 跨进程 RMW 补锁清单

- **定案：G1 + G3 同批补**（两者都在共享根，多库并排下并发写是常态路径）。G1（`global.json`）按 `providers.json` 先例（异步孪生 `acquireCrossProcessLockAsync` + 既有 revision 乐观锁——补锁治丢更新，revision 治用户可见冲突）；G3（`workdir.json`）同批补锁治 `recent[]` 丢条目。G2 因同库双开已被 D2/D4 拦降为「CLI+GUI 并存」旧面（现状已存）、G5 随通道恢复批处理并登记，均不在本批。

### D7 观测与降级

- **定案**：日志分目录（D3）后，`logs/` 按库可读；新增启动行记 `instanceKey` 与库路径（诊断多实例问题必需）。
- 不新增设置开关；不做实例数上限（内存由用户自控；建议文档口径「2-3 个库并排」）。

## 四、施工设计（按 D1-D3 定案）

### 4.1 启动顺序（改造后）

1. 主进程顶层：解析 `--dir` > 读 `<home>/workdir.json`.current > `findWorkDir(cwd)` > welcome（**同步完成；不对库目录做任何探测**，`workdir.json` 为本地小文件直读）。
2. 算 `instanceKey`（平台折叠 + hash）。
3. `app.setPath('userData', join(home, 'instances', key))`（首次自动创建；**不再需要**显式 `setPath('sessionData')`——Chromium 写面随实例目录走，实测 3）。
4. `CLW_SMOKE_USER_DATA` 若设，覆盖 `<home>`（实例目录嵌套其下）。
5. `initLogging({ logsDir: join(userData, 'logs') })`（随实例目录，G4 消解）。
6. `requestSingleInstanceLock()`（现语义：拿不到 → 聚焦/退出）+ `acquireAppInstanceGuard(userData)`（提权双开防线保留，路径随实例目录）。
7. whenReady → bootstrap：库定位**复用**既有 resolved 值（不再二次定位）；`serverManager.start({ userDataPath: <home>, workDir, ... })`——**server 的 `--user-data` 与 Electron userData 解耦**（本设计的核心一行）。
8. 其余不变：fork server（`--port 0`）→ 建主窗 → loadURL。

### 4.3 与既有能力的复用（不新造）

- 跨进程锁：`fs/cross-process-lock.ts`（含异步孪生、stale 接管、续期）。

### 4.4 施工补记（拍板随批）

- **`app.relaunch()` 默认继承当前 argv**：切库链必须清掉 argv 里的 `--dir`（及值）——`--dir` 在解析序里优先级最高，不清会把切换目标顶回旧库（切后走 `workdir.json` current 才是新库）。实现取 `app.relaunch({ args: 过滤后 argv })`。
- D4 聚焦路径下，第二实例在锁判定前已落数行启动日志到目标库实例目录（与 G4 同源的微量并发 append）；实施时定是否延后日志初始化（现顺序：initLogging → 锁判定）。
- **测试隔离事故与守卫（2026-10-02 实录，随批入册）**：`workdir.json` 解析改走共享根后，`test/desktop/workdir-read-failure-write-guard.test.ts` 只假件了 electron（临时 userData 进的是 `app.getPath`），`storePath()` 实际落到真实 `~/Library/Application Support/CLWriting/workdir.json`——用例写盘把作者真实书库指针覆写（`current` 被写成测试值）。已按 `setCurrent` 语义反推逐条还原真实档（`current`=真实库；`recent` 仅余另一库条目），并给该档补 `user-data-path` 假件；另加静态门 `test/desktop/user-data-isolation.guard.test.ts`：凡**真实导入** `main`/`ipc`/`lifecycle`/`workdir-controller` 的 desktop 测试，必须假件 `workdir-controller` 或 `user-data-path`（或引 `main-fixtures`），否则红——「测试绝不写真实用户数据」从纪律升为机器门。
- **e2e 落地**：`test/e2e/multi-instance.spec.ts`（挂 release 门，先例 `packaged-app-smoke`）：`--dir` 异库两实例并存且各显其库（cwd 取中立目录，防 cwd 兜底假绿）+ 同库第三实例起即退（exit 0）且持锁实例不受扰 + 实例目录按 `libraryInstanceKey` 真实现派生（期望值不手抄）+ 启动行「来源=arg」落实例日志 + 干净退出后 `window-state.json` 落实例目录、共享根不留。spec 顺序快照随批重拍（33 → 34 spec）。
- **L2 收口实测（2026-10-02）**：vitest 全量 1292 档 / 8817 通过 + 8 跳过（140 秒）；`tsc --noEmit` 与 `typecheck:web-next` 净；`eslint --max-warnings 0` 净（含 `registerIpc` 守卫链抽单源）；五 check 全绿；e2e 全量 51 通过 / 4 跳过（40.8 秒），release 门三门（本 spec + `packaged-app-smoke` + `release-smoke`）同跑 4/4 绿——启动链改动对打包态冒烟的回归面已覆盖。

## 五、测试与验收

- **单测（L1）**：`instanceKey` 派生（折叠/异库异 key/同库同 key/大小写漂移同 key）；`global.json` 补锁后的并发写不丢键（双写交替）；`workdir.json` 补锁后 recent 不丢条目；日志目录分片路径。
- **e2e（新增位，已落地见 §4.4 末条）**：两个实例（不同库、共享 `<home>`）并行启动 → 各自 ready、各自可编辑保存 → 互不干扰；同库第二实例 → 退出且首实例不受扰。**注意**：e2e spec 顺序受 `check:counts` 快照门约束（`test/e2e/spec-order.snapshot.txt`），新增 spec 须走守卫两步闸重拍。
- **不变量（验收判据）**：① 单库用户路径逐位不变（启动/切库/退出的可观察行为）；② 同库不可能双开（含提权差异）；③ 应用级配置（providers/global）跨库共享且并发写不丢更新；④ 任一实例崩溃不影响它实例。
- **L2 终门**：vitest 全量 + tsc/vue-tsc + eslint + 五 check；e2e 必跑（动前端与端点链）。

## 六、风险与不作项

1. **内存**：每实例一套 Electron 渲染进程 + server 子进程。2-3 库并排可接受；对外口径不承诺 N 库（D7）。
2. **同库跨机**（同事 NAS 场景）：本设计不改变现状——库内文件锁保文件完整性，「最后保存者胜」的语义冲突无防护，对话史/审计不跨机。若作者要更严口径，另立专项（需 CRDT/占位锁级别的设计，远超本方案）。
3. **切库链回归面**：`relaunch` + 锁释放 + 回滚基线（`workdir-controller.ts:471-500`）是既有精细区，改动集中于此，须以单测 + 手工走查双证。
4. **潜伏项 G5**（os-kek 通道恢复）：登记在案，随通道恢复批一并处理，不在本设计实施面。
5. **库路径大小写/规范化**：key 用折叠 hash 而非 `trueCasePath`（性能约束，D2），残余为「同一物理目录的两种拼写」在极端形态下可能派生两个 key——影响面仅「同库双开防线」，届时由夹持（用户手工输入路径）触发概率极低，登记。
6. **启动链同步解析的两处残余**（实施随批登记）：① `findWorkDir(cwd)` 在启动链顶层同步执行（key 须先于 `setPath`，不能等异步预探）——cwd 位于失联网络卷时会冻启动；双击/快捷方式启动的 cwd 恒本地，实际不可达概率极低（bootstrap 原链的异步预探防线保留，仅启动 key 解析这一前置镜像无预探）。② 「实例 key 按启动解析的库派生、bootstrap 实际采用另一个库」形态（current 失效/不可达 → 回落 `findWorkDir(cwd)` 发现库）——该会话的「同库单实例」防线降级，已 `log.warn` 留痕（`main.ts` bootstrap 尾部）。

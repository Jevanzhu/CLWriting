# 分类

每篇笔记的类别由**路径**决定（`{lifecycle}/{class}/`），类别集合是封闭的，门禁拒绝其他目录。要新增一个类别，必须同时改门禁源码里的常量与本文档——这是刻意的摩擦。

目录名由语料的主语言拼写（`.agents/notes/harness.json`）：英文语料用冒号左边那列，中文语料用右边。**不混用**——一棵树里出现另一种拼写，门禁会点名期望的名字，并指出那是另一语言的说法。

## 六个类别

| class | 覆盖什么 | 判据 |
|---|---|---|
| `feature` · `功能` | 面向用户或模型的新能力 | 让某个东西**变得可能**了 |
| `bug-fix` · `缺陷修复` | 修正缺陷，或补上事故复盘暴露的缺口 | 让某个错误**不再发生** |
| `simplification` · `简化` | 删除代码、行为或表面积，不新增能力 | 可观察行为**没有变化** |
| `architecture` · `架构` | 关于**交付源码**的结构决策：包之间如何关联、运行时的词汇是什么 | 改的是我们 ship 的东西 |
| `process` · `流程` | **围绕**代码的工具链、策略或工作流：门禁、包管理器、vendoring | 改的是我们**怎么干活** |
| `testing` · `测试` | 测试基础设施与测试策略 | 改的是**怎么验证** |

## 边界怎么判断

**architecture 与 process 的分界**：架构管交付的源码；流程管外围的工具与工作流。一个改动如果只影响开发者机器的行为而不影响程序运行，那是 process。反过来说，「CI 里加一个检查」是 process，而「检查这个行为的那个运行时守卫」是 architecture。

**为什么没有 refactor**：它与 `simplification` 重叠，而后者的判据——「可观察行为是否改变」——已经足够区分。多加一个类别只会让归类变成争论。

**feature 与 simplification 的分界**：看是否让新的行为变得可能。把两个内部函数合并是 simplification；让用户能做一件以前做不到的事是 feature。即使 feature 的实现删掉了更多代码，它还是 feature。

**bug-fix 与 feature 的分界**：文档说应该 A、代码做成了 B，修成 A 是 bug-fix；文档也说 B 但 B 不对，那是 feature（行为的有意改变）。仓库里判断不了的时候，看 issue 是怎么报的。

## 类别记录主导意图

一次改动常常同时包含功能、测试、文档和清理。类别记录的是**主导意图**，附带的部分不改变它：一个 feature 顺带补了测试、改了文档、升了依赖，它仍然是 `feature`。

判断方法：如果只能保留这次改动的一部分，保留哪一部分仍然让它有意义？那就是主导意图。

## 一个决策只有一个 owner

同一机制已经有一篇笔记时，**更新它**，不要新建。重复的笔记会让事实分叉：两篇都说自己是权威，读者不知道该信哪个。

判断重叠看的是**机制**而不是标题措辞。「缓存失效策略」和「为什么缓存会陈旧」大概率是同一个 owner。

真的推翻了结论，才新建一篇，并在两篇里互相链接：
- 新笔记指回旧的：说明它取代了什么。
- 旧笔记在还没被完全合并前保持不动——**不要**把它改写成相反的意思。

## 类别与文档层级的关系

class 描述的是**决策的性质**，不是文档的位置。一篇 `process` 笔记完全可能描述一个只作用于 `docs/` 目录的门禁；一篇 `architecture` 笔记可能讨论一个尚未落地的包结构（此时它在 `proposed/`）。

文档层级（哪个事实住在哪个文件）属于 `project-harness` 的职责。

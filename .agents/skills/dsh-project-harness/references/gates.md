# 门禁图

## 门禁是数据

每个门禁是一个声明式的对象，不是一段脚本：

```
{
  id, label, command, args,
  needs: [...], after: [...], env, quick, allowFailure
}
```

这样做的直接好处是：图可以被**静态校验**。运行前就能拒绝未知依赖、重复 id、自依赖、依赖环。一个跑到一半才发现依赖写错的流水线，比一个启动就报错的流水线贵得多。

## needs 与 after：这个区分是核心

两种依赖，语义完全不同：

- **`needs`** — 硬依赖。前驱失败时本门禁**跳过**，并记录原因。用在「读半成品会报假错」的场景：覆盖率检查不需要在构建失败后跑。
- **`after`** — 只排序。前驱无论成败都等它落定，然后本门禁**照常运行**。用在「并发写入会互相破坏」的场景。

上游的真实用例值得记住：一个 HMR 测试会启动 dev server，从而重写共享的构建产物目录；同时有若干检查在读那些产物。这里需要的既不是「并行」（会撕裂）也不是 `needs`（读产物的检查即使写入者失败也应该跑，否则丢失诊断信息）。`after` 恰好表达了这个意思：等它结束，但不管它结果如何。

**判据**：问「前驱失败时，我这个门禁的结果还有意义吗」。有意义用 `after`，没意义用 `needs`。

## 跳过必须显式记账

被跳过的门禁在汇总里是 `skipped`，并且带一条原因（`required gate build did not pass` / `fail-fast: an earlier gate failed`）。

**为什么值得单独设计**：`skipped` 和 `passed` 都是「没报错」，如果不区分，一个因为依赖写错而从未运行的门禁会伪装成绿灯。这是门禁体系最危险的失败模式——系统看起来很绿，但什么都没检查。

因此聚合判定要**把 skipped 算作失败**。上游的聚合检查里有一句 `contains(needs.*.result, 'skipped')`，正是为此。

## fail-fast 的正确语义

失败即停能省掉大量无谓的机器时间（一次红灯的流水线不必把剩下的门禁全烧完）。但实现上有两个必须守住的细节：

1. **已经在跑的不要杀。** 杀掉它们会丢失诊断输出，且可能留下半写状态。
2. **没启动的记为 skipped + 明确原因**，不是静默消失。

上游还遇到过一类棘手情况：agent 捕获了终止信号然后以 0 退出——按退出码判断会被当成成功。所以中止路径的记账不能只看退出码。

## allowFailure

有些门禁的结果值得看，但不该阻塞合并（平台差异、诊断性检查、观察期的新门禁）。

用它的纪律：
- 允许失败的门禁**仍然受 `needs` 约束**——如果它的前驱失败，它照样跳过。允许失败不等于允许在缺前提时跑。
- 不要用 `allowFailure` 掩盖不稳定的检查。那是把「测试不可靠」伪装成「策略选择」。修不稳定性，或者删掉那个检查。

## 聚合模式

门禁按用途分组，命名为模式。上游有十几个，但只需要理解三类：

- **quick** — 无需构建，秒级反馈。本地高频循环用这个。设计目标是**能在等一杯咖啡的时间里跑完**。
- **primary / check-all** — 全量，CI 与「提交前彻底自查」用。
- **平台矩阵** — 多操作系统、多运行时版本。

分支保护**只要求一个稳定的聚合检查名**，不要在分支保护里枚举具体门禁或矩阵腿。上游的注解写得很直白：矩阵腿的名字会随运行时版本演进，枚举它们意味着每次升级引擎都要改分支保护规则，而漏改的后果是保护静默失效。

**预置的聚合名以门禁表的 `MODES` 为准**，模板只承诺其中两个入口：秒级的一档，与全量的一档（`check-all`）。全量档是**扩展点**——把构建、测试、平台门加进它；它对其它模式必须是超集，这条由 `run-gates.spec.ts` 钉住，因为「全量」写在名字里，是一个承诺而不是一句描述。同一条纪律还有一面：文档里以命令形态写下的模式名必须真的存在，模板是采用方的 standing orders，写进去的命令就是承诺——`check-all` 曾在四处被引用而表里没有它，就是这条对照存在的原因。

## 并发上限

本地与 CI 要给不同的上限，且本地通常要**更小**。反直觉但有理由：多个文档门禁各自会构建完整的编译程序，不限并发会让大机器用内存爆炸换取秒级的墙钟收益。

CI 侧的并发通常由机器核数推导，并留出一部分余量给不能被占满的环节。

## 让门禁在脏仓库上也能开张：债务台账

**这是把门禁装进已有项目的关键，不是可选项。**

一个门禁如果只在干净仓库上可用，那它对绝大多数真实仓库毫无价值。把 link 检查装到一个三年历史的仓库上，它第一天会报出两百条死链——**而它没有能力区分哪条是历史遗留、哪条是你这次改坏的**。结果是门禁被关掉，或者被加进 `allowFailure` 永久静音。

债务台账解决这个区分。`scripts/harness/baseline.json` 记录「这个门禁允许报告哪些违规」，运行时把违规切成两半：

| | 含义 | 后果 |
|---|---|---|
| 在台账里 | 历史遗留，已接受 | 打印计数，不阻塞 |
| 不在台账里 | 本次新引入 | 门禁失败 |

三条规则让它只能变小：

1. **默认拒绝扩张。** 台账已有条目时，`--write-baseline` 遇到新违规直接报错退出，除非显式 `--accept-new`。这条最重要：它让「记录第一天的债」和「放过一次回归」变成命令行上两个不同的东西，评审时看得见。
2. **陈旧条目每次运行都报告。** 修掉债之后会打印「N 条台账条目已不再匹配任何东西」，催你重记一次把它删掉。
3. **记账是显式动作。** 只有 `--write-baseline` 写文件，日常运行只读。

**键必须对无关编辑稳定。** link 门禁用 `路径|链接目标`；行号不行，因为任何一次上方编辑都会让整个台账错位、全部条目变成陈旧。wrap 门禁用 `路径|上一行文本 ⏎ 下一行文本`——反过来说，**改动那段文字就会让它重新暴露**，这恰好是应该顺手合并的时候。

**这是把棘轮（ratchet）用在债上。** 和文档预算、覆盖率下限是同一个模式：从实测值起步，只保证「只能变好」。任何「立刻变好」的初始状态都意味着红灯，红灯意味着门禁会被绕过。

## 宣称值：不自己更新，就让门禁去对账

门禁体系有一个反身失效：**门禁自己的数字也会过期**。「本仓有几个 skill」「这个聚合跑几道文本门」写进文档的那天是对的，下一次改动就未必——而不会有人为了一句话去重算一遍。自律在这里不成立，恰恰因为写的时候是对的：它后来错着，没人知道。

把宣称变成可核的对账：一条**宣称 = 数字（或清单）+ 源头命令**，住在 `scripts/harness/doc-claims.manifest.json`，由 `verify-doc-claims.ts` 每次比对。两类：

- **count** — 命令打印一个整数（或用 `byLines` 数它的非空输出行），文档里写着同一个数；`expect` 可以表达下限（`atLeast`）与上限（`atMost`）。
- **list** — 命令每行打印一项，文档必须逐项提到。`skills/` 下新增一个目录而 README 还停在旧清单，这里就红。

**`atLeast` 是把「只增不减」变成机器可判的形态。** 口号背不出来的那一刻没有代价；写成「文档说 10，源头至少测到 10」，删掉一门就红。文档字数上限、覆盖率下限是同一族棘轮，区别只在方向。

三条纪律：

1. **同一事实只在一个地方写数值。** 同一个数字出现在 README 行、CI 步骤名、分支保护清单里时，只留一处是正本，其余指过来。CI 的步骤名曾经把门禁逐个列出来，加了一门它就静默少列一个——现在它只说「跑哪些见脚本」。
2. **数值的来源是命令，不是人。** 命令是 argv 数组（不给 shell 引号与平台差异留缝），以仓库根为 cwd 运行；人手上的数字就是下一次要对的账。
3. **这个门禁有意不挂台账。** 其它门禁可以用台账接受历史债，宣称值不行：**改一个错数的成本远低于记一笔错账，而台账会奖励「留着它错」**。账实不符只有两个正当出口——按源头改数字，或者删掉那句话。

**诚实边界**：能对账的前提是「源头是命令」。散文里的宣称（例如用中文标签列出门禁类别）没有机器可读的源头，标签与文件的映射本身是人的判断，只能留给评审。所以文档里不要手抄清单——**抄了就要给它一条命令**，给不出命令的清单迟早是错的。

## 写一个新门禁的检查表

1. 它会因为什么而失败？写一个会触发它的输入。
2. **跑一次，确认它真的失败了。** 没红过的门禁等于装饰。
3. 它读什么产物？读取者与写入者之间要有 `after` 或 `needs`。
4. 它该进哪个模式？本地循环能秒级跑完的进 quick。
5. 失败信息里有没有 `path:line`？没有的话，修到有——一条定位不到位置的报错会浪费所有人的时间。
6. 它需要构建产物吗？需要就别进 quick。
7. 它让某个数字或清单变得可核了吗？如果这条规则意味着文档里会写下数字，就给那个数字在 `doc-claims.manifest.json` 里配一条宣称。

## 入口判断与运行版本

门禁是 TypeScript 源文件直跑（靠 Node 的类型剥离），所以「Node 够不够新」直接决定门禁跑不跑得起来。下限的声明点是 `package.json` 的 `engines`，别处只引用它。

这里有一条必须知道的缝隙：**存在「能执行这些文件、但入口判断为假」的 Node 版本组合**，脚本于是正常退出 0 而一个检查都没跑。静默绿比报错危险得多——它长得跟通过一模一样，而且不留任何痕迹。

两道防线：

- 入口判断读路径，不读 `import.meta.main`。后者在足够新的版本上才有，旧版本上恒为假，正好落进上面那条缝隙。判据与版本区间写在 `harness-root.ts` 的 `isEntryPoint` 上（两个 skill 各持一份、逐字节一致）。
- `scripts/structure.spec.ts` 里的「每个随包发布的门禁都能真的跑起来」逐个启动 `verify-*.ts`，断言它至少打印自己的名字；找不到任何门禁也算失败。入口判断整片失效时，这条用例会红。

采用方要判断手上的 Node 够不够，看 `package.json` 的 `engines`；判断装的是哪一版 skill，看 `scripts/harness/version.json`。

## 已知的诚实边界

门禁证明的是**「在这个检查覆盖的范围内没发现问题」**，不是「没问题」。范围之外的一切——语义正确性、设计合理性、文档准确性——都不在任何自动化门禁的保证里。

写门禁文档时把这句话写进去。假装门禁能保证更多，会让评审人放弃他们本该做的那一半。

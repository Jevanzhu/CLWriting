# 代码评审

**这是判断指导，不是完整清单。** 清单让人以为打完全部勾就尽到责任了，而评审的价值恰恰在清单之外。

## 先做两件事，再看 diff

**一、核实 PR 的真实 base 和 head。** 不要相信 PR 页面上显示的范围——它可能已经过时，或者被 force-push 换过。用实际的 commit 引用去取 diff。

**二、跑一次变更范围报告。** 先知道这次改动触及了哪些层（源码、测试、文档、配置、生成物），再决定把注意力放在哪。报告只识别范围，不替代语义评审。

## 注意力排序

**正确性、生命周期、安全、被破坏的必需行为——先于风格。**

`一条有据可依的阻断项胜过一串 nit。` 反过来也成立：十个格式建议凑成的评审意见，会让作者看不出哪个真的需要改。

## 阻断项

**一、新写的散文需要语义评审。** 自动化检查无法建立准确性——链接能通、格式合规，但说的可能是错的。

**二、文档与代码在同一个 diff 里。** 配置项、默认值、错误信息、协议字段、事件、公开行为改了，对应的 README 与 JSDoc 必须在同一个改动里跟着改。分散的文档更新不会发生。

**三、核心类型与契约的同步。** 类型或接口改动要连同它的文档、等价性声明一起更新。

**四、注册项有清理路径。** 新注册的回调、监听器、资源必须有对应的释放逻辑，并且有测试覆盖释放路径。

**五、证据存在。** 作者跑过与改动面相称的检查，且 CI 覆盖了完整的矩阵。**反过来核验**：如果作者声称跑了某个检查，diff 里应该有那个检查会产生的痕迹。

**六、面向用户的文案是本地化拥有的。** 拒绝在组件、模板、helper 返回值、无障碍属性、原始类型的默认值里硬编码产品文案——它们必须走类型化字典。

## 人工检查项

这些无法机械化，需要真的读懂代码：

**接口契约的两侧追踪。** 改动接口时，两侧都要看：实现是否满足声明，调用方是否仍符合假设。只改一侧是常见的漏。

**生命周期与并发。** 发布前的竞态窗口、await 期间的取消、回调的围堵范围、销毁时能否达到静止状态（quiescence）。这类问题在测试里几乎不会暴露，只会在线上的低概率时序里出现。

**能力与消费者。** 新加的公开方法有几个调用者？如果只有一个内部调用者，那是不必要的 API 扩张——加宽了表面积却没有第二个消费者。**反向也检查**：删掉的公开方法里，有没有外部消费者。

**边界覆盖最终操作。** 检查链的最后一个环节是否真的被验证过。检查了「请求被构造」但没验证「请求被发出」是很典型的缺口。

**真实入口路径。** 手工挂载的插件不会暴露 Loader 的导出错误。要从真实入口跑一遍。

**模型视角。** 如果改动影响模型看到的东西，检查模型**实际收到的**提示词、工具 schema、诊断信息——而不是你以为它收到的。

**执行点。** 追踪到真正执行拒绝的那一步。声明式的约束若没有对应的执行点，等于没有约束。

**测试强度与可靠性。** 测试是否会在行为回归时失败？有没有负向对照？并发下会不会假失败？

**状态的所有与借用。** 谁拥有这块状态，谁只是暂时借用。借用的代码不应该假定它在等待期间没变。

**决策记录与实现是否一致。** 有决策记录时，实现是否符合记录里的决策。不一致说明其中一方过时了。

## 报告方式

**说清缺陷、位置、影响、证据。** 「这个循环会在空数组时多跑一次，第 42 行的索引访问会读到 undefined」比「这里有问题」有用得多。

**局部缺陷贴在最紧的 diff 范围上**，跨切面的架构问题用 PR 级评论——这样作者能分清哪些是改这一行就行的、哪些需要重新讨论设计。

**区分阻断项与建议。** 阻断项是「不改就不能合」，建议是「改了更好」。混在一起会让作者猜。

**省略已经被绿色门禁强制的问题。** 格式、链接、预算——门禁已经管了，重复指出只是噪音，且暗示你不信任自动化。

## 收到评审时

**逐条核实每一项，然后在技术层面回应——修改或反驳，不做表演式赞同。**

「好的，你说得对，我这就改」在作者其实不同意时是有害的：它让分歧消失但问题留下。技术性反驳（「这里不能按你说的改，因为 X 会导致 Y」）比附和更有价值。

## 评审人自己也要守的纪律

**不要在评审里要求作者用 `--no-verify` 绕过门禁。** 门禁失败要么是代码问题，要么是门禁问题——两者都该显式处理。

**不要要求与这次改动无关的重构。** 想清理别处的代码，单独开一个改动。混在一起会让 diff 无法审查，也会让回滚变得不可能。

**如果这个改动引入了缺陷、而后续改动放大了它——修在引入它的那个 PR 上**，然后向上传播。修在下游会让引入它的那个 PR 带着缺陷合并，且它的评审人看不到修复过程。

# 文档链

## 链解决什么

[doc-governance.md](doc-governance.md) 管「每个事实住在哪、写多长」；链管「一件事从提出到了结，走哪些档、在哪一步留痕、什么时候可以冻起来」。

缺了链，常见的失败是这几种：决定只有结论没有过程，半年后没人知道当初排除了什么；同一件事的来龙去脉散在聊天、issue 和多个 commit 里；过期的文档没人敢删也没人敢信，因为看不出哪份还算数；归档靠记忆，「冻结」和「暂时放着」从目录上看不出区别。

链的答案是三个部分：**索引**让一切可被找到，**活账**让未了结的事有唯一清单，**槽位目录**让每份文档在动笔之前就知道自己该长什么样。

## 槽位与职责

八个槽位，两种形态：索引与活账各是一份文档，其余六个是目录。

| 槽位 | 职责 | 不属于这里 | 形态 |
|---|---|---|---|
| 索引 | 全链导航：每个槽位一行，写清职责与当前篇数 | 任何正文内容 | 单档 |
| 活账 | 未了结事项的唯一清单，一行一条 | 已完成的历史、过程叙述 | 单档 |
| 评审 | 对方案或交付的评审结论与验收判定 | 实施进度、设计理由 | 目录 |
| 设计 | 方案、取舍、被否决的替代方案 | 逐日的实施记录 | 目录 |
| 执行 | 批次计划与交付记录：做了哪几批、各自结论、证据指针 | 设计理由（链到设计档） | 目录 |
| 调研 | 外部事实、现状盘点、可行性结论 | 决策本身（决定住设计档） | 目录 |
| 规范 | 长期有效的操作规范，替代口头约定 | 一次性流程、批次记录 | 目录 |
| 归档 | 冻结的历史，只读 | 还可能改动的东西 | 目录 |

判据与文档层级一致：写一份新档之前先问「这件事已经住在哪了」。同一主题的设计档只有一份在改时不要另立「设计（二）」——改原文，修订说明住评审档。评审档同主题多份是正常的（每轮一份），设计档不是。

每份链档开头写一行**定位**：本档是什么、不属于本档的是什么、被排除的部分在谁那里。这一行是链的自证——没有它，读者要靠通读才能判断该不该信这份档。

## 命名与归位

`<主题>-<类型>[-<限定>]-<日期>.md`，四段都可判。主题是这件事的名字（不是文体名）；类型取所在目录的类型（设计/执行/评审/调研/规范）；限定可选，用于区分同主题的多个版本或署名评审者；日期是**立档日**，补写旧事也用今天的日期——它标记文档自己的时间线，不是事件发生的时间线。

日期用 `YYYY-MM-DD`：文件名可排序、可比较、能被脚本解析。

一档只讲一件事。主题换了就立新档并链回旧档，不要在一份档里追加不相关的第二件事——追加会让日期、限定、结论一起失真。

## 流转

一件事的典型路径：调研（可选）→ 设计 → 评审 → 执行（一批或多批）→ 了结并归档。各槽位的进出判据：

- **立设计档**：这件事存在可选方案，或有人可能反对。没有可选方案的纯执行任务不写设计档，直接进执行档记录取舍。
- **进评审**：设计或交付告一段落，需要独立于作者的人给结论。评审档必须给出三者之一——**通过**、**有条件通过**（条件逐条进活账）、**退回**（退回理由进活账，改完重评）。空缺的评审等于没评。
- **进执行**：方案已定（评审通过，或明确记录「无人评审、作者自决」）。执行档先写全局序（哪个批次先做、依赖与可并行面），再按批展开：靶点、动作、验收。每批完成时把 commit 号回填进执行档的末节——执行记录是回填出来的，不是边做边写的日志。
- **成规范**：执行中出现了会被反复用到的操作规则，把它从执行档提出来写成规范档，并从原处删掉——不复制（见 [doc-governance.md](doc-governance.md) 的「一个事实一个家」）。
- **了结**：活账里的条目要么完成（从活账移出），要么明确放弃（写明理由，也从活账移出）。活账不允许长期挂着「已完成但没摘」的条目——那会让活账失去「看一眼就知道还欠什么」的作用。

评审意见不落空的标准：每条意见都能在活账或某份链档里找到归宿，没有停在口头的「回头改」。

## 归档与精简

归档是**冻结**，不是整理：移进归档目录的文档不再修改，哪怕错别字。要改就移回来改，改完再冻。

归档前必须过三关：

一、**核验内容与历史一致。** 用 git 复原锚核对该文档当前内容与归档所指的 commit——「正在冻的就是当时那份」。内容对不上就先弄清差异从哪来，不要直接把现状冻住。

二、**未了结的事先立开放项。** 归档的文档里如果还活着条件或待办，先把它们提成活账条目再归档；否则冻结会把它们一起冻住。

三、**归档动作留痕。** 归档的 commit 号写进索引的历史行或活账对应条目；只凭目录现状没人能判断「什么时候冻的、当时冻的是哪一版」。

归档**原地直删，不做打包压缩**：git 已经是存档，压缩包是第二份副本，会分叉且不可 diff。需要引用归档内容时，链接指进归档目录；归档内的出链允许过期，因为冻结意味着不再维护。索引与活账在归档后要同步跟上：索引的历史行更新指针，活账摘掉对应条目。

对照 `agent-notes` 的归档：决策记录用整文件哈希封存并由门禁拒绝任何改动，链的归档靠 git 与索引行——**强校验留给决策记录**，链档的冻结靠流程纪律。

## 记档与校验

记档是链的燃料，文法只有一条：**一句结论 + 指针**。结论写决定或状态，不写心情；指针写文件路径或 commit 号，不写「详见相关文档」。

反例：「推进了设计相关工作，进展顺利」——没有结论、没有指针，读者无从核实。正例：「设计定稿：槽位定为八个，命名四段可判——`03-设计/文档链-设计方案-2026-10-13.md`」。

校验由 `scripts/harness/verify-doc-index.ts` 承担。契约是仓库数据——链必须自带材料：

- `scripts/harness/doc-index.manifest.json` 声明链：`index`（索引文档路径）、`scan`（槽位目录的根）、`entries`（每个槽位一条，含 `dir` 与可选的 `count`）。
- 门禁核对四件事：声明的目录都在磁盘上；`scan` 下每个一级目录都被声明；索引里每个槽位目录都有命名它的行、每个一级文档都被引用；`count: true` 的目录，命名它的索引行上的数字必须等于磁盘上的实际篇数。
- `{}` 表示本仓库不带链，门禁放行；manifest 缺失才是错误——那意味着链存在但没声明，属于配置漏项。
- 计数只数非隐藏文件，`.gitkeep` 不算一篇，目录可以先占位。

链与 `agent-notes` 的分工：**过程与交付**（做了什么、怎么评的、证据在哪）住链档；其中会成为长期约束、值得未来检索的**决策**（为什么这么选、放弃了什么）另立 agent note——一次性证据不进决策记录，决策记录不抄过程。

# 提交前的证据选择

**除了钩子，没有通用的本地基线。** 每个行为改动需要它自己的、会因该回归而失败的最小检查。

## 按改动触及的面选证据

| 改了什么 | 跑什么 |
|---|---|
| 某个包或脚本的行为 | 拥有该行为的那个测试文件，或聚焦的测试名 |
| 远程/网络 mock 的类型 | 类型检查（注意：未构建产物上的 `any` 只是局部兜底，不是严格证据） |
| 文档、决策记录、目录 | 文档门禁 |
| 模型、编辑器、CLI、终端可见的输出 | 聚焦的快照重放 |
| 清单文件、公开导出、构建配置 | 构建 + 卫生检查 + 产物冒烟 |
| 真实外部服务 | 真实端到端测试 |

**关键判据**：这个检查会不会因为本次改动引入的**那个具体回归**而失败？不会，就不是充分证据。

## 覆盖率按源文件选，不按测试文件

跑覆盖率时要显式指定**源文件范围**，否则会统计到无关代码：

```sh
<test-runner> run <被测行为的测试文件> \
  --coverage --coverage.include='<包目录>/src/**/*.ts'
```

不要用「无测试也通过」的开关、不要下调阈值、不要用窄的 include 范围掩盖未覆盖的文件。这三件事都是把「没测到」伪装成「测过了」。

## 不要重复已经通过的检查

推送前**不要**为了安心再跑一次刚跑过的检查。重复不产生新信息，只浪费时间，并且会让人养成「反正要跑两遍」的习惯，进而跳过第一遍。

同样，不要因为存在某个聚合命令就反射式跑全量。全量只在三种情况下跑：用户明确要求、诊断 CI 失败、改动确实横跨整个仓库。

**不要重建已经被删掉的聚合脚本。** 它被删掉通常是因为它鼓励了全量本地跑。

## 钩子该做什么

钩子的定位是**「立刻能修的小事」**：

- 格式化暂存的代码，并把修复后的文件重新加入暂存区
- 检查暂存的空白问题
- 校验暂存的门禁相关文件（决策记录格式、归档哈希）
- 重新生成生成物（如第三方声明清单）

**钩子不该做**：跑测试、跑快照、跑文档检查、跑构建、跑卫生检查。

理由值得记住：往钩子里塞这些东西会让提交变慢，而变慢的钩子会让人学会用 `--no-verify`。**一个被普遍绕过的钩子比没有钩子更糟**——它制造了「有检查」的错觉。

推送钩子可以比提交钩子稍重一点（比如一次增量类型检查），但同样到此为止。

## 重写历史时的纪律

**`Raw --force is never allowed.`**

改写推送必须用带 lease 的形式，并且显式观察到的远端引用。远端已经移动时**中止**，不要覆盖别人的提交。

如果正在做 merge-forward、又需要换一个更新的基线，先保住当前进度（提交或打标签），再取新基线——否则一次失败的 rebase 会让你丢失已完成的工作。

**改写之后必须重新验证。** 提交 ID 变了意味着所有基于旧 ID 的假设失效：重新取 head、重新检查未解决的评审意见、重新确认状态。原样重复改写前跑过的检查**不算**验证。

## 失败时

**停下来，修掉，或者明确说清阻碍。`Do not push and hope CI differs.`**

本地失败而期待 CI 通过，是在赌环境差异。偶尔赌赢一次会让这个习惯固化，直到某次赌输——而那次输掉的通常是一个本该被抓到的回归。

如果失败看起来是环境问题（凭证、网络、沙箱），用**最小的**权限提升重试，并保留证据说明这确实是环境问题，而不是代码问题。**不要**为了绕过失败去改测试或改门禁。

## 推送后确认

推送之后核实远端引用与本地一致：

```sh
git rev-parse HEAD origin/$(git branch --show-current)
```

不匹配说明推送没真正生效（常见于代理、钩子中断、并发推送），而下一步的 PR 会基于一个不是你以为的版本。

## 一个特殊的坑

如果 PR 上显示「没有检查」，先看**可合并性**。冲突或脏状态的 PR 上，平台**根本不会创建** PR 工作流运行——所以「没有检查」不是「检查还在排队」，而是「检查永远不会来」。空提交、切换草稿状态、回滚重推都不会有分别。先解决冲突。

# 文档治理

## 一个事实一个家

每条规则、每个事实只在**一个**文件里定义，其他地方链接过去。这是文档体系最重要的一条，因为重复是腐烂的起点：两份说同一件事的文本会分叉，分叉之后没人知道该信哪个。

先给每个层级定好职责边界和「**不属于这里**」的清单——后者比前者更重要，因为越界是实际发生的失败。

| 层级 | 职责 | 不属于这里 |
|---|---|---|
| 根 `AGENTS.md` | 每次会话都需要在上下文里的标准指令，一条一到三行，各自链到它的家 | 故事、worked example、情境流程 |
| 子树 `AGENTS.md` | 该子树的局部强制规则（如 `packages/AGENTS.md`） | 全仓通用规则（链到根） |
| 架构文档 | 系统怎么组装、模块边界、运行时词汇 | 具体 API 签名（链到源码） |
| 子系统文档 | 一个子系统的机制与生命周期 | 跨子系统的编排 |
| 决策记录 | 为什么这么选、放弃了什么（→ `agent-notes` skill） | 迁移计划、验收清单（交付后） |
| cookbook | 怎么做一件具体的事 | 为什么这么设计 |
| 包 README | 该包的职责、配置、公开行为、已知限制 | 全仓架构 |
| 技能（skills） | 可复用的工作流与专业判断标准 | 产品与运行时契约 |

**判据**：写下一段话之前先问「这个事实已经住在哪了」。如果答案在别处，改写那里的原文，然后链接过来。

## 字数预算

用 `wc -w` 计数，只在**超限**和**文件缺失**时失败：

```sh
node scripts/harness/verify-doc-budgets.ts
node scripts/harness/verify-doc-budgets.ts --list   # 只报告，不失败
```

预算清单在 `scripts/harness/doc-budgets.manifest.json`，形如 `{ "AGENTS.md": 1960 }`。

三条纪律：

**一、超限的处理顺序是 迁移 → 精简 → 提高上限。** 先问「这个事实是否本来就该住在别处」——多数超限其实是越界的结果，迁移才是正解。其次是精简（见 [prose-standard.md](prose-standard.md)，注意精简不等于删字）。实在需要更多空间才提高上限，且必须在同一个改动里给出理由。

**二、上限是护栏，不是削减目标。** 在目标以内要保留至少 5% 余量；已经在目标以上时**冻结上限**，直到迁移或精简把文档带回目标以下。

**三、上限过低是 bug。** `A too-low ceiling is a budget bug.` 一个让人为了合规而删掉必要信息的预算，比没有预算更糟。

## 一段一行

**每个段落占一个物理行。** 由 `verify-md-wrap.ts` 强制。

理由不是美观：段落被硬折行后，改一个词会让 diff 跨越好几行；中英对照时两侧的折行位置不可能一致；review 时看不出「这一句是新加的」。一段一行让 diff 精确对应语义改动。

代码块、表格、列表保持自己的格式；缩进的围栏（列表内的代码块）也算代码块。

## 围栏里的代码要能编译

文档里的 `ts` / `js` 代码块应当真的能通过类型检查或至少能解析。粘贴的类型声明用专门的 info string 标记（`ts type-equiv`），并在清单里注册——这样它们能被自动校验，而不是慢慢腐烂成错误文档。

## slop 清单

八类应当被删掉的文本。这份清单是**评审工具**，不是自动门禁——它们需要判断，而判断属于人。

**一、重复的规则。** 同一条规则出现在两处。grep 一下特征短语，如果命中多处，留一处。

**二、越界的历史。** 把实现过程、评审讨论、变更沿革写在描述现状的文档里。「原先是 A，后来改成 B」属于决策记录。

**三、实现状态标注。** 「已实现！」「未来计划……」「暂未支持」。状态由代码、目录、issue 表达，文档里不重复声明——尤其是「未来计划」，它会在实现之后变成谎言。

**四、手抄的目录。** 把常量、测试清单、函数签名抄进文档。抄的那一刻就已经是冗余副本，而且它不会随代码更新。

**五、推理转录。** 把「我先看了 A，发现不行，于是去看 B，最后选了 C」写进文档。读者要的是结论和理由。

**六、兄弟方法旁的重复理由。** 三个方法都需要「为什么这样排序」，就在共享的类或接口上写一次。

**七、段落墙。** 连续三百字不分段。读者的眼睛需要一个落点。

**八、强调膨胀。** 处处加粗、大写、`critically`、`very important`。**处处是重点等于没有重点**，而且它让真正重要的那一处失去了信号。

另有一类专门针对 `implemented/` 决策记录：**规格腔**（should、迁移计划、验收清单）。已交付的东西用陈述句，见 `agent-notes` skill。

## 链接

`verify-md-links.ts` 校验相对链接的目标文件存在、且 `#fragment` 锚点在该文件里真实存在。

几个实现上的取舍值得知道：
- 外部 URL 不抓取——那会让门禁依赖网络，且把「目标站点改版」变成你的构建失败。
- 锚点比对使用 GitHub 的 slug 规则（小写、去标点、空格转连字符、**保留连字符与下划线**）。最后一条容易写错：`### list_agents` 的锚点是 `#list_agents`，把下划线当标点删掉会让所有下划线标题的引用变成假阳性。
- 记录生成的产物（`expected/`、`snapshots/`、`fixtures/`）不参与链接检查。它们引用的是被测系统输出的字面文本，其中的占位路径（`path/to/image.png`）是内容而不是引用。需要检查其中某个文件时，用 `scripts/harness/markdown-patterns.json` 显式列入。

## 扫描范围的两种模式

默认模式：递归所有目录，跳过构建产物与依赖树（`node_modules`、`dist`、`build`、`vendor` 等），并跳过记录生成产物的目录。

显式模式：存在 `scripts/harness/markdown-patterns.json` 时，它是一个 glob 数组，**替代**默认遍历。适合大型仓库里只想管住一部分文档的情况——上游项目就是这么做的（只扫 `README`、`docs/`、`.agents/notes/`、`packages/*/*.md`、`AGENTS.md`）。

显式模式的一个已知代价：范围窄意味着漏检。上游用窄范围时，中文 README 里一个指向英文专有锚点的坏链就漏了过去；用默认的宽范围扫描时它立刻被抓出来。**范围越窄，越要清楚自己在放弃什么。**

# 语言策略

一个仓库里有两种语言问题，混在一起就会各自出错：**哪些文件要写两遍**（配对），和**每个文件写哪种语言**（语言选择）。分开答，两条答案都不会打架。

## 两个轴

**配对轴：这份文件是被执行的还是被理解的。** 被执行面（`AGENTS.md`、配置、模板、门禁脚本、提交钩子）**永不配对**——机器逐字消费它，两份副本就是两个事实；被理解面（README、`docs/`、决策记录）是给人读的，需要双语时只在这一面配对照文件与一致性记录（契约全文在 `agent-notes` skill 的 `references/bilingual.md`）。

**语言轴：谁必须遵守它。** 被执行面的读者是 agent 与未来的维护者，语言取**仓库工作语言**——不取会话语言，不取作者习惯。判据是「这条规则半年后由谁读」：读的人变了而语言没变，规则就被跳过了。

## 判据：这条改了，需要谁点头

写进指令文件之前逐条问一次，答案决定它住哪：**没人需要点头**——跑一遍门禁就能判对错的，是**规则**，留在 `AGENTS.md`；**需要有人被说服**的，是**决策**，写进决策记录（`agent-notes`），指令文件只留一句指针。规则单语；决策的**理由**住在被理解面，那一面才配对。

这条判据的用处是把「要不要双语」从一个风格问题变成一个归属问题：**指令面永不配对**，所以它没有「写哪种语言的对照件」这个选项，只有「用工作语言」这一个答案。

## 语言从哪里来

按顺序解析，前一步有答案就不看后一步：

1. **声明。** `AGENTS.md` 在「本文件的维护」一节用散文声明工作语言（模板已含此节）；`.agents/notes/harness.json` 的 `primaryLanguage` 是同一句话的机器可读版，管目录拼写与归档门禁。首次铺树时 `bootstrap --notes-language` 两处一并写下；此后它们是**同一次迁移的两半**，改一处必须同批改另一处。
2. **散文证据。** 没有声明时看仓库自己的散文：常驻档、`docs/` 链、提交信息的主要语言就是工作语言。
3. **首次撰写时的会话语言。** 两者都没有（全新仓库）时，用写下第一条规则时实际使用的语言——写完就把它**声明下来**，别让下一个人再猜。

**确定即声明，声明即单语。** 一个仓库只有一种工作语言；多语言仓库指的是**读者可见的产品**多语言，不是内部图文多语言。

## 文件类别

| 文件 | 面 | 语言 | 配对 |
|---|---|---|---|
| 根 `AGENTS.md`、子树 `AGENTS.md` | 执行 | 工作语言 | 永不 |
| `CLAUDE.md` | 执行 | ——（指向 `AGENTS.md` 的符号链接，不写内容） | 永不 |
| 门禁脚本、`lefthook.yml`、`harness.json` 等配置 | 执行 | 工作语言（标识符仍用英文） | 永不 |
| 归档树说明书（`.agents/notes/<归档>/AGENTS.md`） | 执行 | 工作语言 | 永不 |
| 决策记录正文 | 理解 | 主语言 | 按需，见 `agent-notes` |
| README、`docs/` 层级 | 理解 | 主语言 | 按需 |

**标识符不是散文**：代码、路径、flag、目录名、JSON 键、门禁 id 一律英文小写形态——这是被执行的，不是被理解的，翻译它只会制造两个名字。

## 执法边界

门禁能钉住的是**模板选择**，不是散文语言：

- `bootstrap --notes-language en|zh` 决定四件事一起拼写——`harness.json` 的 `primaryLanguage`、决策树目录名、归档说明书、起步模板的语言版本；旗标与已有声明矛盾时直接报错退出。
- 起步模板每份两版（`templates/<名>.zh.md` / `.en.md`），由 bootstrap 按声明选版复制。
- 字数预算按「空白分词 + 每个汉字另计一词」计数——中文没有词边界，只数空白分词会让中文文档在任何上限下都通过（见 [doc-governance.md](doc-governance.md)）。

**门禁不读散文语言。** 没有任何检查会因为你用中文写了英文仓库的 `AGENTS.md` 而报红，也没有检查会因为两侧语言不同而报红——这类判断留给评审。这条边界是诚实的：假装能机器判定「这段文字该用哪种语言」，只会产出会被关掉的门禁。

## 边界情况

**双语仓库的 `AGENTS.md` 写哪一版？** 写工作语言那一版，另一版不写。指令面单语是刻意的：agent 每次会话都读它，两份就要打架。需要两种语言读者的**知识**（用法、设计、决策理由）住被理解面，那边配对。

**贡献者主要说另一种语言。** 那是评审与沟通的配置，不是指令文件的语言——把对外沟通放 `CONTRIBUTING.md`（被理解面，可配对）。改变工作语言是一次**显式迁移**：改声明，`git mv` 整棵树，重录归档说明；不是逐文件的漂移。

**混合语言已经发生了。** 先声明，再按「一个改动搬一个文件」收敛到声明；新写的文件按声明语言写，不要因为旁边是另一种语言就跟着漂。归档树里的历史拼写不改——封存时是什么就是什么。

**主语言与工作语言必须一致吗？** 是，除非有明确理由分开（例如决策语料面向外部读者而仓库内部用另一种语言）——那种情况是**例外，要写进声明**，不是默认允许的漂移。

## 迁移

换工作语言 = 一次独立改动，四件事同批：

1. 改 `AGENTS.md` 的声明与 `.agents/notes/harness.json` 的 `primaryLanguage`；
2. `git mv` 决策树的 lifecycle / class / 归档容器目录（归档树里已封存的**路径不改名**，见 `agent-notes` 的 `references/archiving.md`）；
3. 归档说明书换成新语言；活跃树上的文件按「一个改动搬一个文件」收敛；
4. 跑全量文档门禁——目录拼写错的名字会被逐条点名。

不要用 `bootstrap --notes-language` 改语言：它只在**首次铺树**时生效，目标已有 `harness.json` 时以声明为准，旗标与声明不符会报错退出。这条限制是保护：换语言要移动整棵树，那是独立的一次改动，不是重跑的副作用。

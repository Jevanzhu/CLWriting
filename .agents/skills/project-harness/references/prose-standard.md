# 散文标准

适用于文档、注释、JSDoc、提示词、面向用户的字符串、诊断信息、以及 agent 指令本身。

**这是编辑判断，不是清单。** 规则之间会冲突，靠理由判断。

## 核心：保留完整命题

删字之前，逐条识别这段话承载了什么：

- **actor 与 action**：谁做什么（被动语态常常掩盖了执行者，而执行者往往正是读者需要的）
- **条件与时序**：在什么条件下、以什么顺序
- **情态**：must（必须）、may（可以）、never（绝不）——这三个词的强度差异不能抹平
- **负面保证与例外**：保证不发生什么，以及在什么情况下不成立
- **所有权与副作用**：谁负责、会改变什么
- **失败模式与后果**：出错了会怎样

**一条都不能丢。** `A smaller word count alone is not an improvement.` 删掉「仅在 X 时」会把一个精确规则变成错误规则；删掉「不会重试」会让读者以为失败会自动恢复。

## 精简 vs 损害

判据是**命题是否完整**，不是字数。

合格的编辑：
- 把「在大多数情况下通常一般会」改成「通常」
- 把被动改主动，让执行者显出来
- 把「由于……的原因」改成「因为」
- 删掉不影响命题的元评论（「值得注意的是」「需要指出的是」）

不合格的编辑：
- 删掉限定条件换取简洁
- 把三个分别说明的例外合并成一个笼统说法
- 把「不会自动重试」删成「会失败」——后者没说清楚读者该做什么

## 术语要精确

写作时问自己：这个抽象名词指向的对象，有没有更准确的名称？

- 想说**响应字段**就别写「响应形状」
- 想说**JSON 校验**就别写「验证边界」
- 想说 **ESM 导出**就别写「模块形状」

**`contract` 这个词只保留给真正有约束力的场景**：前置条件、后置条件、不变量、兼容性承诺，以及其他调用方、被调用方、实现方、提供者、消费者所依赖的义务。**流程、通信、安全、事务、生命周期边界**这些词保留字面意义。滥用抽象名词会让文档读起来像在说事，实际什么都没说。

## 按位置规定必备覆盖

不同位置需要覆盖的内容不同。缺了这些，读者就得去别处猜。

**公开 JSDoc** — 非显然的契约：参数含义与约束、返回值语义（尤其是「返回 null 意味着什么」）、抛出的失败、副作用与幂等性。函数式导出带 `@param` / `@returns`。

**内部注释** — 只写代码本身看不出来的：为什么是这个顺序、为什么不能改成看起来更直接的做法、依赖了什么外部事实。**不要复述代码。**

**模块注释** — 这个模块的职责边界，以及它明确不负责什么。

**测试** — 描述**行为**，不是「正确性」。测试名应该说明「什么情况下会发生什么」。改掉过时行为时连它的测试一起改，并在 PR 里说明为什么。

**决策记录** — 见 `agent-notes` skill。

**README** — 职责、配置项、公开行为、已知限制。限制那一节最常被漏，也最有价值。

**失败与诊断信息** — 可读的摘要 + 受影响的操作 + 安全的下一步。`Never claim success, rollback, or safe retry without guarantees.`

**Agent 指令与 skill** — 除了规则本身，还要声明**行为护栏与范围限制**，例如「这是判断指导，不是脚本/清单」。不写这句，agent 会把指导当机械清单执行，然后在你没预料到的情境里做出荒谬的推论。

**面向用户的字符串** — 产品文案由本地化字典拥有，不要硬编码在组件里（有本地化门禁时它会被拒绝）。

## 边界声明

写文档时**明确写出这个文档不保证什么**。这是最容易被省略、又最有价值的一节。

好的例子：「绿灯意味着在这些确切内容上确认过一致性，不意味着确认本身可靠」——它把质量责任明确交回给评审人，而不是让人误以为门禁通过了就万事大吉。

写「已知限制」时不要写成免责声明。写清楚：在什么条件下会失败、需要人工做什么、什么情况下应该重新考虑这个决定。

## 不要做的事

**不要复述代码。** 注释说 `// 遍历用户列表` 是噪音；说 `// 这里必须按 id 排序，否则下游的二分查找会静默错位` 才有价值。

**不要写推理转录。** 「我尝试了 A，失败后改成 B」——过程属于 PR 描述，文档里只留结论和理由。

**不要解释远处行为。** 注释应该解释**它所在位置**需要知道的事。想解释另一个模块的行为，在那里写，或者写进架构文档。

**不要用隐喻。** 用直接、具体的词。注释与文档承载的是契约和事实，隐喻会让不同读者读出不同含义。这一点在技术文档里尤其重要，因为读者可能不是母语者。

**不要保留评审历史。** 「按 reviewer 的要求改成……」——决定和理由留下，谁在什么时候要求的属于 PR。

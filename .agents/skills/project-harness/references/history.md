# 历史、分支与合并

## 有意识地选择 PR 历史

**拆分独立的改动。** 一个 PR 只做一件事时，评审能聚焦、回滚能精确、出问题能定位。把「修 bug」和「顺手重构」混在一起，会让两者都无法审查，也会让回滚变成不可能。

**修在引入它的那个 PR 上。** 发现问题时，如果它是在某个已经评审过的 PR 里引入的，就把修复加到那个 PR 上，然后向上传播——不要在后面某个 PR 里修掉。理由：修在下游会让引入它的那个 PR 带着缺陷合并，而它的评审人永远看不到修复过程，也就无法从中学到东西，更无法判断原有的评审是否充分。

## merge-forward 与 rebase

两种刷新方式，各有适用场景：

**merge-forward** —— 把主干合并进你的分支。历史里多一条合并提交，但**每个提交的 ID 不变**。适合：已经推到远端、已经评审过、有人基于它工作的情况。ID 不变意味着所有基于旧 ID 的引用（评审意见、状态检查、别人的分支）继续有效。

**rebase** —— 把提交搬到新基线上，产生新的 ID。历史线性、干净。适合：还没推送、或分支只是私人的、且你愿意重新验证一切的情况。

**默认选 merge-forward。** 它更安全，代价只是历史里多一些合并提交，而这个代价几乎没人真的在意。

**判据**：这个分支有没有别人依赖？有就 merge-forward。

## 堆叠 PR

当几个 PR 互相依赖（B 需要 A 的代码）时，用平台的原生 stack 功能，不要手工维护分支链。

**核心规则**：

- **顺序由实际的 base 关系决定**，不要靠记忆或文档维护一份列表。底部的 PR 指向主干，往上每一个指向前一个的 head 分支。
- **用平台命令整栈合并**，不要逐 PR 手工合并加手工改 base。手工操作会在中途出错，留下指向已删除分支的 PR。
- **一个 PR 一个工作树**。在同一个工作树里切换分支来应付多个 PR，是冲突和误提交的主要来源。
- **评审修复修在引入它的那一层**，然后向上传播（同上文「修在引入它的那个 PR 上」）。

**不要自动解散、重排或重建已有的 stack。** 这类操作会改动共享的远端元数据，影响范围可能超出你以为的那几个 PR。发现结构异常时，停下来问，不要自动修。

**同步操作要特别小心**：某些 stack 命令会把「rebase + 受 lease 保护的 force-push」作为一个不可分割的操作执行——**无法在重写和发布之间插入本地验证**。因此这类命令执行后必须立刻重新验证每一层，在全部验证通过之前不要声称栈已就绪，也不要合并。命令成功不等于栈没问题。

## 重写历史的纪律

**`Raw --force is never allowed.`**

必须用带 lease 的形式，并显式指定你观察到的远端引用。远端已经移动时**中止**——那说明有人推送了新东西，覆盖它就是删掉别人的工作。

**改写之后一切基于旧 ID 的假设失效**：重新取 head、重新检查未解决的评审意见、重新确认可合并性与检查状态。不要因为「刚才跑过了」就跳过。

**保住检查点**：正在做 merge-forward 时若需要换一个更新的基线，先把当前进度提交或打标签。一次失败的 rebase 加上没有检查点，等于丢失工作。

## 提交信息的约定

结构化的提交前缀（`fix:`、`feat:`、`test:`、`docs:`、`refactor:`、`chore:`、`perf:`）是有价值的——它们让历史可搜索、让变更日志能自动生成。

但**不要为此加一个提交消息门禁**，除非你确定团队会一直遵守。理由：提交消息门禁失败时，开发者习惯性的反应是 `--no-verify`，而这个习惯一旦养成，会连带绕过提交钩子里那些**真正有价值**的检查（格式化、决策记录校验、归档哈希）。

上游项目的做法值得参考：约 97% 的提交符合约定式前缀，但**没有任何自动强制**——纯靠约定与评审。这是刻意的取舍：一个偶尔被违反的约定，比一个让人学会绕过钩子的门禁更健康。

如果确实要强制，把它放在**服务端**（合并前检查），不要放在本地钩子里。

## 分支命名

按改动类型前缀（`fix/`、`feat/`、`refactor/`）或按作者命名空间（`<用户名>/`）。两种都可以，重要的是**一致**。

把「作者命名空间」用于多人并行开发的场景能减少冲突；把「类型前缀」用于需要按类型筛选分支的场景。

## 合并方式

**squash 合并**适合「分支里的中间提交没有独立价值」的情况——多数功能分支都是这样。它让主干历史每个提交都是一个完整、可回滚的改动。

**merge 提交**适合「分支里的提交有独立价值、且需要保留」的情况——大型改动拆成多个逻辑提交时，这些提交本身就是文档。

**判据**：历史读起来，你希望看到一个改动一次，还是希望看到它被拆解的每一步？多数时候是前者。

主干上**不要直接推送**，一律经 PR 与检查进入。这既是为了门禁生效，也是为了让每个改动有一个可讨论的位置。

# 治理模型

这份文档讲的是**没有**随本 skill 提供可运行代码的机制。

它们在上游项目里运作良好，但每一个都依赖组织级基础设施：GitHub App、Projects v2 看板、Python + Pygments、多包发布序列、双语语料。单人仓库引入它们，维护成本会远超收益。

但它们的**问题定义与核心算法**很有价值——将来团队化时，你会需要它们，而且会需要在这里找到判断依据。下面每一项给出：解决什么问题、核心机制、自建的前提。

## 一、加权审批

### 解决的问题

「一个 +1 等于一次批准」在两种情况下失真：

- **资深评审人的一次认真评审**和**顺手点过的批准**权重相同。
- **改了一行的 PR** 和**重写一个子系统**的 PR 需要同样数量的批准。

前者让评审变成形式，后者让大改动无人敢深看。

### 核心机制

**基准分**：每个评审人有一个权重（配置在策略文件里），普通有写权限的评审人一分，特定几人两分。合并阈值设为两分。

**作者信用**：`min(100, 已合并 PR 数) × 11/1000`。0 个 PR 得 0 分，50 个得 0.55，100 个及以上封顶 1.1 分。关键约束是**作者信用不能单独满足阈值**（上限 1.1 < 2）。它补偿的是「这个人提交过很多已合并的改动」，即熟悉仓库约定的证据。

组合效果很微妙：91 个已合并 PR 的作者配一个普通评审刚好过关，90 个只有 1.99 分。

**blame 加权**：一分的批准可以按「该评审人拥有多少被改动的生产代码行」加权上调，公式 `min(2, 1 + 4 × 归属行数 / 总改动行数)`。0%、12.5%、25% 的归属分别给出 1、1.5、2 分，25% 以上封顶。

同一个人改过这块代码的 25% 以上，他对这次改动的评审确实比陌生人有价值——这是这个机制的核心假设。

**「生产代码」的定义是机械的**：`packages/`、`apps/`、`python/`、`native/` 下的 `src/` 目录，加上少数明确列出的入口文件。排除测试、固定装置、快照、示例、生成代码、依赖、声明文件、注释与空行。用词法分析器区分注释与字符串，混合行计入。

**归属在「实时 base 与确切的评审 head 的 merge base」处计算。** 这个细节很重要：用别的基点算出来的归属会包含不属于本 PR 的改动。

### 值得借鉴的三个防御

**一、策略从默认分支读取。** 审批策略的改动只有合入默认分支才生效——防止一个不受信的 PR 改掉给自己的评分程序。

**二、绑定期望来源。** 分支保护要求 commit status 时必须**同时**限定期望来源（如 GitHub Actions），仅按名字匹配会接受其他集成伪造的同名状态。

**三、失败必须可见。** 评估失败时发布 `error` 状态，而不是「默认通过」。中途失败的评估留下上一次的成功状态是最危险的。

### 已知的诚实边界

上游文档自己写着：**`blame` 衡量的是最后触碰代码的人，不是评审质量或语义专长。** 这个机制是启发式的，不是真理。

### 自建前提

- 需要平台 API 能读评审记录、合并历史、文件 blame。
- 需要能写 commit status 并对评审做操作（撤销、请求）。
- 归属计算需要完整历史——浅克隆必须被**拒绝**，不是降级。
- 大约两千行策略代码加一个词法分析器依赖。

**建议**：单人仓库不要做。它的收益来自「多人评审的质量参差」，人少的时候问题不存在。

## 二、Issue 看板状态机

### 解决的问题

「这个 Issue 的下一步归谁」——是等作者改代码，还是等评审人看？这个信息通常散落在对话里，没人能一眼看出队列里哪些事真的卡住了。

### 核心机制

把 PR 事件当作**命令**处理，而不是从聚合状态推导：

| 事件 | 目标状态 |
|---|---|
| PR 打开或**正文**编辑（改标题不算） | In progress |
| 请求评审 | In review |
| 提交变更请求 | In progress |

**普通事件只前进不后退。** 唯一的例外是「变更请求」可以把 `In review` 退回到 `In progress`，而且**仅在** `In review` 这个状态本身是自动化写入的时候。人类手写的状态受保护——自动化不得覆盖人对「下一步归谁」的判断。

这条守卫值得记住：它是「自动化可以改状态，但不能覆盖人的意图」的具体实现。

### 三个正交的标签维度

上游把「变更意图」与「受影响的领域」严格分开：

- **意图**（`kind/*`）：封闭集合，恰选一个，记录**主导意图**。附带的测试、文档、清理不改变它。
- **领域**（`area/*`）：至少一个，**开放可扩展**——没有既有标签诚实覆盖时可以自行创建，但必须事后报告。
- **优先级**（`p0`–`p3`）：最多一个。

另有一份**保留别名清单**，把迁移前的同义词全部锁住，防止它们被当成「无关的运维标签」重建回来。这个小设计解决的是真实的回潮问题。

### 事实源三元组

上游要求每条强制规则同时存在于三处：**平台的活配置**、**仓库里可执行的代码**、**决策记录**。三者必须一起改。

理由很实在：只改代码不改平台配置，规则不生效；只改平台不改代码，下次有人读代码会得出错误结论；不改决策记录，半年后没人知道为什么这么设计。

### 自建前提

需要一个看板工具（Projects v2、Linear、Jira 均可）、一个能读写它的凭证、以及大约三百行纯规则代码（验证部分）+ 一百多行 API 封装。

**这部分是可移植性最高的**：`kind` 与 `area` 正交、主导意图、保留别名——这三个设计不需要任何基础设施就能应用。

### 已知的诚实边界

上游自己写着：**生命周期处理是事件驱动的，不是对账器；漏掉的事件不会修复状态。** 并发变更也没有原子的 compare-and-swap。

## 三、多序列发布

### 解决的问题

一个仓库里有多个发布单元（主包、依赖的内核包、原生插件、Python SDK），它们各有各的版本节奏。用同一个版本号统管会让所有单元被迫同频；各自为政又没人知道哪些版本兼容。

### 核心机制

**每个序列有自己的版本基线、标签前缀、触发方式，互不等待。** 发布主包不会重新发布内核，反之亦然。

**版本落库，不由 CI 派生。** 版本号被提交进仓库，人在这之后打标签。**CI 从不写仓库。** 这让「发布的到底是哪个版本」可以从仓库状态直接读出，而不是从某次 CI 运行的日志里推断。

**注册表三态决策**（幂等的关键）：

| 注册表状态 | 动作 |
|---|---|
| 没有该版本 | 发布 |
| 有该版本，且完整性哈希相同 | 跳过（同一产物重跑） |
| 有该版本，但哈希不同 | **失败**，报告「内容变了却没升版本」 |

第三态是最有价值的：它抓住了「改了代码忘记升版本，然后重跑发布」这个会导致线上版本与源码不一致的失误。

**预发与发布分离**：每个 PR 跑一次「打包彩排」（无凭证），发布是一个需要人工触发的独立动作。**发布永远不该出现在 PR 检查列表里。**

### 发版批纯度

**发版批只做版号与出包，不夹带。** 挂账项与待拍板先各自成批收口，收口之后才发版。

要保住的是「这次发出去的是哪个状态」能被一句话回答。夹带一处顺手修的东西之后，这个回答就变成两句，而第二句——「另外还改了一点」——恰好是唯一没被发布流程覆盖的改动面：它没经过这一批的验收，却跟着产出了。

**可判形态**：给发版批一个可识别的标识（提交信息前缀或分支名），再要求它的 diff 只落在版本声明面——版本文件、锁文件、变更日志的版本段。给不出标识的仓库没有机器判据，只有评审判据：审阅者逐条看这批改了哪些文件、是否都属发版面。两者都算数，区别只在于门禁替你看了多少。

### 自建前提

一个包注册表、一个能触发发布的方式、以及幂等检查（多数注册表提供完整性哈希）。核心代码量不大，但**族模型的设计**需要先想清楚——哪些包共享版本，哪些独立。

## 四、双语配对

### 解决的问题

维护中英双份文档时，两侧会静默漂移：一边加了一节，另一边没有。等发现时，往往已经没人知道该以哪边为准。

### 核心机制

**一对 = 三个文件**：主文件、对照文件、一个记录两侧哈希的 sidecar。

**哈希按标题分节**。每节的主侧与对照侧各存一个短哈希（上游用 SHA-256 前 16 位）。改了一侧而未更新 sidecar，门禁立刻变红。

**结构镜像**独立校验：标题层级与顺序、列表种类与起始序号、列表项数量、表格行列数、代码块内容、带 query/fragment 的链接目标——全部逐项比对。

**排除代码块与生成区域**（它们本来就要求两侧逐字节相同），但**其余内容即使恰好相同也要哈希**——这条防的是「把主侧段落原样抄进对照侧而不翻译」逃避记录。

### 最值得抄的一条

**门禁的诚实边界**：上游文档原文写着——绿灯意味着「在这些确切内容上两侧被确认过一致」，**不**意味着「确认本身是可靠的」。门禁检查哈希与 Markdown 结构，它无法判断两侧是否真的说了同一件事。

**一个重新记录过哈希、但对照部分写得很糟的配对会通过门禁——它不该通过评审。**

这句话把质量责任明确交回给评审人，是这套机制里最成熟的部分。

### 分节哈希 vs 整文件哈希

上游从整文件哈希迁移到分节哈希是有实测数据的：在一次历史回放里，整文件哈希在 850 个合并提交上产生冲突，分节哈希降到 595 个（**减少 46%**）。原因是分节记录让 git 的默认文本合并能处理互不相干的小节。

**如果你要自建，直接做分节版本。** 整文件哈希的冲突率在多人协作下不可接受。

本 skill 打包的 `agent-notes` 归档门禁用的是整文件 Git blob 哈希（`foo.i18n.yaml` 一条文件两行记录），活跃树则不做哈希、只做结构镜像——分节记录要解决的是活跃文档的并行合并冲突，而归档树封存后不可变，不存在这个问题。为并行编辑的活跃文档集自建配对门禁时，才需要分节版本。

### 自建前提

如果确实需要双语：约一千八百行 TypeScript、一份术语表、一个翻译提示词模板。

**不需要双语的场景下有一个通用内核值得单独抽取**：把「两份必须同步的文档」按节哈希记账，可用于 README 与其副本、文档与代码示例、上游 API 文档与本地镜像。剥离语言维度后，它是一个通用的**文档漂移检测器**。

## 什么时候开始做这些

**别一开始就做。** 上游是在有了稳定的协作节奏和明确的痛点之后才逐步建立的——决策记录先于审批加权，归档机制晚于语料积累。

判断顺序：

1. **决策记录**（`agent-notes`）——先做，收益立竿见影且零依赖。
2. **门禁图与文档治理**（本 skill 主体）——随第一个真实痛点加入，不要预先设计完整体系。
3. **标签正交与 Issue 状态机**——团队超过三人、或 Issue 队列开始失控时。
4. **加权审批**——评审质量出现明显的参差时。
5. **多序列发布**——发布单元真正分家（有独立消费者）时。
6. **双语配对**——确实需要维护两种语言时。

每一步的共同特征是：**它解决的是一个已经发生过的具体问题**，不是为了完整性而设计的。

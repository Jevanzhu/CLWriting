# 从零建立

`bootstrap.ts` 只做机械的事，并且刻意**不做**需要判断的事。理解这条边界，就不会指望它替你想清架构。

```sh
node ~/.agents/skills/project-harness/scripts/bootstrap.ts --target ~/myproj --dry-run
node ~/.agents/skills/project-harness/scripts/bootstrap.ts --target ~/myproj
```

中文语料在第一次铺的时候声明语言，别等铺完再改：

```sh
node ~/.agents/skills/project-harness/scripts/bootstrap.ts --target ~/myproj --notes-language zh
```

`--notes-language`（缺省 `en`）一次定下四件事：`harness.json` 里的 `primaryLanguage`、决策记录树的目录名（`提案中/已实施/已否决` × `功能/缺陷修复/简化/架构/流程/测试`、归档容器 `归档/`）、归档说明书用的语言、以及起步模板取哪一版（`AGENTS`、`docs/AGENTS`、`lefthook` 各按语言两版）。它只在**首次铺树**时生效：目标已经有 `harness.json` 时以声明为准，旗标与声明不符会直接报错退出——换语言要移动整棵树，那是独立的一次改动，不是重跑的副作用。工作语言该定哪一种，见 [language-policy.md](language-policy.md)。

## 新项目 vs 已有项目

**空仓库**直接跑。**已有内容的仓库**加 `--adopt`，这是两种情况的唯一区别，但它是关键区别：

```sh
node ~/.agents/skills/project-harness/scripts/bootstrap.ts --target ~/myproj --adopt
```

不加 `--adopt`，装完立刻跑门禁会撞上一堵红墙——link 门禁会抓住你几年积累下来的所有死链，而它**没有能力区分「历史遗留」和「你这次改坏的」**。一堵第一天就全红的门禁，第二天就会被关掉。

`--adopt` 做的是：把目标仓库**当前已存在**的违规记进债务台账 `scripts/harness/baseline.json`，于是门禁从这一刻起只拦**新产生**的违规。

## 债务台账：棘轮机制

台账是「历史遗留」的唯一真相来源，格式是「门禁 id → 已接受的违规键」：

```json
{
  "version": 1,
  "entries": {
    "markdown-links": ["docs/DESIGN.md|api.md"],
    "markdown-wrap": ["README.md|This paragraph is wrapped ⏎ across two lines."]
  }
}
```

三条规则让它只能**变小**：

1. **默认拒绝扩张。** 台账已有条目时，`--write-baseline` 遇到新的违规会**直接报错退出**，除非显式加 `--accept-new`。「记录第一天的债」和「放过一次回归」在命令上就是两个不同的东西，评审的人一眼能看出来。
2. **陈旧条目每次运行都会报告。** 修掉一条债后，门禁会打印「N 条台账条目已不再匹配任何东西」——提醒你重记一次，把它从文件里删掉。
3. **记账是显式动作。** 只有 `--write-baseline` 会写台账；日常运行只读。

键的选择决定了台账会不会反复churn。link 门禁用 `路径|链接目标`（改上面的行不影响它），wrap 门禁用 `路径|上一行文本 ⏎ 下一行文本`（行号会随任何编辑漂移，文本不会；反过来说，**改动那段文字就会让它重新暴露**——而这正是应该顺手合并的时候）。

生产环境的正确用法是**分批还债**：修一批 → `--write-baseline` 重记 → 台账文件在 diff 里可见地变短。台账不是批准书，是待办清单。

## 它会做什么

1. **建 Agent Note 生命周期树**：三个 lifecycle × 六个 class，各放一个 `.gitkeep` 让 git 保留空目录；目录名按 `--notes-language` 拼写（缺省英文：`proposed/`、`implemented/`、`rejected/`）。
2. **建归档树**：六个 class 目录**全部建出**（即使为空——归档门禁要求六个都在），加空的 `manifest.json` 与 `AGENTS.md`；后两者只写一次，重跑不再触碰——它们随封存树冻结。
3. **复制校验器**到 `<target>/scripts/harness/`，并把安装来源的版本写进 `scripts/harness/version.json`（安装方元数据：内容一变就刷新，不是你的申报项）。
4. **实测词数生成文档预算**：读 `AGENTS.md`、`docs/AGENTS.md`、`README.md`、`docs/architecture.md` 里存在的那些，按当前词数 × 1.15 作为初始上限（词数 = 空白分词 + 每个汉字另计一词）。留 15% 余量是因为初始上限不该立刻就对现有内容亮红灯。
5. **复制起步模板**：`AGENTS.md`、`docs/AGENTS.md`、`lefthook.yml`——按 `--notes-language` 取对应语言的那一版，且**只在首次铺装**（目标还没有 `scripts/harness/run-gates.ts`）、目标不存在同名文件时复制；升级重跑不复活已删除的起步文件（它们仍在 skill 的 `templates/` 下，要找回自取）。
6. **`--adopt` 时录制债务台账**：跑一遍 link 与 wrap 门禁并 `--write-baseline`，把当前违规记为已接受债务。

注意第 4 步和第 6 步是同一种设计：**都是从当前实测值起步，而不是从理想值起步**。文档预算不因为现有文档超长就报错，债务台账不因为现有死链就报错。棘轮的原则是「只能变好」，不是「立刻变好」。

`--dry-run` 只打印计划，不写任何文件。默认不覆盖任何已存在文件。

`--force` 用于升级后刷新校验器副本，**只覆盖校验器**。五份 manifest（文档预算、文档索引、注释卫生、测试面、宣称）装的是你自己的申报，不在它的覆盖面里；`run-gates.ts` 底部的门表也是申报——它改过就默认保留（不改动的副本照常升级），覆盖它同样是 `--reset-manifests` 的事。

要重新生成 manifest，用 `--reset-manifests`：它把每一份按当前实测的树重播一遍，门表一并还原成预置的，**你写在里面的申报会被覆盖**。破坏性动作有自己的名字，就不该是升级的顺带效果——`--force` 曾经连它们一起重置，一次例行升级能让索引与宣称清单变成空文件、注释规则退回起步形状，而采用方不会收到任何提示，门禁只是安静地少管一片地方。

加 `--adopt` 时 `--dry-run` 会说明将要录制什么而不实际执行。

## 为什么校验器是复制而不是引用

**门禁必须在全新 clone 里、在没有任何 skill 安装的 CI 里跑得起来。**

如果校验器靠符号链接指向 skill 目录，那么：CI 上跑不了（没装 skill）、别人的 clone 上跑不了、skill 升级后目标仓库的行为静默改变。把校验器复制进仓库后，它是**仓库自己的代码**，随仓库版本化，改了要评审，升级要显式 `--force`。

代价是重复：同一个校验器会在多个仓库各有一份。这个代价是值得付的，因为另一种做法会让门禁失效。

## 它不做什么（这些需要你判断）

**AGENTS.md 的内容。** 模板给的是空骨架。**standing orders 只写「每次会话都需要在上下文里的规则」，一条一到三行，各自链到它的家。** 不要在这里放故事、worked example、情境流程——那些属于 references 或 docs。

判断某条规则该不该进 AGENTS.md：问「agent 这次不懂它，会不会犯一个昂贵的错误」。会，才写进去。不会，就放在它应该在的文档里，让需要的人去读。

**门禁清单。** `run-gates.ts` 底部的 `MODES` 表就是这个仓库的检查声明。模板里预置了文档门禁；其余要你按技术栈填。填的时候读一遍 [gates.md](gates.md) 的检查表——特别是「跑一次确认它真的会失败」。

**package.json 脚本。** 每个门禁最好有一个 npm script 名字，让编辑器、CI 和人都走同一个入口。**聚合本身住在门禁表的 `MODES` 里，package.json 只是它的壳**：`"check": "node scripts/harness/run-gates.ts text"` 这样的脚本不再自己列门禁，于是成员名单只有一处，加规则时不会漏掉某一条入口。门的依赖关系由门禁图拥有。

**提交钩子。** 模板的 `lefthook.yml` 只放了几条立刻能修的小事。**不要往钩子里加测试和构建**——它会让开发者学会用 `--no-verify`，而一个被绕过的钩子比没有钩子更糟，因为它制造了「有检查」的错觉。

**CI 接线。** 把同一个聚合命令接进 CI。关键是分支保护只要求**一个**聚合检查名。

## 顺序建议

先做最小可用的，跑通再加：

1. `bootstrap`（已有仓库加 `--adopt`）→ 立刻跑一次 `doc-quick`，应该是绿的。
2. 写 `AGENTS.md` 的前十条规则。**不要**一次写五十条。
3. 加第一个真正有价值的门禁（通常是 lint 或类型检查），并**制造一次失败**确认它会红。
4. 接进 CI，在分支保护里要求那个聚合名。
5. 装提交钩子。
6. 之后按痛点加门禁。**加门禁的门槛应该是「这件事已经出过一次问题」，不是为了完整而完整。**
7. 已有仓库：随手还债。改到哪个文件就顺手修哪个文件里的历史违规，然后重记台账。

一套只有六个门禁但每条都真的会拦人的体系，比一套六十个门禁但没人认真看的体系有价值得多。

## 与 agent-notes 的配合

`bootstrap.ts` 同时建好了 Agent Note 的目录树，但**写第一篇决策记录**是 `agent-notes` skill 的事。两者的分界：本 skill 决定「规则住在哪里、怎么强制」，`agent-notes` 决定「一个决策怎么被记录」。

## 升级

skill 更新后，用 `--force` 重跑可以刷新 `scripts/harness/` 下的校验器副本。**这会覆盖你对校验器的本地修改**——如果你改过它们（这很正常，门禁本来就该按仓库定制），先 diff 一下再决定。校验器里唯一的例外是门表 `run-gates.ts`：它写的是这个仓库的检查声明，改过就默认保留（没改动的副本照常升级），还原成预置表要显式 `--reset-manifests`；manifest 里的申报同样不受影响。

升级是**行为变化**，不只是代码刷新：同一份文档在旧版过得了门、在新版可能过不了（口径会变），而描述门的行为、或说明「为什么不接某道门」的文档写的是旧行为却不自知；复制进仓库的起步文档里承诺的命令（「跑这个模式」）同样如此。碰到改门禁的版本，这些陈述要同批核对更正——它们是行为的副本，副本不会自己更新。

升级后确认装的是哪一版：`scripts/harness/version.json` 记录复制这些校验器时 skill 的版本，`bootstrap` 的输出行里也会打印。版本号只住在 `skills/VERSION` 一处，两个 skill 一起发版、共用一号；凡是改动 `scripts/`、`SKILL.md`、`references/`、`templates/` 下任何文件，都同批动它——采用方据此回答「我这个仓库装的是哪一版」，而这一问只在出问题时才有人问。

把「校验器副本已按本地需要修改」这件事记在 `scripts/harness/README.md` 里，否则下次升级会丢掉你的改动；写进门表的采用面不在此列——那是声明，升级不覆盖。

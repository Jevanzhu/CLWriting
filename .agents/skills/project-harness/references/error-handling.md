# 错误处理

四条原则。每一条都对应一类真实事故，所以理由比条款重要。

## 一、类型化、结构化的失败

失败要有**声明的类型**、稳定的判别式、以及保留的 cause。机器用来分支的身份标识与展示给人看的文本必须分离。

**`Never route handling by parsing messages.`** 靠匹配错误文本决定怎么处理，等于把文案改动变成行为改动——改一个错别字就能让重试逻辑失效。

好形态：错误对象带 `code`（稳定的、机器读的）和 `message`（人读的、可自由改动），并保留 `cause` 指向底层失败。跨进程或跨网络时，判别式要能序列化。

## 二、catch / recover / stop

**`Catching limits exception propagation, not mutations.`** 这是最容易被忽略的一条。

catch 一个异常不意味着状态回到了抛出之前。如果被调用的函数已经写了一半的数据、已经释放了资源、已经把缓存改脏了，那么捕获异常之后进程继续运行，**带着一个不一致的状态**。

**`Only the affected state's owner can establish safe continuation.`** 处理归属因此不能靠「就近原则」。一个中层函数不该吞掉它不理解的状态损坏——它既不知道损坏的范围，也不知道怎么修。

层级分工：

- **能真正恢复的层**（拥有那个状态、知道怎么回退）→ 恢复并继续。
- **不能恢复的层** → 向上传播，并**明确标记状态的不确定性**。
- **顶层** → 停止依赖该状态的工作，显式报告，给出安全的下一步。

**`Logging alone is not recovery.`** 记一行日志然后继续跑，是把一个已知的失败变成后续更难诊断的失败。

## 三、报告要本地化、可操作、可见

每个最终报告包含三段：

1. **可读摘要**——发生了什么
2. **受影响的操作**——什么没做成、什么处于未知状态
3. **安全的下一步**——读者现在应该做什么

第三段最常被省略，也最重要。

**`Never claim success, rollback, or safe retry without guarantees.`** 没有回滚就别写「已回滚」。不确定是否幂等就别写「可以安全重试」。不确定状态是否一致就说「状态未知，请先核对 X」。

具体的诊断信息比抽象的更好：`timeout 必须是正数，当前值是 -1，检查 <路径> 的 timeout 字段` 胜过 `配置无效`。前者读者能直接行动。

**区分「未知」和「失败」**：抛出异常表示明确失败；超时、连接中断、进程被杀表示**结果未知**——请求可能已经成功落地了。这两者的处理方式完全不同，把未知当失败会导致重复执行。

## 四、验证结果，不是验证「捕获到了异常」

**`Verify resulting state and visible outcomes, not merely that an exception was caught.`**

测试错误处理时，「抛出了预期的异常」只是故事的一半。真正的断言应该是关于**世界状态**的：文件没被创建、计数器没被递增、锁被释放了、下次调用能成功。

一个只断言「捕获到了异常」的测试，在异常处理代码什么都没做的情况下也会通过。

## 资源与生命周期

- **释放要幂等**：能被调用两次而不出错的 `close()`，比要求调用者精确控制次数的 `close()` 可靠得多。
- **不要在 catch 里做可能再次失败的事**：回滚路径本身失败时要有兜底，否则会掩盖原始错误。
- **取消要显式**：await 期间被取消的操作必须检查取消状态，否则会带着已失效的前提继续执行。
- **空的 `catch` 要写下错误名和为什么**——空 catch 是明确的怀疑对象，让它自己解释自己的正当性。

一个空 catch 的合格形态：

```
try { await flush() } catch (error: unknown) {
  // A failed flush loses buffered telemetry only; the request already succeeded.
  if (!(error instanceof DiskFullError)) throw error
}
```

try 只包一条语句，catch 说明它吞掉的是什么以及为什么可以吞。

## 理论出处

这三条原则不是凭空来的，各自有明确的来源，理解它们有助于判断边界情况：

- **Meyer（1997）** — 契约式设计：前置条件、后置条件、类不变量。失败处理的第一步是明确「谁的义务」。
- **Sutter（1999）** — 异常安全保证的层级（基本保证、强保证、不抛保证）。「不做任何承诺」也是承诺，只是最弱的那种。
- **Armstrong（2003）** — 隔离与监督：「让它崩溃」在监督树存在时是正确的；在没有监督的进程里则是灾难。

判断一个错误该被捕获还是该向上传播，本质上是在问：**这里有没有那个能安全续行的所有者**。

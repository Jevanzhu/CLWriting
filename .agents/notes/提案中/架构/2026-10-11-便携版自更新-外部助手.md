# Agent Note: 便携版自更新由外部助手做目录交换

Status: proposed

## 问题

便携版用户升级要手动「下载 zip → 退出 → 解压覆盖 → 重启」，全程得知道 zip 放在哪、得会解压。要把它变成应用内的一键动作，先要面对一个 OS 层约束：Windows 会锁住正在运行的 `CLWriting.exe` 与已加载的 `.dll`，**应用在自身存活期间解不开自己的目录**——这与选用哪个下载或更新库无关。本决策已拍板但暂不实施（活账登记：排进版本计划才动工）。

## 提案

替换动作交给一个外部助手进程：应用下载并校验新版本 zip 后，起一个 detached 助手、自身退出；助手等锁释放，把 zip 解压到同级新目录，然后做**目录交换**——

```
解压到同级新目录 → 旧目录改名 .old-<版本> → 新目录改名成正式名 → 重启 → 启动成功后删旧目录
```

任一步失败，把旧目录名改回来即回滚。助手复用主 exe 的特殊 argv 模式（不增加分发面），并在 `main.ts` 最顶部按 argv 分支后直接 `return`：不建窗口、不起 server、不抢单实例锁。

## 曾考虑的替代方案

**形态 B：重启后自搬。** 退出前把新版本解压到同级暂存目录并写 `pending-update.json`，下次启动由极早期引导步骤改成「先起助手完成替换再重启」。落选原因：实际仍需助手（运行中的自己同样被锁），只是把「等进程退出」换成「启动早期介入」，而用户会经历一次「闪一下又重启」，观感更差。

**形态 C：`.cmd` / PowerShell 脚本替换。** 否决：执行策略与杀软启发式风险更高，且难做原子回滚。

**引入 `electron-updater`。** 不做：它要求 NSIS 安装包或正式签名，两条都与现状（便携 zip + ad-hoc 签名）冲突。

**增量 / 差分更新，或静默后台自动更新。** 不做：zip 全量替换约 200MB 级可接受；静默更新与「AI 与网络动作都让作者知情」的既有取向冲突。

## 验收标准

- 正常路径：点更新 → 下载有进度 → 校验通过 → 退出 → 目录已替换 → 新版本启动 → 旧目录被清。
- 回滚路径：替换各步人为中断（杀助手、拔盘、置只读）后，下次启动必须是可用状态（新的或旧的，不能是坏的），且有可诊断留痕。
- 多实例：第二实例在跑时点更新 → 明确提示，不静默失败、不损坏目录。
- 助手模式隔离：助手进程不建窗口、不起 server、不抢单实例锁（用例钉住）。
- 不变量：任何更新路径都不得触碰书库与 userData。

## 风险

- **代理用户可能必失败**：内置 fetch 不读代理——这是方案的存亡问题，动工前必须先实测 Electron `net` 与既有代理配置两条路。
- **杀软拦截**：对「等进程退出就替换二进制」的启发式拦截，本应用未签名、态势更差；助手不隐藏自己，失败回滚并留报告，长期靠购证签名。
- **替换中途断电**：目录可能停在「旧已改名、新未就位」；助手启动时先做恢复检查——目标目录缺失但存在 `.old-*` 就自动改回。
- **mac 不在本方案内**：自动更新需正式签名（现为 ad-hoc），购证后另开方案。

# Agent Note: 决策记录树与文件名随语料语言

Status: implemented

## 问题

主语言声明过去只管文件配对与骨架标题，目录名写死英文（`proposed|implemented|rejected` × `feature|bug-fix|…`）。中文语料因此停在半截：标题、正文全中文，路径全英文，读者在 `.agents/notes/implemented/process/` 里读中文决策，而 skill 早就在标题层把两种语言当成同一个槽的两套拼写——目录却只有一套。文件名主干也是英文 kebab，与同一篇笔记的中文标题不同词。

## 决策

主语言一次定下整棵树的拼写，与骨架标题同一套槽表（`aliases.ts`）：三个 lifecycle 目录（`提案中|已实施|已否决`）、六个 class 目录（`功能|缺陷修复|简化|架构|流程|测试`）、归档容器（`归档`）、文件名主干用语。两种拼写不混住一棵树——另一语言的拼写被门禁逐条点名，附上期望名与「那是另一语言的说法」一句。文件名的主题段不成门禁条目（判不了语言），按约定跟主语言走，模板与文档同批写明。

归档树是例外，且只例外一处：**封存的路径不改名**。类目录两套拼写都认，对照文件的 tier 按文件自身读，不再与当前声明比对——哈希清单钉死的是字节与路径，替已封存的历史改名等于伪造。归档容器不在例外里：清单的键相对容器，容器改名不动任何封存，所以容器跟声明走。

`bootstrap.ts` 增 `--notes-language en|zh`（缺省 `en`），一次铺出与声明一致的树、归档说明书与 `harness.json`；目标已有声明时以声明为准，旗标冲突直接报错退出——换语言要移动整棵树，属于独立的一次改动。

## 曾考虑的替代方案

**两套拼写都收（别名式，照标题的成例）。** 门禁同时认 `implemented/` 与 `已实施/`，存量语料零迁移。落选原因：那正是半截形态的另一种写法——一棵树里两种拼写并存，读者与脚本都得先问「这篇在哪套写法下」，而换来的迁移只是一个 `git mv` 能做完的事。

**只改目录，文件名主干留英文。** 改动面更小，不必动格式细则里的命名条与既有引用。落选原因：路径的后半截仍是英文，中文语料的读者要对着 `已实施/流程/2026-10-14-docs-root-location.md` 猜主题；配对本就共用主干，主干取主语言的词不破坏配对。

## 后果

换来的：中文语料从容器到文件名一路中文，标题与路径同词，检索与浏览不再跨语言；门禁仍按槽判名，英文语料与上游语料的形态一字未变。本仓一次迁移：三个 lifecycle 与归档容器、二十四个类目录、五篇文件名，连同扫描面清单与活面引用（规范第七、九节、`markdown-patterns.json` 的 glob、被引用的那篇记录）同批改。旧路径到新路径的对照见 `02-执行/docs-落位与语别改造-执行方案-2026-10-14.md` 批 F 记录——批 A–D 的执行记录与历史散文里的英文路径不回改，那是当时的名字。

付出的：主语言从文件级的声明变成树级的声明，改语言等于移动整棵树，是一次显式动作而非重跑的副作用；归档树里因此可能住着混拼写的历史（封存当时的样子），读者要认这一点，归档侧的门禁也不再拿当前声明去核对类名与 tier。

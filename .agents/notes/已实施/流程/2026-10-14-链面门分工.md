# Agent Note: 链面门只接三面，自建 check 不退役

Status: implemented

## 问题

本仓装 skill 附带的门禁校验器之后，同一条纪律出现了两个可能的执行者：自建的五道 check，与 skill 的泛化门。两边都接，同一事实就有两个声明点，改一边不红、改两边才不红；只接 skill 的门，自建 check 里那些泛化门没有的判据会净损失。而且「不接」这件事如果不写下来，看起来就像忘了接线——下一个读门表的人会顺手把它接上。

## 决策

链面机器门 = `npm run check:harness`（`scripts/harness/run-gates.ts` 的 `text` 模式），只接三门：`markdown-links`（相对链接与锚点）、`markdown-wrap`（一句一行，存量硬换行挂 `baseline.json` 债务台账）、`doc-index`（文件树 ↔ 索引一致、槽位篇数一致、槽位顶层档被索引提及）。扫描面住 `scripts/harness/markdown-patterns.json`，槽位声明住 `doc-index.manifest.json`。

不接线的四面在 manifest 里一律声明 `{}`：

| 面 | 执行者 | 不接的原因是判据不同源 |
|---|---|---|
| 注释卫生 | 自建 `check:comments` | 含 `.vue` 注释面、跨行配对、切除残形，与仓库自己的清理器同源 |
| 测试面 | 自建 `check:counts` | `.only` / 无条件 `.skip` 由 AST 扫描，另有零断言门、批号上锚、顺序快照 |
| 篇幅 | 自建 `check:docs` | 中文档按单行长度；skill 的预算门量总量（中文逐字计入），判据不同轴 |
| 数字声称 | 自建 `check:counts` | README 与索引面的声称值全场对账，覆盖比通用 manifest 宽 |

`{}` 声明的是「本仓不声明该面」，不是「该面已清白」；改分工必须同批改门表与规范第八节。

## 曾考虑的替代方案

**用 skill 泛化门全量替换自建 check。** 最强的一条理由是它把「同一条纪律两个执行者」一次消掉：声明点从两处收成一处，分工表不必靠人守，改漏门表与规范也不会漂移。落选原因：`check-comments` 与 `check-counts` 的判据超出泛化门——泛化门只看注释标签与测试聚焦标记，自建门还管跨行配对残形、零断言用例、pageerror 接线、批号上锚与顺序快照；替换是净损失。

**为五个自建 check 补 manifest 声明面、纳入 harness 门表。** 落选原因：它们已是「仓库自己的代码」形态——判据写死在脚本里、随仓库评审与版本化，符合门表对采用方的要求；再包一层声明只会多出一份要同步的清单。

## 后果

换来的：每条纪律只有一个执行者、一个声明点；四份 `{}` manifest 让「哪些面明确不声明」成了可读事实，升级 skill 副本时不会被误当成漏接线；链面三条判据随副本升级自动获得上游修复。

付出的：分工靠人守——门表与规范第八节要同批改，改漏了机器不拦；skill 升级带来新的泛化门时，要重新判一次接或不接，而这一步没有判据表可查，只能读两边的判据原文。

# Agent Note: 便携版自更新由外部助手做目录交换

Status: implemented

## 问题

便携版用户升级要手动「下载 zip → 退出 → 解压覆盖 → 重启」，全程得知道 zip 放在哪、得会解压。要把它变成应用内的一键动作，先要面对一个 OS 层约束：Windows 会锁住正在运行的 `CLWriting.exe` 与已加载的 `.dll`，**应用在自身存活期间解不开自己的目录**——这与选用哪个下载或更新库无关。

## 决策

替换动作交给一个外部助手进程：应用下载并校验新版本 zip 后，起一个 detached 助手、自身退出；助手等旧进程退出，把 zip 解压到同级新目录，做**目录交换**——

```
解压到同级新目录 → 旧目录改名 .old-<旧版本> → 新目录改名成正式名 → 重启 → 启动成功后删旧目录
```

任一步失败，把旧目录名改回来即回滚。助手起手先做恢复检查：目标目录缺席而 `.old-*` 在场（中断停在「已改名、新未就位」窗）时，取 mtime 最新者改回。

助手复用主 exe 的特殊 argv 模式（不增加分发面，免去「助手自己也要更新」的鸡蛋问题），并在主进程入口最顶部按 `--apply-update` 分支后直接退出：不建窗口、不起 server、不抢单实例锁。

**助手一律从暂存副本运行**：退出链把整棵应用目录复制到 `<home>/更新缓存/<版本>/helper` 再拉起副本，argv 契约与交换序不变，复制失败 = 丢弃意图并留痕。这是真机实测倒逼的形态——Electron 进程自镜像在目标目录内时，目标目录改名必败 EPERM（真 `node.exe` 同形态不挡、Electron 镜像移出目标即通），证据见[批 0 前置验证调研](../../../../docs/04-调研/便携版自更新-调研-批0前置验证-2026-10-14.md)。

多实例（本产品一库一实例、共享同一应用目录）：替换前检测同目录下是否有其他存活实例（`queryLockHeld` 扫 `<home>/instances/*/app-instance.lock`），有则回滚并以人话提示「请先关闭其他窗口后重试」。闸落两处——点击时预检 + 助手预检。不主动 kill 其他实例：用户可能有未保存的稿子，主动杀进程不在本决策授权范围内。

下载与校验在主进程：便携 zip 落 `<home>/更新缓存/<版本>/`（共享根而非应用目录——放应用目录会在替换时被一起搬走），流式写 `.part`、完成即校验 sha256（来源优先 GitHub 资产 `digest`，兜底发布链的 `SHA256SUMS.txt`）后原子改名，失败 / 取消 / 断流一律删半成品。出站走 Electron `net.fetch`（受系统代理）——内置 fetch 不读代理，这是动工前实测过存亡的项。进度与取消经桌面桥 IPC 事件回传，不走 SSE：下载与替换都落在主进程 / 助手侧，走 SSE 要新增主进程 → server 子进程转发链，复杂度高于收益；浏览器模式无桥，保持「复制链接」降级。

提示面 = 工作区左栏标题条左端的角标 + 点击弹层 + 设置·关于页签；状态机、文案与桥订阅单源在 `stores/update.ts`。待重启态显式要求用户确认，有未保存内容时先走既有保存链。

**不搬 userData、不搬书库**：书库在用户自选目录、userData 在系统目录，都不在应用目录内——根 README 对用户的承诺（书稿怎么升级都动不到）由这条结构事实兑现。

## 曾考虑的替代方案

**形态 B：重启后自搬。** 退出前把新版本解压到同级暂存目录并写标记文件，下次启动由极早期引导步骤改成「先起助手完成替换再重启」。落选原因：实际仍需助手（运行中的自己同样被锁），只是把「等进程退出」换成「启动早期介入」，而用户会经历一次「闪一下又重启」，观感更差。

**形态 C：`.cmd` / PowerShell 脚本替换。** 否决：执行策略与杀软启发式风险更高，且难做原子回滚。

**原地覆盖而非目录交换。** 否决：中途被打断（断电、杀助手、杀软拦截）会留下「半新半旧」的目录，且无法回滚——这是最坏结局。目录改名在同卷上是近乎瞬时的元数据操作，任一步失败把名字改回去即可；代价是替换期需要约一份应用体积的空闲磁盘（便携软件可接受）。

**引入 `electron-updater`。** 不做：它要求 NSIS 安装包或正式签名，两条都与现状（便携 zip + ad-hoc 签名）冲突。

**增量 / 差分更新，或静默后台自动更新。** 不做：zip 全量替换（主程序约 200MB 级）可接受；静默更新与「AI 与网络动作都让作者知情」的既有取向冲突。

## 后果

换来的：便携版升级成为应用内一键动作（下载 → 校验 → 退出 → 替换 → 重启），用户不需要知道 zip 放在哪、不需要手动解压；每条失败路径都有回滚或可诊断留痕（结果条写 `<home>/更新缓存/更新结果.json`，下次启动展示），不静默损坏；助手不隐藏自己、不触碰书库与 userData 的承诺可被不变量核验。

付出的：替换期要求其他实例已关闭；磁盘上多留一份应用体积（助手暂存副本约 366 MB + 包体 154 MB，留存至下一次升级随旧版本缓存一并清扫）；「更新失败」类问题直接进作者报障面，且失败形态（杀软、只读盘、代理、多实例）比应用本体功能更碎；mac 不在本方案内（自动更新需正式签名，现为 ad-hoc，购证后另开方案）；助手形态在真机上被推翻过一次——从目标目录内运行必败 EPERM，最终形态是暂存副本，代价是每次更新多一次整棵目录复制。

未了结：起服子进程的更新检查出站不读系统代理（与下载腿的 `net.fetch` 不对称），仅系统代理的用户收不到更新提示——上游对照与落法待拍板，登记在活账。
